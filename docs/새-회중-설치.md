# 새 회중 세우기

> 2026-08-23 작성 · **2026-08-24 실제로 해 봤다.** 빈 Supabase 프로젝트에
> 구조를 세우고 운영과 개수를 대조해 전부 맞는 것을 확인했다.
> 그때 걸린 것들을 아래에 적어 두었다.

## 먼저 알아야 할 것

**코드는 복사하지 않는다.** 저장소 하나에 Vercel 배포를 여러 개 붙인다.
그래야 버그를 고칠 때 `git push` 한 번으로 모든 회중이 고쳐진다.
회중마다 다른 것은 **환경변수(어느 Supabase 를 보느냐)** 뿐이다.

**소유권은 회중마다 나눈다.** 새 회중 책임자가 자기 Supabase 조직과 Vercel 팀을
만들고 결제·복구 계정을 가진다. 설치를 대신할 때는 임시로 초대받아 작업하고,
인수인계 뒤에는 작업자 계정과 운영 키를 제거한다. GitHub에는 코드만 두며 회중
자료·백업·`service_role` 키를 올리지 않는다.

**DB 는 회중마다 따로 만든다.** 한 DB 를 나눠 쓰면(멀티테넌트) 쿼리 하나에
조건을 빠뜨리는 순간 남의 회중 명단·주소·방문 기록이 보인다. 그리고 그건
아무도 알려 주지 않는다. 비용(3곳부터 월 $25)을 내더라도 갈라 두는 편이 낫다.

**'프로토타입 DB' 를 따로 만들어 두지 않는다.** 우리 DB 에 새 SQL 을 돌릴 때마다
프로토타입에도 돌리는 일을 사람이 계속 기억해야 하고, 그건 반드시 실패한다.
대신 필요할 때 **우리 DB 에서 구조를 뽑고**, `npm run verify-install` 로
**살아 있는 우리 것과 대조**한다.

## 비용

무료 활성 프로젝트는 계정당 2개다. 그 다음부터 유료.

| 회중 | 구성 | 월 |

| 3곳 | 무료 2 + Pro 1 | $25 |

## 순서

### ① Supabase 프로젝트 만들기
지역은 가까운 곳(Northeast Asia / Southeast Asia). 만들 때 정한 **DB 비밀번호를
적어 둔다** — 나중에 구조를 넣을 때 필요하다.

### ② 확장 켜기
Dashboard → Database → Extensions 에서:

```
pgcrypto    비밀번호 해시 (로그인)
pg_cron     매일 정리·봉사 알림·세션 자동 종료
pg_net      푸시 발송 (Edge Function 호출)
```

### ③ 구조 넣기 — **실제로 해 본 절차**

```
supabase/baseline.sql          구조 전부 (157 KB)
supabase/baseline-extras.sql   예약작업 3 · 버킷 2 · 스토리지 정책 5
```

SQL Editor 에서 **이 순서대로** 통째로 붙여 실행한다. 에러 없이 돌았다.

**낡았으면 다시 뽑는다.** `pg_dump` 는 DB 비밀번호가 필요하고 supabase CLI 는
Docker 가 필요하다. 둘 다 없으면 SQL Editor 로 뽑는 길이 있다.

```
1. supabase/tools/_EXPORT_schema.sql 을 **파일에서 새로 열어** 통째로 실행
   (결과 첫 칸 query_version 으로 옛 탭 실행인지 구분한다)
2. Download CSV
3. npm run db:baseline <받은 파일>
```

> ⚠ **그 파일의 DDL 키워드를 도로 붙여 쓰지 말 것.**
> Supabase SQL Editor 는 쿼리 **글자**에서 `create table <이름>` 을 찾아 그 관계를
> 조회한다. 문자열 안이어도 반응한다 —
> `select 'create table public.x'` → 42P01 / `select 'public.x'` → 정상.
> 그래서 `'create' || ' table …'` 로 끊어 놓았다. 이걸 모르고 사흘을 헤맸다.

### ③-0 baseline 뒤에 나온 것 이어서 실행

`supabase/migrations/` 의 `.sql` 을 **파일 이름 순서대로 전부** 실행한다.
이름에 날짜·시각이 박혀 있어 순서를 따로 기억할 필요가 없다.

baseline 은 뽑은 시점의 사진이라 그 뒤에 넣은 것은 안 들어 있다.
`applied/` 는 baseline 이전의 옛 기록이라 여기서 실행하지 않는다.

### ③-1 확인 — 개수를 대조한다 (**이걸로 끝이 아니다**)

`supabase/tools/_VERIFY_new_project.sql` 을 새 프로젝트에서 실행한다.
2026-08-24 기준 열두 항목이 전부 맞았다.

```
테이블 40 · 뷰 1 · 시퀀스 33 · 함수 59 · 트리거 12 · 인덱스 28
정책 42 · RLS 켠 테이블 38 · realtime 12
예약작업 3 · 스토리지 정책 5 · IDENTITY 컬럼 4
```

> ⚠ **개수가 맞아도 뚫려 있을 수 있다.** 실제로 열두 항목이 전부 맞은 채로
> `anon` 이 `app_users.pin`(bcrypt 해시)을 읽을 수 있었다. 아래 ③-2 를 꼭 볼 것.

**실제로 해 보고서야 잡은 것 세 가지:**

**IDENTITY 컬럼이 통째로 빠졌었다.** `login_logs` · `notices` · `review_tasks` ·
`service_suggestions` 의 `id` 에 기본값이 없었다. IDENTITY 는 기본값 테이블이
아니라 `pg_attribute.attidentity` 에 있다. 이대로 세우면 공지 작성·로그인 기록이
**전부 insert 에서 실패한다.** (지금은 고쳐져 있다)

**새 프로젝트는 테이블을 만들 때 RLS 를 켜 둔다.** 운영에서 꺼져 있는
`special_periods` · `login_logs` 까지 켜졌다. **정책이 없는 채로 켜져 있으면
에러가 아니라 빈 결과가 온다** — `special_periods` 는 화면이 직접 읽으므로
특별봉사 시즌이 조용히 사라진다. baseline 이 이제 `disable` 도 적는다.

### ③-2 권한 확인 — **개수로는 안 드러난다**

새 Supabase 프로젝트는 테이블을 만들 때 권한을 통째로 준다. 운영의 PIN 보호는
'테이블 SELECT 를 주지 않고 컬럼별로만 준다' 에 기대고 있어서, 회수하지 않으면
**anon 키로 bcrypt 해시를 가져갈 수 있다.**

```sql
select grantee, privilege_type
from information_schema.role_table_grants
where table_schema = 'public' and table_name = 'app_users'
  and grantee in ('anon','authenticated') and privilege_type = 'SELECT';
```

**행이 나오면 뚫린 것이다.** 이렇게 되돌린다.

```sql
revoke all on public.app_users from anon, authenticated;
grant DELETE, INSERT, UPDATE on public.app_users to anon, authenticated;
grant SELECT (id, login_id, name, role, phone, group_name,
              approval_status, is_active, created_at, last_login_at)
  on public.app_users to anon, authenticated;
```

> v6 이후의 `_EXPORT_schema.sql` 은 회수를 먼저 적으므로 이 단계가 필요 없다.
> 옛 baseline 으로 세웠다면 반드시 확인할 것.

### ③-3 회중 기본 설정

`supabase/tools/_SET_새회중_기본설정.sql`을 열어 다음 값을 그 회중 것으로 고친 뒤
새 프로젝트에서 실행한다.

```text
name                 회중 표시 이름
province             주소의 광역 시·도 전체 이름
provinceShort        지도 검색에 함께 시도할 짧은 이름
defaultCity          시가 빠진 주소에 붙일 기본 시·군
mapCenter            건물이 하나도 없을 때 처음 보일 지도 중심
territoryBoundary    전체 회중 외곽선 [경도, 위도] 배열. 없으면 []
placeNames           동·읍·면의 [한국어, 중국어, 영어] 번역. 없으면 []
```

이 값은 **그 회중 Supabase에만** 저장된다. 같은 GitHub 코드로 배포해도 각 Vercel은
자기 Supabase 설정을 읽으므로 지도 중심·주소 검색·경계·지명 번역이 섞이지 않는다.
설정 행이 없으면 특정 회중 자료가 없는 중립값을 사용한다. 현재 용인 운영값은
2026-09-08 운영 DB의 `congregation_profile`로 이관했고, 경계 좌표가 든 일회성
SQL은 적용 직후 저장소에서 제거했다.

지역(구·시) 이름과 상위 시·번역은 별도로 `territory_regions`에서 읽는다. 새 회중이
아직 지역을 하나도 만들지 않았다면 용인 지역을 가짜로 표시하거나 `미배정 건물`
카드를 먼저 만들지 않는다. 지역을 만든 뒤 새로고침하면 첫 지역을 기준으로 만든다.

> ⚠ 현재 저장소의 과거 Git 기록에는 예전 용인 경계 파일이 남아 있다. 다른 회중에
> 저장소 접근 권한을 주거나 공개하기 전, 개인정보와 운영 자료가 없는 깨끗한 배포
> 저장소를 현재 소스 스냅샷으로 새로 만들고 그 저장소를 공통 원본으로 삼는다.

### ④ cron 작업 등록
`supabase/applied/` 에서 `cron.schedule` 이 들어간 SQL 을 찾아 그 부분만
새 프로젝트에서 실행한다.

```
v3_data_retention.sql          매일 정리 (KST 04:00)
v3_daily_service_digest.sql    오늘의 봉사 알림
v1plus_auto_service_session_v2.sql  세션 자동 종료
v2_service_logs_developer_only.sql
v3_management_tools.sql
```

### ⑤ 스토리지 — **건너뛰지 않는다**

채팅 사진 첨부가 스토리지를 쓴다. `baseline-extras.sql` 에 버킷 2개와
`storage.objects` 정책 5개가 들어 있으니 그걸 실행하면 된다.

> ⚠ 정책이 없으면 업로드가 `new row violates row-level security policy` 로 막힌다.
> 예전에 실제로 겪었다.

### ⑥ 푸시 열쇠(VAPID) 만들기

**회중마다 새로 만든다.** 우리 것을 복사하면 그 회중 앱에서 우리 회중 사람들에게
알림을 보낼 수 있게 된다.

```bash
npx web-push generate-vapid-keys
```

### ⑦ Edge Function 배포 + 비밀값

```bash
supabase link --project-ref <새 프로젝트 ref>
supabase functions deploy send-push --no-verify-jwt
supabase functions deploy cleanup-chat-images
```

> ⚠ `--no-verify-jwt` 가 **꼭 필요하다.** 이 함수는 Supabase JWT 가 아니라
> 자체 키(`PUSH_EDGE_FUNCTION_KEY`)로 호출자를 확인한다.

**함수 쪽 비밀값** (Dashboard → Edge Functions → Secrets, 또는 `supabase secrets set`):

```
VAPID_PUBLIC_KEY         ⑥ 에서 만든 공개키
VAPID_PRIVATE_KEY        ⑥ 에서 만든 비밀키   ← 여기 넣는다
VAPID_SUBJECT            mailto:담당자@주소
PUSH_EDGE_FUNCTION_KEY   아무 긴 무작위 문자열 (직접 정한다)
```

**DB 쪽** (SQL Editor). 이게 있어야 트리거가 함수를 부른다:

```sql
insert into app_private_settings (key, value) values
  ('push_edge_function_url', 'https://<ref>.supabase.co/functions/v1/send-push'),
  ('push_edge_function_key', '<위와 똑같은 PUSH_EDGE_FUNCTION_KEY>')
on conflict (key) do update set value = excluded.value;
```

> ⚠ **VAPID 비밀키는 DB 에 넣지 않는다.** 함수는 환경변수만 읽는다.
>   `app_private_settings` 에 넣어도 아무 일도 일어나지 않는다.
>   (예전 문서가 그렇게 적혀 있었다 — 그대로 하면 푸시가 안 나간다)

### ⑧ Vercel 배포 만들기
**같은 저장소**를 보는 새 프로젝트를 만들고 환경변수만 그 회중 것으로 넣는다.

```
VITE_SUPABASE_URL
VITE_SUPABASE_ANON_KEY
VITE_NAVER_MAP_CLIENT_ID     주소마다 등록이 필요하다 (약관·한도 확인)
VITE_VAPID_PUBLIC_KEY
```

⚠ **우리 회중의 Vercel 주소는 절대 바꾸지 않는다.** 바꾸면 홈화면 PWA·로그인
세션·푸시 구독이 전부 무효가 된다 (CLAUDE.md 참고).

### ⑨ 검사

```bash
npm run verify-install -- --target-url https://xxx.supabase.co --target-key <service_role>
```

표와 함수가 우리와 같은지 대조한다. 빠진 것이 있으면 ③을 다시 한다.

### ⑩ 첫 관리자 계정
아직 화면이 없다. SQL Editor 에서 직접 넣는다 (트리거가 PIN 을 해시로 바꾼다).

```sql
insert into public.app_users (login_id, name, pin, role)
values ('admin', '관리자 이름', '0000', 'admin');
```

첫 로그인 뒤 **바로 비밀번호를 바꾸게 한다.**

### ⑪ 그 회중이 채울 것
관리자가 로그인해서 자기 것부터 만든다. 우리 데이터는 하나도 넘어가지 않는다.

```
설정 → 지역 관리        지역(구·시) 추가
구역 → 새 구역 카드      지역·동·번호
사용자 관리             집단 이름, 계정
```

### ⑫ 사람들 설치
홈화면에 PWA 추가 + 알림 허용. 이때 푸시 구독이 만들어진다.
