# 운영 반영 체크리스트 (2026-09-13)

이 문서는 데모에서 확인한 변경을 용인 운영 환경에 반영할 때의 순서다.
운영 데이터 쓰기는 이 문서를 검토한 뒤 별도 작업으로 실행한다.

## 1. 운영에 이미 반영된 기반

- 쓰기 RLS 전환: `TEMP_session_gate_*` 0개
- 역할별 일정·배정·개인 봉사·구역 구조·방문 기록·사용자 정책
- 정기방문 종료, 끊긴 담당 재배정, 장소 수정·삭제 요청 흐름
- 호수 표기와 세대 용도 마이그레이션

운영 작업 전에 `.env.local`에 아래 값이 있는지 먼저 확인한다. Vercel CLI가
프로젝트 연결 과정에서 파일을 다시 만들 수 있으므로 키 이름만 검사하고 값은 출력하지 않는다.

- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_ANON_KEY`
- `VITE_NAVER_MAP_CLIENT_ID`
- `SUPABASE_SERVICE_ROLE_KEY`
- `SUPABASE_DB_URL`

현재 Vercel Production 환경에서 클라이언트 키 세 개는 다시 내려받았다.
`SUPABASE_SERVICE_ROLE_KEY`와 `SUPABASE_DB_URL`은 Vercel에 보관된 값이 없어
Supabase 대시보드에서 복구해야 한다. 테스트 smoke는 별도 `.env.test.local`의
`SUPABASE_DB_URL`을 사용한다.

그다음 운영에서 아래를 한 번에 확인한다.

```sql
select
  (select count(*) from pg_policies
    where policyname like 'TEMP_session_gate_%') as temp_policies,
  (select value from public.app_private_settings
    where key = 'environment') as environment_marker,
  (select count(*) from information_schema.tables
    where table_schema = 'public' and table_name = 'event_cart_applications') as cart_table,
  (select count(*) from pg_proc p
    join pg_namespace n on n.oid = p.pronamespace
    where n.nspname = 'public' and p.proname = 'reset_demo_environment_tx') as demo_reset_function;
```

기대값은 `temp_policies=0`, `environment_marker=null`, `demo_reset_function=0`이다.
`cart_table`은 전시대 기능 적용 여부 확인용이다. SELECT 정책은 Realtime 계약 때문에
이번 배포에서도 변경하지 않는다.

## 2. 전시대 기능 보류

- 전시대 신청자 명단 공개 범위와 전시대 일정 공개 범위가 아직 결정되지 않았다.
- 전시대 마이그레이션과 전용 smoke는 운영 후보에서 제거해
  `wip/demo-cart-review-20260913` 브랜치에 보존했다.
- 운영에서는 `VITE_CART_APPLICATIONS_ENABLED`를 설정하지 않는다. 기본값은 `false`다.
- 기능이 꺼지면 전시대 DB 조회·Realtime 구독·RPC 호출과 관련 UI가 모두 비활성화되고,
  일반 봉사 신청은 기존 `event_participants` 계약을 사용한다.
- 계약이 정해지면 권한 정책, 화면 가림이 아닌 서버 조회 계약, rollback을 함께 작성하고
  다시 리뷰받은 뒤 DB 마이그레이션과 `VITE_CART_APPLICATIONS_ENABLED=true`를 함께 배포한다.

### 운영에 적용하지 않을 SQL

- `supabase/demo/20260913_1100_demo_environment_reset.sql`
- 외부 시연 DB 전용 초기화 함수와 가짜 자료다.
- 함수 자체에 테스트 환경 가드가 있지만 운영에는 배포하지 않는다.

## 3. 코드 배포 항목

- 세대 생성 Realtime 반영: 다른 봉사자의 휴대폰에도 새 세대가 즉시 표시됨
- 특별봉사 시즌: 시작일·종료일 입력과 모바일 날짜 칸 정리
- 캘린더 특별봉사 표시와 일정 폼 배치 정리
- 비활성·미승인 사용자를 참가자 수동 추가 목록에서 제외
- 게스트 이름 입력과 파란 테두리 구분
- PC 캘린더 신청자 잘림과 일정 상세 배치 수정
- PC 지도 확대·축소와 구/동 포인트 표시 개선
- PC 구역 관리 도구막대, 표, 상세 패널 겹침 수정
- 공지와 댓글 UI 제거. 채팅과 시스템 점검 공지는 유지
- 대화 방법 제안 관리의 CSV 작업을 접힌 메뉴로 정리

코드 배포 전:

```bash
npm test
npm run build
npm run lint
npm run smoke:all
```

`smoke:all`은 등록된 테스트 DB에서만 실행한다. 알림 트리거를 건드린 배포라면
`npm run smoke:notify`도 별도로 실행한다. DB 적용이 있는 배포는 30분 이내에 만든
백업이 있어야 하며, 반드시 DB를 먼저 적용한 뒤 코드를 배포한다.

## 4. 데모에만 유지할 항목

- 브랜드 표기 `DEMO`, 테스트 지역과 예시 자료
- `관리자`, `인도자`, `봉사자` 시연 계정과 공통 PIN
- 개발자 전용 데모 초기화 버튼
- 초기화 시 생성되는 끊긴 정기방문 1건과 대기 중 자료수정 요청 1건
- 데모 Supabase와 데모 Vercel 프로젝트

## 5. 운영 배포 후 사람 확인

1. 일반 사용자: 일정 신청·취소, 채팅 열기
2. 인도자: 본인 일정 수정, 신청자 관리, 팀 구성과 구역 배정
3. 관리자: 사용자 승인, 장소 수정 요청 처리
4. 두 기기: 한 기기에서 세대 추가 후 다른 기기에 즉시 표시되는지
5. 모바일·PC: 공지와 댓글 진입점이 없고 시스템 점검 공지는 정상인지
6. PC 구역: 상세 패널을 열어도 카드 이름과 표 열이 겹치지 않는지

문제가 있으면 코드 배포는 이전 Vercel 배포로 되돌리고, DB는 해당 마이그레이션의
rollback 계약을 확인한 뒤 별도로 되돌린다. 데모 초기화 SQL을 운영 복구 수단으로 쓰지 않는다.
