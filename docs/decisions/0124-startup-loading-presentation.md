# 첫 로딩 화면 정리

- 상태: 데모 검증, 운영 미적용
- 결정일: 2026-11-18
- 기준: `ee13b02` (당시 데모에 배포된 앱 코드는 `76f73e3`와 동일)
- 요청: 기존 앱 느낌에 맞는 첫 로딩, 추가 대기와 데이터 사용량 증가 없이 데모만 변경

## 결정과 범위

JS 실행 전 index.html과 React AppLoading을 같은 배경, 지도 로고, Field Map 이름,
작은 회전 표시로 맞춘다. 기존 favicon의 벡터를 인라인으로 사용하고 공통 CSS를
head 안에 한 번만 둔다. 새로운 이미지나 글꼴, 스타일시트 요청은 없다.
부트 화면과 React 화면의 브랜드 위치를 유지한다. 준비되지 않은 홈이나 개인 자료를
미리 보여 주지는 않는다. 로딩 상태별 기존 번역 문구는 유지한다.

실제 앱 변경은 index.html, App.css, AppLoading.tsx뿐이다. 로그인 검사, useStore,
조회 순서/범위, 권한, 배정, 신청, 초안, DB, 기능 설정은 변경하지 않는다.
최소 표시 시간, 종료 애니메이션 대기, 가짜 진행률, 자동 재시도는 추가하지 않는다.
기존 12초 지연 안내, 수동 앱 다시 불러오기, 실패 안내와 재시도 실패 처리는 유지한다.
동작 줄이기 설정에서는 회전만 멈추고 상태 문구는 남긴다.

## 시험

- 전체 2,592개 / 266파일 통과. lint와 데모용 build 통과.
- AppLoading 7개: 기존 수동 복구/언어/실패 시험에 부트-React 구조/로고 일치,
  즉시 unmount와 타이머 정리, 실패 시 브랜드/복구 유지와 회전 제거를 추가했다.

  변이를 모두 복구한 뒤 7개 재통과. 화면 종료를 기다리는 새 타이머는 없다.

## 화면 검사

`scripts/verifyStartupLoadingDemo.mjs`는 로컬/데모 주소와 데모 DB만 허용한다.
업무 자료 쓰기를 차단한다. 로그인 및 기존 자동 세션 정리는 발생할 수 있다.
390x844, 320x568(앱 150% 확대/동작 줄이기), 1365x900에서 다음을 검사한다.

1. JS 전 부트 화면, 로그인 청크 대기 중 React 화면의 브랜드 위치 일치.
2. 추가 이미지/글꼴 요청 없음, 작은 화면/확대 상태에서 가로 넘침 없음.
3. 실제 12초 후 수동 복구 버튼 표시.
4. 일정 조회에 503 오류를 주입하면 오류 안내와 수동 복구 유지, 회전 표시 종료.
5. 미처리 pageerror 없음.

Chromium 로컬 세 화면 통과. WebKit은 모듈 응답을 멈춰 두면 초기 파싱/화면 확인이
진행되지 않아 첫 도구 실행이 시간 초과됐다. 앱 오류로 판정하지 않았다. WebKit의
부트 검사는 JS 비활성 별도 context로 분리하고 React 상태와 위치를 비교한다.
따라서 WebKit 위치 비교는 같은 context의 연속 전환을 직접 관찰한 검사가 아니다.
수정한 도구로 WebKit 로컬 세 화면도 모두 통과했다. 기록은
`scratch/startup-local-ui.json`, `scratch/startup-local-webkit-fixed-ui.json`에 있다.
실제 아이폰 PWA의 시작 화면/OS 전환은 사용자의 기기 확인이 별도로 필요하다.

## 사용량과 시간

기존 `measureServiceNavigationDemo.mjs`, Chromium 390px, REST 요청별 120ms 지연,
같은 데모 계정/설정, 역할별 전후 각 3회. 모든 요청 종료 후 600ms 안정 구간으로
측정 구간을 나누며 30초 안에 끝나지 않으면 실패한다. 서비스 워커는 차단한다.
원본: `scratch/speed-startup-before.json`, `scratch/speed-startup-after.json`.

|---|---:|---:|---:|
| 봉사자 | 2,275 / 2,330ms | 39 / 39 | 41,273 / 41,273B |
| 인도자 | 1,173 / 1,177ms | 29 / 29 | 45,861 / 45,861B |
| 실제 관리자 | 1,135 / 1,239ms | 29 / 29 | 48,784 / 48,783B |

관리자 후 측정 한 번은 2,041ms였다. 온라인 측정에는 변동이 있으므로 이 결과를
속도 개선이나 정확히 같은 로딩 시간이라고 표현하지 않는다. 코드상 데이터 준비를
지연시키는 대기는 추가하지 않았고, 이번 작업은 로딩 속도 개선이 아닌 표시 변경이다.
관리자 응답의 1B 차이도 사용량 절감으로 주장하지 않는다.

캘린더 첫 진입은 봉사자 17건, 인도자/관리자 6건, 홈 복귀는 모두 3건으로 동일했다.
3역할 x 3반복 x 3구간 총 27개 전후 쌍의 요청 수와 조회 경로 목록이 일치한다.
초기 후 측정 이후에는 좁은 화면 브랜드 줄바꿈 CSS만 보강했다. 데이터/시간 코드는 같다.

데이터 사용량과 정적 파일 용량은 구분한다. 동일한 압축 방식으로 측정한 초기 HTML,
주 JS, 주 CSS의 gzip 합계는 102,469B에서 103,489B로 **1,020B 증가**했다.
HTML +836B, JS +293B, CSS -109B다. 이는 로고/마크업/레이아웃 코드 비용이며
별도 요청은 추가되지 않는다. 네트워크 전체 바이트가 전혀 늘지 않았다고 말하면 안 된다.
Vercel 실제 압축/브라우저 캐시에 따라 전송량은 다르며, 배포 후 처음에는 다른 변경과
마찬가지로 파일 해시가 바뀐 청크를 다시 받을 수 있다.
