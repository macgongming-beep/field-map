# 봉사자 모바일 홈 코드 선로딩

- 날짜: 2026-11-22
- 상태: 로컬 검증 완료 후 데모만 반영. 운영 미적용.
- 변경 전 기준: `4775877` (0153 지도 개선 포함).
- 범위: App의 MobileHome 코드 로딩. 자료 조회, 권한, 저장, 개인 구역 판정, 기능 설정은 변경하지 않는다.

## 결정과 기존 동작 보존

로그인 확인이 끝난 일반 봉사자가 모바일 홈(`/`)을 열 때만, 기존 자료 로딩과 함께
MobileHome 모듈을 가져온다. 비로그인, 로그인 확인 중, PC, 인도자/관리자/개발자,
다른 주소, 봉사자 미리보기에는 선로딩하지 않는다. 기존 자료 준비 관문은 그대로다.
미리 모듈을 가져오는 것만으로 홈이나 홈의 자료 소비 컴포넌트를 마운트하지 않는다.

처음에는 같은 import Promise를 선로딩과 React.lazy가 나눠 쓰도록만 바꿨다.
코드 요청은 앞당겨졌지만 자료 완료 후 약 0.3초 대기가 그대로 남았다. 이 중간안은
배포하지 않았다. 최종안은 이미 가져온 모듈이면 처음 마운트할 때 바로 사용한다.
아직 준비되지 않았으면 기존 lazy/Suspense 경로를 쓰고, 마운트 후에는 선택한
컴포넌트를 바꾸지 않아 내부 화면 상태를 보존한다. 새 지연/타이머를 넣지 않는다.

성공한 코드와 진행 중 import는 공유한다. 코드만 기억하고 계정 자료는 기억하지 않는다.
선로딩 실패는 화면 오류를 새로 만들지 않고 정상 렌더 경로에 맡긴다. 실패 Promise는
helper에서 버리지만, 브라우저/Vite 자체의 실패 모듈 캐시까지 복구한다고 보장하지 않는다.
정상 렌더의 코드 로딩 오류와 기존 앱 복구 장치는 바꾸지 않는다.

## 전후 측정

운영과 같은 기능 설정 46개 + 데모 DB. Chromium 390x844, CPU 4배 감속,
서비스워커 OFF, 유효한 데모 세션으로 새 브라우저 context에서 앱을 다시 여는 조건이다.
앱 파일은 로컬 제공, DB는 실제 통신이며 각 조건에서 전후를 번갈아 3쌍 순차 측정했다.
진행 중 요청이 전부 끝나고 800ms 조용해야 다음 화면으로 넘어간다(30초 초과는 실패).
홈 표시 기준은 `.mh-page` 존재 + `.app-loading` 없음이다. 시간은 중앙값이다.

| 조건 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 홈 첫 표시, 로컬 파일 즉시 제공 | 1,245ms | 975ms |
| 홈 첫 표시, JS/CSS 요청마다 150ms 지연 | 1,388ms | 1,112ms |
| 홈 코드 요청 시작, 즉시 제공 | 940ms | 492ms |
| 홈 코드 응답 완료, 즉시 제공 | 965ms | 517ms |
| DB 요청 수, 두 조건의 모든 실행 | 39 | 39 |
| 앱 파일 요청 수, 모든 Chromium 실행 | 18 | 18 |
| 홈 재진입 시 MobileHome 추가 요청 | 0 | 0 |

즉시 제공 시 홈 시간은 전 1245/1225/1254, 후 975/976/953ms다.
150ms 조건은 전 1428/1335/1388, 후 1201/1112/1059ms다.
WebKit 390px 1쌍은 1212 → 987ms, DB 39 → 39, 앱 파일 19 → 19였다.
WebKit은 화면·왕복 smoke이며 반복 성능 결론으로 쓰지 않는다. 홈/캘린더/홈 정상,
페이지 오류 없음, 화면 캡처 확인. 실제 아이폰/안드로이드 실측은 아니다.

## 사용량과 한계

- 12개 Chromium 실행의 DB 요청 종류/주소/조건 목록이 모두 동일하다.
- DB 응답 원문 합계 46,488~46,490바이트. 차이 1~2바이트는 동기화 시각 RPC의
  응답 길이 변화이며, 조회하는 자료 범위가 늘어난 것이 아니다.
- 앱 응답 원문 2,662,379 → 2,662,673바이트(+294). JS 17개 합계
  2,509,120 → 2,509,414바이트; gzip 합계 708,707 → 708,820바이트(+113).
  요청 수는 늘지 않지만 코드 크기가 완전히 같다고 하지는 않는다.
- 요청/원문 크기는 압축·캐시·서비스워커·청구량과 다르다. 설치 앱에서 이미 캐시된
  경우의 효과나 첫 설치 전체 다운로드 시간은 이번 측정 범위가 아니다.
- 선로딩 시작 뒤 앱을 닫거나 자료 읽기가 실패하면, 예전에는 받지 않았을 홈 코드를
  받을 수 있다. import는 취소하지 않는다. 따라서 모든 중단 경로까지 사용량이
  절대 늘지 않는다고 보장하지 않는다. 정상 홈 진입/재진입의 중복 요청은 없다.
- 홈을 막는 기존 자료 조회 9단계는 이번에 바꾸지 않는다. 모임 글/알림도 변경하지 않는다.
- `VITE_RECIPIENT_DISCOVERY_REUSE_ENABLED`, `VITE_ROUTE_LIGHTWEIGHT_ENABLED`는 계속 OFF다.

## 측정 안전과 제외 실행

데모 DB/앱 주소만 허용하고 표·Storage 쓰기는 막았다. RPC는 관측된 읽기/인증 이름만
허용했으며 자동 세션 정리는 응답 0으로 대체했다(39건에는 이 호출도 포함).
데모 로그인/세션 확인/자동 로그인 기록은 발생한다. 업무 자료 쓰기, 운영 DB 접속,
운영 환경변수/배포 변경은 하지 않는다. 세션 토큰은 메모리에만 보관하고 결과에서 제외한다.
분석용 Vercel 스크립트는 양쪽 모두 빈 응답으로 대체한다.

최초 하네스 실행은 분석 스크립트가 로컬에 없어 404로 중단됐고 결과에서 제외했다.
import만 미리 받은 중간안은 `import-only-chromium.json`에 따로 남기고 최종 수치에
섞지 않는다. 성능 측정과 시험/변이는 동시에 실행하지 않았다.
