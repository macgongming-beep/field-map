# 집단 봉사 운영 전환 전 최종 점검

- 상태: 배포 보류. 데모 기능 검증 통과와 운영 전환 승인은 별개다.
- 점검일: 2026-11-17 (KST)
- 후속: 세 전환 항목 보완·격리/데모 리허설은 [0105](0105-group-service-staged-rollout.md) 참조. 이 문서는 최초 점검 당시 결과를 보존한다.
- 범위: 데모 실행 검증, 저장소 코드, 운영 DB 구조·집계 읽기, 배포 정보 조회.
- 운영 변경: 없음. 운영 로그인·업무 RPC·쓰기·알림·마이그레이션·배포·환경변수 변경을 하지 않았다.
- 이번 수정: 점검 도구·문서와 최신 UI 계약에 맞춘 검사 기대값만. 앱 기능과 SQL은 수정하지 않았다.

## 판정

현재 데모 코드를 운영으로 그대로 옮기면 안 된다. 아래 세 항목을 해결한 별도 전환 후보를 만들고 다시 검증한 뒤 사용자 승인을 받아야 한다. 기존 데모의 기능 실패를 뜻하는 것은 아니다.

### 1. 운영에 없는 전시대 표를 새 신청 경로가 직접 참조한다

- 운영 읽기 확인: `public.event_cart_applications`가 없다. 데모에는 있다.
- `20261116_1100_service_application_activity.sql:57`의 일반 봉사 신청 함수는 이 표를 무조건 조회한다.
- 격리된 PGlite에 실제 마이그레이션을 읽혀 유효 세션·열린 일정을 준비하고 전시대 표 없이 일반 신청을 실행했다. `42P01: relation "public.event_cart_applications" does not exist`를 재현했다. 운영에서는 실행하지 않았다.
- 대신 신청의 `20261117_1200` 경로와 `20261116_1030`의 일정 알림 본문 치환도 같은 의존성을 가진다. 이 두 경로의 실패까지 실행 재현했다고 주장하지 않는다.
- 운영의 설치된 `notify_on_comment`에는 전시대 참조가 없고 데모에는 있다. 데모 본문을 통째로 복사하지 않는다.
- 전시대가 없는 운영에서도 정상 동작하도록 의존성을 분리하고, 표가 있는 경우/없는 경우의 신청·대신 신청·알림을 모두 시험해야 한다. 이번 기능 배포를 위해 전시대 기능까지 임의로 운영에 추가하지 않는다.

### 2. 새 저장 경로가 데모 전용인데 DB 변경은 옛 경로를 즉시 차단한다

- `src/features/groupService/model.ts:12-15`는 데모 모드와 데모 DB 주소를 모두 요구한다. 운영에서는 새 기능·권한·배정 저장 경로가 꺼진다.
- `src/hooks/storeMutations/eventAssignments.ts:123` 및 `calendar.ts:446` 등은 이 값으로 새 버전 저장/옛 저장 경로를 선택한다.
- 반면 `20261117_1010_assignment_revisions.sql:124-128`은 옛 배정·팀원 제외 RPC 네 개의 실행권한을 바로 회수한다. 엄격한 직접 쓰기 차단도 이어진다.
- 따라서 현재 마이그레이션을 그대로 적용하면 운영 클라이언트가 사용하는 저장 경로가 막힐 수 있다. 단순히 환경변수 하나를 켜거나 운영에 데모 모드를 사용하는 것으로 해결하지 않는다.
- 새 경로를 운영 전환 단계와 연결하고, 구버전 앱과 새 앱이 공존하는 동안의 계약을 먼저 준비해야 한다.

### 3. 단계별 전환 구현과 옛 참가자 제외 경로 제거가 아직 남아 있다

- `0098`의 전환 절차는 설계 문서이며, 현재 파일을 그대로 운영에 적용해도 된다는 승인이 아니다.
- `src/hooks/storeMutations/calendar.ts:451-512`에는 자동 세션 → 카드 → 비공식 → 식당 → 참가자를 여러 요청으로 지우는 옛 경로가 남아 있다.
- 엄격 차단과 함께 남겨 두면 앞 요청만 반영되고 다음 요청에서 막히는 부분 변경 위험이 있다. 코드상 확인이며 운영에서 파괴적 재현을 하지 않았다.
- 추가형 DB 변경 → 새 앱 전환 → 실제 사용 버전 확인 → 엄격 차단 순서의 실행 파일, 단계별 감사 목록, 복구 절차가 필요하다. 옛 여러 요청 삭제 경로는 엄격 단계 전에 제거해야 한다.
- 데모의 definer 함수 목록 13개를 운영 승인 목록으로 그대로 쓰지 않는다. 데모 전용 reset 함수와 단계별 공개 RPC가 다르다.

## 사용량과 성능

- 댓글 최초 열기: 선택한 집단 20행, 이번 표본 응답 본문 5,600바이트.
- 댓글 한 건 추가·수정은 해당 행만 읽고, 삭제는 해당 ID만 확인했다. 이 변경으로 캘린더를 다시 읽지 않았다.
- 앱 복귀: 이미 읽은 20/40행 범위만 재조회했다. 백그라운드에서는 댓글 조회가 없었다.
- 소켓 재연결에는 기존 캘린더·자료 복구 조회가 함께 발생한다. 댓글 비용만으로 전체 앱 비용을 설명하지 않는다.
- 위 바이트는 해제된 HTTP 응답 본문 기준이지 실제 청구량이 아니다. Chromium의 복귀·실제 소켓 재연결 시험이며 실물 휴대폰 수명주기 측정은 아니다.
- 데모 RLS 실행 계획: 인도자 배정 10행 4.069ms, 봉사 세션 33행 1.724ms; 일반 성원 배정 9행 1.548ms, 세션 32행 1.399ms. 운영 규모 성능 합격 근거로 쓰지 않는다.

## 남은 승인 조건

1. 위 세 전환 문제를 운영에 쓰지 않고 격리 환경에서 해결하고 회귀 시험한다.
2. 운영에 준하는 자료량의 격리 DB에서 권한 정책·댓글 인덱스 실행 계획과 실제 응답 시간을 측정한다.
3. 구버전/새 버전 앱과 각 DB 전환 단계의 신청·취소·배정·공유·관리 작업을 검증한다. 임시 호환 단계에서는 동시 저장 보호가 완성됐다고 주장하지 않는다.
4. 백업과 복구 리허설, 각 단계의 실제 DB definer 감사 목록을 준비한다.
5. 실제 휴대폰 푸시 수신과 알림을 눌렀을 때의 집단·댓글 진입을 확인한다. 이번에는 알림 요청 큐까지 확인했고 실물 기기에 발송하지 않았다.
6. 결과를 다시 공유하고 별도의 운영 적용 승인을 받는다.

## 재현 도구와 로컬 증거

`scripts/preflightGroupReleaseReadOnly.mjs`는 읽기 전용 모드만 있으며 적용 기능이 없다. 프로젝트 주소·DB 사용자·세션 풀러 포트를 확인한다. `PREFLIGHT_ENV_FILE`로 대상 환경 파일을 지정하고 `demo --read-only` 또는 `production --read-only`를 전달한다. 비밀값을 명령 인자로 넣지 않는다.

로컬 생성 결과는 커밋하지 않는다:

- `scratch/group-release-production-readonly.json`, `group-release-demo-readonly.json`
- `scratch/group-release-missing-cart-repro.json`
- `scratch/assignment-review-smoke.json`, `assignment-maintenance-smoke.json`
- `scratch/assignment-review-audit.json`, `assignment-review-definer-audit.txt`
- `scratch/group-comment-notification-audit.json`
- `scratch/group-tabs-ui-results.json`, `group-comments-results.json`

카탈로그에서 수집한 운영 함수 목록은 관찰 자료이며, 승인된 운영 단계별 허용 목록이나 보안 감사 전체를 대신하지 않는다.
