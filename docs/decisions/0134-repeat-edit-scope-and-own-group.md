# 반복 일정 수정 범위 복구와 내 집단 우선 표시

- 상태: 사용자 데모·운영 적용 승인, 검증 후 순차 전환
- 결정일: 2026-11-19
- 선행: 0132 기존 일정 집단 추가, 0133 집단 목록 운영 전환

## 원인과 수정

옛 일정 편집 화면은 저장 전에 반복 수정 범위를 물었지만, 새 ServiceEventEditor에는
그 선택이 없어 현재 일정과 명시적으로 고른 같은 날의 시간대만 저장했다.

- 반복 ID가 있는 일정은 저장 전에 `이 일정만 수정` / `이후 반복 일정도 수정` / `돌아가기`를 제공한다.
- 반복 ID 없는 단일 일정은 그대로 저장한다. 제목·요일이 같다는 이유로 다른 일정을 묶지 않는다.
- 회중/집단, PC/모바일의 공통 편집기에 적용한다. 옛 편집기의 기존 범위 선택은 유지한다.
- `함께 수정`으로 선택한 다른 시간대는 자기 반복 ID를 따라 확장한다. 시간대와 집단별 series를 합치지 않는다.
- 기준은 수정 전 선택한 날짜다. 그 날짜를 포함한 이후의 기존 반복 일정만 대상으로 하고, 지난 날짜는 제외한다.

## 조회와 저장 보호

명시적으로 이후 수정 버튼을 누를 때만 `read_service_series_edit_targets` 한 번으로
각 반복 전체의 ID/수정 버전/원본 필드/접속 정보를 읽는다. 화면에 받은 월 범위에 의존하지 않는다.
활성·승인 관리자/개발자만 실행할 수 있다. 공개 달력/신호/알림에 비밀번호를 넣지 않는다.
현재 편집본의 root 버전도 서버에서 확인한다. 중복 root/복수 시간대를 잘못 공유하는 series,
집단이 섞인 series는 거부하고 일부만 수정하지 않는다. 최대 200개다.

이후 날짜에는 실제로 바꾼 필드만 적용한다. 제목만 수정하면 날짜별 인도자, 메모, 접속 정보는 유지한다.
인도자를 바꾼 경우 이름과 주 인도자 ID를 함께 변경한다. 날짜는 상대 일수로 이동하고,
앞으로 미룰 때는 뒤 날짜부터 갱신해 다음 회차와의 일시적 충돌을 피한다.
접속 정보는 JSON 키 순서가 아닌 각 값으로 비교한다.

기존 `save_service_events_tx`의 단일 트랜잭션, 관리자 쓰기 권한, 모든 행 버전 검사,
중복 시간대 방지, 요약 알림, 요청 ID 재시도 보호를 그대로 사용한다. 저장 함수는 교체하지 않는다.
조회에 실패해도 현재 일정만 대신 저장하지 않는다. 조회 후 새로 추가된 회차는 이번 읽기 목록에 포함되지 않는다.
불확실한 저장 응답 뒤 재시도는 같은 조회 목록과 요청 ID를 사용한다.

집단 추가를 함께 선택하면 이후 대상 날짜에도 독립 일정을 생성하며 새 집단/시간대마다
새 반복 ID를 쓴다. 이미 점유된 미래 시간대가 있으면 기존 서버의 중복 검사가 전체 저장을 취소한다.
기존 신청자·배정·댓글을 새 집단으로 복사하지 않는다.

## 내 집단 탭

서버가 이미 알려 주는 `ownGroup`을 사용하여 내 집단을 첫 탭/기본 선택으로 둔다.
추가 설정이나 조회는 없다. 명단 권한·신청 조건은 바꾸지 않는다.
소속이 없거나 그 시간에 내 집단 일정이 없으면 기존 순서를 유지한다.
수동으로 바꾼 탭은 인원 갱신 때 유지하고, 다른 계정으로 바뀌면 새 계정의 집단을 다시 선택한다.
댓글 알림의 명시적인 집단 이동은 기본 선택보다 우선한다.

## 검증

- 단일/이후 선택 전 저장 금지, 다음 달 대상 포함, 실패 시 단일 저장 금지, 재시도 요청/버전 유지.
- 개별 인도자/메모/접속정보 보존, JSONB 키 순서, 날짜 이동, 시간대 분리, 새 집단 반복 생성.
- 내 집단 첫 탭/기본 선택, 수동 선택 보존, 알림 이동, 계정 변경, 미소속/없는 집단 신청.
- 실제 데모 anon 역할에서 관리자만 전체 반복 조회, 지난 회차 보존, 다음 달 수정,
  비공개 접속정보 조회, 저장 재시도/오래된 버전 거부를 확인하고 모두 롤백했다.
- 변이: 범위 선택 제거(4개), 내 집단 정렬 제거(1개), 이후 필드 전체 덮어쓰기(1개)를 시험이 잡았다.
  SQL 관리자 역할 검사를 제거해도 권한 시험이 실패했다. 원본 DB/SQL 파일은 변이하지 않았다.
- Chrome 실제 편집기 로컬 화면의 390px 배치와 범위 선택 후 단일 ID 저장 요청을 확인했다.
  이 화면은 DB를 쓰지 않는 격리 화면이며 실제 DB 검증은 위 롤백 시험과 구분한다.

초기 로딩·일반 진입 조회를 추가하지 않는다. 이후 반복 수정에서만 추가 조회 한 번과 대상 행 수만큼 저장량이 든다.
네트워크 바이트 전후 실측이나 실제 아이폰/안드로이드 검사는 이번에 하지 않았다.

## 전환

`scripts/serviceSeriesRelease.mjs demo apply --confirm-demo` 후 `demo verify`를 통과해야
`production apply --confirm-production`이 가능하다. 양쪽 모두 public/private 백업과
롤백 리허설을 먼저 하고, 단일 트랜잭션으로 읽기 RPC만 설치한다.
일정/신청/배정 두 표/모임 접속정보/설정 해시가 같음을 확인한다. 운영에는 시험 일정을 만들지 않는다.
기존 배정 함수 목록과 실행 권한을 실제 DB에서 감사한다. 백업은 목록 읽기 검사이며 복원 시험은 별도다.

운영 DB 준비 뒤 main을 fast-forward하고 운영의 환경변수는 그대로 유지한다.
별도 메타정보 구역 조회 최적화는 이번에도 OFF다. 실패 시 앱만 이전 배포로 돌려도 기존 기능이 동작한다.
새 읽기 RPC는 남겨 두어도 기존 저장에 영향을 주지 않는다.
