# 최신 운영 코드 기반 후보가 먼저 필요하다

- 날짜: 2026-11-17
- 상태: 운영 전환 보류. 후보 이식 범위 조사 완료, 운영 후보 미작성.
- 범위: Git 원격 갱신·로컬 코드 및 SQL 검토. 운영/데모 DB 접속과 배포 없음.
- 선행: [0105 전환 절차](0105-group-service-staged-rollout.md), [0106 데모 실기기·성능](0106-demo-physical-push-and-scale-check.md)

## 확인한 차이

- 조회 시점 `origin/main`: `f8ccae471b22fe3dcff1c694d56592b43e49ef78`.
- 데모 검증 브랜치: `586cbdb8960273c2fb165c604d5ed553858d030a`.
- `git rev-list --left-right --count origin/main...HEAD`: main 전용 82 / 데모 전용 133 커밋.
- `git merge-tree --write-tree --name-only origin/main HEAD`: 충돌 파일 46개, 문서 경로 및 `.md` 제외 26개. 이는 실제 병합·체크아웃 변경이 아닌 병합 계산이다. 리뷰의 100개 이상이라는 파일 수와는 다르지만 핵심 경로 충돌이라는 결론은 같다.
- 충돌 대상에 DesktopCalendar, AdminMobileCalendar, AssignmentEditor, calendarEventRefresh, calendarParticipants, useStore, useNotifications가 포함된다.
- `main`은 운영 지연 로딩·Sentry 등의 변경을 포함하므로 데모 파일로 덮어쓰면 안 된다. 커밋 개수는 서로 다른 변경의 개수와 같지 않으며 동일 변경의 별도 이식 이력도 구분해야 한다.

기존 2,599개 시험·화면 검사·아이폰 결과·합성 규모 측정은 데모 코드와 데모 DB에 대한 근거다. 미래의 운영 후보 코드가 통과한 것으로 옮겨 적지 않는다.

## 이식 범위

집단 봉사 최초 커밋은 `fc7781f`이고 바로 전 기준은 `21a725c2a91141d2d7b773296b0179774fe6e811`이다. 이 기준부터 데모 검증 지점까지 src/scripts/supabase 변경은 115파일이다. 이는 후보 이식 검토 목록이지 전부 복사할 파일 목록이 아니다.

1. 최신 main의 운영 기능·지연 로딩·관측·권한 계약을 기본으로 유지한다.
2. 집단 일정 편집·탭·재방 연구 신청·선택적 모임 정보·기본 펼침 댓글 UI와 해당 시험을 이식한다.
3. 모든 인도자 배정/관리자 일정 편집, 리비전 충돌 검사, 원자적 참가자 제외, 제한된 재조회와 관련 시험을 이식한다.
4. 신규 SQL 18개와 단계별 생성·감사 도구는 선행 설치 계약을 대조한 뒤 후보에 포함한다. 유지보수 감싸개는 운영의 실제 본문을 보존해야 한다.
5. 데모 로그인·reset 함수·시험용 계정/일정·전용 키·백업은 운영 기능에 포함하지 않는다. 기존 데모 확인 도구는 데모 브랜치에서 후보 배포를 대상으로 실행할 수 있으므로 운영 앱에 억지로 섞지 않는다. 검증용 fixture와 운영 실행 기능은 구분한다.
6. 전체 브랜치 병합, 핵심 파일의 일괄 덮어쓰기, 모든 충돌에서 한쪽 선택은 하지 않는다.

## 선행 DB 계약

현재 준비 묶음의 최초 선행 검사는 `private.cleanup_team_participant_removal()` 존재 확인에 한정되어 충분한 설치 감사가 아니다. 아래 항목을 포함한 후보 전용 사전 점검을 먼저 완성해야 한다.

- 후보가 사용하는 기존 함수의 정확한 서명·본문·실행권한: 일정 단일/반복 수정, 카드/팀 저장, 참가자 정리, 신원 확인, 세션 확인, 이름 변경·사용자 정리·건물 병합.
- `notify_on_comment`, 수신자 필터·푸시 발송 함수의 설치 본문과 권한. 후보 준비 적용 전후 차이를 대조하고 데모 본문으로 대체하지 않는다.
- 후보 조회가 사용하는 알림·사용자 디렉터리·봉사 기록 함수와 필요한 표·칼럼·인덱스·정책·실시간 구독 상태.
- 예: `20261110_1600_notification_feed_without_comments.sql`은 데모 브랜치에는 있으나 main에는 없다. **파일 부재는 운영 DB 미설치를 입증하지 않는다.** 후보가 그 기능을 요구하는지 먼저 확인하고 필요할 때 별도 의존성으로 다룬다. 무조건 준비 묶음에 추가하지 않는다.
- 수동 설치 이력이 있으므로 마이그레이션 파일명 목록만 비교하지 말고 실제 카탈로그와 함수 정의를 읽기 전용으로 대조한다. 이번 조사에서는 운영 DB를 다시 읽지 않았다.

## 다음 순서와 합격 조건

1. 최신 main SHA를 고정하고 별도 후보 브랜치에서 필요한 변경을 이식한다. main에는 아직 병합하지 않는다. 후보 작성 자체도 이번 조사에서는 수행하지 않았다.
2. 후보의 전체 시험·lint·build를 실행하고 후보 SHA, SQL 묶음 해시, 환경 설정을 함께 기록한다.
3. 동일 후보를 데모에 배포해 PC·모바일·회중/집단 신청·배정·동시 저장·관리 기능·댓글/알림·실기기 진입을 재검증한다. 운영 환경 조합에서도 검사하며, 데모 자동 활성화에만 기대지 않는다.
4. 선행 DB 대조·백업·복구 근거 및 후보 기준 결과를 리뷰받는다. 필요하면 권한 정책 전/후 비용도 동일 표본으로 비교한다.
5. 별도 운영 승인 후에만 0105의 준비 DB → 첫 배포 관문 → main 반영/새 앱 → 기기 업데이트 확인 → 엄격 단계로 진행한다.

후보를 만들기 위해 준비 DB를 먼저 운영에 넣거나, 충돌 해결을 위해 운영 main을 먼저 바꾸지 않는다. 후보 검증 단계와 실제 운영 전환 단계를 분리한다.
