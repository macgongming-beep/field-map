# 봉사자 첫 로딩의 독립 조회 병렬화

- 결정일: 2026-11-18
- 상태: 데모 검증. 운영 변경 없음.
- 기준 앱: `605fa23` (문서 포함 기준 HEAD `5fb09cf`).

## 범위

봉사자 앱 재실행에서 첫 전체 로딩을 완료하기 전, window 일정 범위인 경우만 바꾼다.
홈 window는 개인 전체 배정의 근거로 재사용할 수 없으므로, 개인 구역의 독립 조회가
홈 일정 응답을 기다릴 필요가 없다. 두 작업과 설정/특별기간/정기방문 등 독립 slice를
함께 시작한다. 카드와 방문 기록(`visits`, `visitHistories`)은 새 건물이 준비된 뒤 읽는다.
봉사 세션은 기존 visits 묶음과 오류 처리 계약을 그대로 유지했다.

`VITE_RECIPIENT_INITIAL_PARALLEL_ENABLED=true`일 때만 켠다. 기본값은 false이며
DEMO_MODE를 따라 켜지지 않는다. 이번 데모 빌드에만 명시적으로 true를 넣었다.

## 보존하는 계약

- 조회 대상/조건/페이지 처리/개인 구역 계산/권한/DB/저장 경로는 변경하지 않는다.
- 완전한 full/service 일정은 기존처럼 완료 후 재사용한다. 이번 분기를 타지 않는다.
- 최초 성공 이후 화면 전환, 재연결, 쓰기 후 갱신은 기존 경로를 유지한다.
- recipientReader의 진행 중 read 공유를 사용한다. 건물/경계가 같은 범위를 별도로 다시 읽지 않는다.
- 첫 로딩은 모든 필수 작업이 성공해야 완료된다. 실패를 빈 자료나 성공으로 취급하지 않는다.
- 실패한 첫 작업의 다른 읽기도 모두 끝나야 다음 재시도가 진행된다. 이전 작업의 늦은 응답이
  새 작업을 덮지 않게 한다. 기존 취소/재시도 대기열과 45초 제한을 유지한다.
- 방문 기록은 새 세대 목록으로 읽고, 카드도 새 건물/허용 카드 범위를 사용한다.
- 변경 시각 확인 두 번, 카드 요약 직렬 조회, 로그인 순서, 일정/배정 쿼리는 이번에 손대지 않는다.

## 전후 비교

데모 DB, Chromium 390x844, 요청 시작마다 120ms 추가 지연, 실제 봉사자 계정.
저장된 로그인으로 페이지를 다시 열고 홈이 표시되는 첫 프레임을 측정했다.
실제 iPhone의 PWA 복귀/푸시 검사는 아니며, 운영 속도를 보장하는 숫자가 아니다.
요청 종료와 응답 본문 수신 뒤 600ms 안정 구간으로 측정 경계를 나누고,
30초 내 안정되지 않으면 실패한다. 실패 응답/페이지 오류/넘침을 검사한다.

첫 전후 각 3회(`scratch/speed-cold-{before,after}.json`)에서 봉사자 중앙값은
2,758 -> 2,471ms였다. 통신 편차를 줄이기 위해 전/후를 번갈아 3쌍 더 실행했다.
최종 비교 기록은 `scratch/speed-cold-pair-{1,2,3}-{before,after}.json`이다.

| 항목 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 봉사자 첫 홈 표시, 3쌍 중앙값 | 2,878ms | 2,408ms |
| 해당 전환의 전체 자료 응답 완료, 중앙값 | 3,039ms | 2,581ms |
| 첫 진입 요청 | 39건 | 39건 |
| 첫 진입 자료 응답 원문, 중앙값 | 41,273B | 41,273B |
| 이어서 캘린더 이동 | 17건 | 17건 |
| 홈 돌아오기 | 3건 | 3건 |

각 쌍의 첫 화면은 2,965->2,299 / 2,762->2,408 / 2,878->2,463ms였다.
모든 쌍에서 요청 수와 쿼리 목록은 같았다. 쿼리 비교 시 변경 확인의 실행별
`changed_at` 기준 시각만 정규화했다. 홈 표시 내용도 동일했다.
응답량의 1~2B 변동은 동적 응답 길이 범위이며 신규 자료 조회는 없다.
이 수치는 REST 응답 원문이지 압축 전송량/JS 다운로드/전체 서비스 과금의 측정은 아니다.
동시 요청 수는 늘 수 있다. 서버 부하가 같은 비율로 줄거나 모든 실패 경로의 비용이
같다고 주장하지 않는다. 실패 시 이미 시작한 요청은 마저 끝내며 새 자동 재시도는 추가하지 않았다.

인도자/실제 관리자도 각 3회 확인했다. 첫 진입은 각각 29->29건,
응답 원문은 45,861->45,861B / 48,784->48,784B였다. 코드 변경 대상이 아니므로
이 역할의 시간 차이는 개선으로 해석하지 않는다. 세 역할의 홈 표시 내용은 전후 동일했다.

## 검증

- 전체 2,574개 시험 / 263파일 통과. lint와 데모 빌드 확인.
- 느린 일정과 느린 건물을 각각 보류해 독립 조회 시작, 카드/방문 기록 대기,
  새 세대의 방문 기록 유지, 중복 읽기 없음, 전체 성공 전 로딩 유지 확인.
- 일정 실패 뒤 남은 조회 종료 대기와 재시도 성공 확인.
- 건물/범위 실패 시 카드/방문 기록을 공개하지 않고 오류 유지 확인.
- 설정 OFF/미지정, full/service 범위는 기존 순서 유지 확인.
- 변이: 병렬 분기를 강제로 끄면 독립 조회 시험 실패.
- 변이: visits의 건물 대기를 제거하면 새 세대의 방문 기록 시험 실패.
  두 변이는 모두 복구했다.
- Chromium PC/모바일 × 봉사자/인도자/실제 관리자 6조합 통과.
  `scratch/myservice-cold-after-ui.json` 결과는 기존 `myservice-before-ui.json`과
  표시 내용/검사 항목이 동일했다. 지도 왕복, 식당 목록, 홈 왕복과 관리자 구역 화면 확인.
  데모에 과거 배정이 없는 계정의 과거 달 화면은 생략했으며 자동 조회 시험으로 보존을 확인한다.
- 브라우저 검사는 데모 로그인/자동 세션 정리 외에 신청/배정/방문 기록을 쓰지 않았다.
