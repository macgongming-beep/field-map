# 자동 복구의 전체 건물 다운로드 절감

- 상태: 데모 검증 중
- 결정일: 2026-09-30
- 관련 기능: useStore foreground / place deletion / unit creation recovery
- DB 변경: 없음 (운영에 있는 0008/0009 신호 표와 clock 사용)

## 배경

0009는 지도 자체의 과거 신호 복구를 제한했지만, 2분 이상 지난 뒤 앱으로
돌아오거나 삭제/생성 채널이 재연결될 때 전체 건물+세대를 다시 받았다.
동시에 겹치는 요청만 공유하므로 순차 재연결에는 같은 본문을 반복 다운로드했다.

## 결정

첫 로드와 수동 새로고침, 저장 뒤 mutation 조회는 유지한다. 기능 플래그가 켜져
있고 성공한 초기 서버 기준점이 있을 때, 자동 복구의 buildings slice만 바꾼다.

1. 서버 시각을 얻고, 마지막 성공 복구/전체 기준점 이후 신호를 30초 겹쳐 조회한다.
2. 전체 건물은 `id` 열만 페이지 끝까지 조회한다. 신호에 없는 새 건물과 삭제도
   현재 store의 시작 시점 ID 목록과 대조한다. 화면의 카드 필터에 한정하지 않는다.
3. 변경/신규/삭제 대상만 20개씩 기존 targeted sync로 갱신한다. 반환이 없는 건물은
   해당 건물과 그 세대의 방문 이력을 메모리에서 제거한다. DB 삭제는 하지 않는다.
4. 모든 묶음이 성공한 뒤에만 별도 buildingsThrough를 전진시킨다. 지도와 공유하는
   revision 캐시로 같은 겹침 구간을 재다운로드하지 않는다.
5. 실패하면 기존 전체 buildings 조회로 복구한다. 실패한 증분 cursor는 유지한다.
   기준점이 없거나 플래그가 꺼져도 기존 전체 조회로 작동한다.

수동 전체 조회가 진행 중인 delta를 전체 스냅샷으로 오인해 합치지 않도록 구분한다.
증분 건물만 읽고 전체 영역 baseline을 전진시키지 않는다. 수동 전체 조회의
초기 시각/성공 판정과 앱 오류 화면 방어는 기존 계약을 유지한다.

## 범위와 한계

- visits(방문 이력+봉사 세션), 배정, 공지, 정기방문 등 다른 slice는 이번에 줄이지
  않는다. 봉사 시간 통계, 오래된 기록의 기간 이탈, 정기방문 삭제를 놓치지 않도록
  별도 계약 검토 뒤 단계적으로 바꾼다. 전체 전송량 문제가 해결됐다고 하지 않는다.
- 순차 재연결은 작은 ID/신호 조회가 남지만, 변경 없는 건물 본문은 재조회하지 않는다.
- 전체 ID 조회는 O(건물 수)이고 페이지마다 요청한다. HTTP 요청 수 0은 아니다.
- 이미 읽은 시각 뒤의 변경을 무조건 일정 시간 무시하는 TTL 방식은 쓰지 않는다.
- 0009와 동일하게 30초 이상인 장기 트랜잭션/관리자 일괄 이관은 수동 전체 갱신이
  필요할 수 있다. 신호를 내지 않는 임의 SQL 갱신까지 완전한 CDC로 보장하지 않는다.
- 페이지 대조 중에 새로 들어온 live 건물을 잘못 지우지 않게 시작 시점의 ID만
  삭제 후보로 본다. 실제 제거 전 targeted read로 존재 여부를 다시 확인한다.
- Supabase 청구 egress는 압축/프로토콜/다른 서비스 트래픽도 포함한다. smoke의
  응답 본문 byte를 월간 절감률로 그대로 해석하지 않는다.

## 검증

단위 시험: 변경 없음, 시차 재연결, 신규/삭제/변경, 버전 중복 제거, 20개 묶음,
부분 실패 cursor 보존, 오류 시 전체 복구, 수동 갱신 분리, foreground 배선.
쿼리 시험: ID만 select, 서버 시간 조건, 화면 카드 범위로 제한하지 않음.
변형 시험: 삭제 대조 제거 시 해당 시험 1개 실패, delta 경로 제거 시 foreground
회귀 시험 실패. 복원 후 통과.

데모 smoke는 기존 두 브라우저 상태/추가/취소/범위 검증에 더해, 긴 foreground에서
전체 건물 본문 요청이 없는지 검사하고 오프라인 중 건물 삭제/호수 생성/상태 변경을
복구한다. 모든 쓰기는 합성 데모 자료에 한정하고 끝나면 정리한다.

2026-09-30 검증: 1,083개 / 150파일, lint/build 통과. 첫 배포 smoke에서
긴 foreground의 건물 조회는 ID 목록 1회 / 응답 본문 515바이트, 전체 본문 0회.
오프라인 삭제+세대 변경 복귀는 ID 목록 501바이트와 대상 건물 묶음 305바이트
(세대/방문 이력과 다른 slice는 별도). 실시간 부재 반영 950ms. 짧은 변경 없는
복귀 3회는 건물 조회 0회. 월간 청구 전송량을 측정한 값은 아니다.

  본문 0회, 오프라인 삭제/호수/상태 복구와 clock 실패 방어 통과. fixture 정리 완료.
