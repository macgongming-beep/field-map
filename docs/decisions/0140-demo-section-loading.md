## 범위와 이유

홈, 캘린더, 구역, 배정, 설정의 첫 진입과 재진입을 구분한다. 화면을 먼저
보여 주기 위해 불완전한 구역이나 배정 정보를 공개하지 않는다. 불필요한
조회와 직렬 대기, 공통 화면의 재생성을 줄인다.

1. 봉사자 개인 배정 확인에서 같은 배정 ID에 의존하는 연결 카드와 일정을
   함께 읽는다. 필터, 열, 페이지 크기, 전체 날짜 범위는 유지한다. 실패하면
   이미 시작한 두 요청이 끝난 뒤 거절해 재시도와 겹치지 않게 한다.
2. 첫 bounded 스냅샷에서는 자료를 읽기 전에 확보한 변경 기준 시각을
   개인 구역 상세 조회에도 전달한다. 중복 시각 조회 한 번을 없앤다.
   이후 수동 새로고침, 쓰기 후 갱신, 재연결은 새 기준을 확인한다.
3. 관리자 사용자 관리 등 명시한 관리 화면에서는 건물 본문과 전체 일정
   이력을 요구하지 않는다. 관리자 배정 메뉴는 PC에서 홈 요약을, 모바일에서
   용도 집계에 필요한 zone 필드를 사용한다. 상세 편집기와 지도는 기존
   완전성 확인을 유지한다. 알 수 없는 경로와 쿼리는 보수적으로 전체 조회한다.
4. 세션 확인과 사용자 명단의 소유자는 앱 루트 한 곳으로 둔다. 구역·사용자
   관리·가입 승인·푸시 설정이 별도 로그인 확인을 시작하지 않는다.
   명단은 같은 사용자·역할·토큰의 진행 중 조회와 최근 성공만 재사용한다.
   명단을 쓰는 화면은 60초가 지난 뒤 들어오면 새로 확인하고, 실패한 조회는
   성공으로 기억하지 않는다. 직접 새로고침과 사용자 변경 작업은 기간을
   무시하고 새로 읽는다. 기기 간 즉시 동기화 기능을 새로 추가한 것은 아니다.
5. 첫 실행 이후 추가 자료 대기에서는 모바일 하단 메뉴와 PC 메뉴, 공통
   세션 제공자를 유지한다. 해당 화면 본문만 대기·오류 안내로 막는다.
   준비 전 편집을 허용하거나 이전 계정의 자료를 보여 주지 않는다.

## 설정과 보존 계약

- `VITE_RECIPIENT_DISCOVERY_REUSE_ENABLED=true`: 개인 배정 조회 순서와 초기 시각 재사용.
- `VITE_ROUTE_LIGHTWEIGHT_ENABLED=true`: 명시한 관리 화면의 조회 범위 축소.
- 두 설정은 명시적 opt-in이며 DEMO_MODE를 따라 켜지지 않는다. 준비된 데모
  빌드만 켠다. 최초 병렬 조회는 기존 `VITE_RECIPIENT_INITIAL_PARALLEL_ENABLED`도 필요하다.
- 사용자별 권한, 배정 저장, 팀 구성, 충돌 리비전, 신청·취소, 댓글·알림 저장,
  SQL과 RLS는 바꾸지 않는다. 지도 줌과 GPS도 이번 변경 대상이 아니다.
- 배정 편집기 진입 시 최신 신청자·수정 기록을 읽는 요청은 유지한다.
- 전체 로딩 실패, 늦은 응답, 계정 변경은 기존 실패·폐기 원칙을 유지한다.
- 일반 명단과 관리 명단의 열 분리는 기존 역할별 읽기 정책을 그대로 사용한다.

## 측정 원칙

변경 전후를 같은 데모 DB, 같은 기능 설정, 같은 로컬 정적 서버와 브라우저로
비교한다. 모바일 봉사자·인도자·관리자와 PC 관리자를 구분한다. 요청 시작마다
120ms 지연을 추가하고, 마지막 응답 완료 뒤 600ms 안정 구간을 확인한다.
30초 안에 안정되지 않으면 그 구간은 실패 처리한다.

화면 사용 가능 시점과 뒤의 전체 응답 완료 시점은 별도로 기록한다. 자료 크기는
REST 응답 원문이며 압축 전송량, JS·지도 다운로드, 서비스 과금 총량이 아니다.
실제 아이폰 PWA나 운영 동시 접속 속도를 보장하는 수치로 사용하지 않는다.
실패 경로에서는 먼저 시작한 형제 조회가 끝날 수 있으므로 모든 실패 상황에서
요청 수가 동일하다고 주장하지 않는다.
동시에 진행하는 요청 수는 늘 수 있다. 운영 규모의 동시 접속 부하 시험은
이번 순차 화면 측정에 포함하지 않는다.

정적 JS도 비교했다. 청크 수는 전후 모두 17개이며 전체 청크 gzip 합계는
703,135 -> 704,483B(+1,348B)다. 이는 모든 청크를 각각 압축한 합계로 실제
첫 진입 다운로드량과 같지 않다. 따라서 앱 전체의 모든 바이트가 줄었다고
표현하지 않고, 화면별 REST 요청·응답 절감과 구분한다.

첫 세 행 이외의 시간은 전체 화면 순회 1쌍의 관측값이며 통신 편차를 포함한다.
원래 즉시 열리는 화면은 뒤의 조회만 줄어든다. 팀 배정 편집기에서 없어지면
안 되는 최신 상태 확인은 그대로다. 모든 화면이 빨라졌다고 해석하지 않는다.

봉사자 첫 홈은 각 쌍이 2,398->1,956 / 2,429->1,901 / 2,327->1,963ms였다.
응답 원문 중앙값은 47,002 -> 46,968B로, 요청 하나를 줄이되 주된 효과는 직렬
대기 감소다. 캘린더 전체 응답 완료 중앙값은 2,286 -> 2,148ms였지만 화면 표시
속도는 개선됐다고 주장하지 않는다. 최초 1.1초 목표에 도달한 것도 아니다.

기록한 63개 구간의 합계는 400 -> 331요청, 923,168 -> 651,549B다.
여러 역할과 반복 진입을 합친 시험 집계이며 한 사용자의 하루 사용량이나
실제 과금 절감률이 아니다. 측정 사이의 준비용 재실행·로그인도 이 합계에서 제외된다.
로그인과 앱의 기존 자동 세션 정리 이외에 신청·배정·방문·설정 저장은 하지 않았다.

추가 브라우저 검사에서는 구역 자료 네 요청을 보류한 채 하단 메뉴로 홈에
돌아갔다가 구역을 다시 열었다. 대기 중 본문은 비워지고 메뉴는 유지됐으며,
요청을 풀자 정상 목록이 복구됐다. 오류나 처리되지 않은 취소는 없었다.
첫 확인의 선택자가 실제 DOM과 맞지 않아 실패한 기록은 별도 보존했고,
실제 지역 행 선택자로 수정한 최종 확인이 통과했다.

별도 복사본의 변이 시험으로 다음 보호를 확인했다.

- 개인 배정의 명단 조건, 페이지 처리, 형제 조회 완료 대기, 시각 재사용과

- 명단의 계정별 분리, 중복 로그인 훅 방지, 성공 시점부터의 60초 갱신 및 실패 재시도.
- 준비 전 본문 차단을 없애거나 공통 화면을 다시 제거하면 새 시험이 실패한다.
  실제 MobileHome의 대기 관문을 제거해도 메뉴 이동 시험이 실패한다.
  세 변이 모두 실패를 확인하고 복구한 복사본은 40개 시험을 통과했다.

분리한 코드 검토에서도 대기 관문과 공유 명단에 새 결함을 찾지 못했다.
이는 클로드의 독립 리뷰나 실제 휴대폰 검사를 대신하지 않는다.

1. 개인 구역 범위가 전후 동일하고, 전달한 시각이 상세 조회보다 앞서는지.
2. 새로고침·권한 변경·취소 뒤 예전 시각이나 개인 배정이 재사용되지 않는지.
3. 가벼운 경로에서도 용도 집계, 지도·상세의 필수 자료가 보존되는지.
4. 공유 로그인 정보가 계정·역할·토큰 사이에 섞이지 않고, 명단 실패와 만료를
   정상적인 빈 목록으로 장기 보관하지 않는지.
5. 화면 대기 중 메뉴는 유지하면서 불완전한 본문은 차단하는지. 배정 초안과
   기존 재시도·오류 안내에 회귀가 없는지.
6. 측정 경계에 앞 화면의 요청이 섞이지 않았고, 사용량 증가나 지연을
   단순히 다음 화면으로 옮긴 것을 개선으로 표시하지 않았는지.

운영 반영은 데모 측정과 리뷰, 사용자 확인 후 별도로 결정한다.

  재배포나 속도 재측정은 하지 않았다. 위 측정값은 기존 앱 변경의 결과다.

## 명단 갱신과 개발자 조회 범위

- 사용자 관리·가입 승인 화면은 같은 계정의 명단 조회 성공 후 60초 안에 다시
  들어오면 기존 명단을 재사용한다. 60초가 지난 뒤 재진입하면 다시 조회한다.
  60초마다 자동 조회하는 타이머는 없으므로, 열린 화면에서 새 가입이 최대
  60초 이내에 자동 표시된다는 뜻은 아니다.
- 리뷰의 "당겨서 새로고침하면 명단도 갱신된다"는 설명은 정정한다.
  `App.tsx`의 당겨서 새로고침은 `refetchAll`로 봉사 자료를 갱신하며,
  로그인 정보의 사용자 명단을 갱신하지 않는다. 가입 승인 화면의 명시적인
  "새로고침" 버튼은 `fetchAllUsers`로 명단을 즉시 다시 읽는다.
  사용자 관리 화면에는 별도 명단 새로고침 버튼이 없다. 이 동작은 이번에
  바꾸지 않았으며 명단 변경 작업 후의 강제 갱신도 그대로 유지한다.
- 캘린더의 가벼운 조회는 관리자·개발자에 적용되지만, 건물의 가벼운 조회는
  기존 `buildingDemandEnabled` 대상인 관리자·인도자 범위에서만 적용한다.
  개발자의 전체 건물 조회는 기존 동작을 안전하게 유지하려고 의도적으로
  남겼다. 개발자에게 건물 조회 절감 효과가 있다고 보장하지 않으며,
  그 범위 확대는 별도 화면 의존성 검증 후 결정한다.
