# 봉사자 홈 첫 실행: 사용자 조회와 카드 요약을 앞당김

- 날짜: 2026-11-23
- 작성: Claude. 브랜치 `claude/perf-review-nov23`.
- 상태: 데모 반영 대상. 운영 미적용.
- 기준: `f0ef3fd` (0160까지).
- 범위: `useAuth`의 세션 복원과 `useStore`의 범위 지정 카드 읽기. SQL, 권한, 설정 변경 없음.

## 원인

최신 데모 빌드에서 봉사자 앱 재실행 시, 홈 표시를 막는 직렬 순서는 다음과 같았다(카드 요약이 홈을 막고 모임 글·알림은 막지 않음은 앞선 지연 대조 실험으로 확인했다).

1. 세션 확인
2. 내 정보(`app_users`)
3. 동기화 시각
4. 개인 범위 색인
5. 일정·팀 배정
6. 건물·세대·경계선
7. 카드
8. 카드 요약
9. 홈 표시

- 2단계는 1단계 결과가 필요 없다. 결과를 1단계 뒤에 쓰기만 하면 된다.
- 8단계 카드 요약은 봉사자의 경우 확인된 개인 범위 카드 ID로 요청하는데, 이 ID는 7단계 카드 응답 전에 이미 정해져 있다.

## 결정

### 1. 사용자 조회를 세션 확인과 함께 보낸다 (`dadf2d3`)

- `app_users` 조회를 `verify_session`과 동시에 보낸다. 결과는 세션 확인이 통과한 뒤에만 쓴다.
- 토큰이 무효(`P0001`)면 조회 결과를 버리고 로그인 화면으로 간다.
  - '토큰부터 확인'이라는 기존 규칙의 목적은 결과 적용 순서와 실패 처리였다. 이 목적은 그대로 지킨다.
- 사용자 행은 원래 공개 읽기라서, 먼저 보내도 새로 드러나는 정보는 없다.
- 조회가 실패하면 기존처럼 저장된 정보로 복원한다.
- 기존 시험 '세션 확인이 사용자 조회보다 먼저'는 실제로 실패할 수 없는 시험이었다.
  - 단언문이 조회 함수 안에서 던져졌고, 오프라인 대체 경로가 그 예외를 삼켰다.
  - 이 시험을 새 계약을 검사하는 시험 3개로 교체했다.

### 2. 범위 지정 봉사자의 카드 요약을 카드 읽기와 함께 시작한다

- 확인된 개인 범위(`recipientReader.cardIds()`)가 있을 때만, 카드 읽기와 같은 시점에 그 ID로 `get_card_summaries`를 요청한다.
  - 인도자·관리자의 요약 경로(카드 응답의 ID 사용)는 바뀌지 않는다.
- 카드 응답 검증(범위 밖 행 거부, 허용 카드 누락 거부)은 그대로 거친 뒤에만 요약을 적용한다.
  - 요약 개수 불일치 거부도 그대로 둔다.
- 카드 읽기가 실패하면 요약 요청이 끝난 뒤에 실패를 던진다. 요약이 실패하면 카드를 적용하지 않는다.

## 사용량

- 정상 경로의 요청 수와 응답은 같다(봉사자 재실행 37건).
- 카드 읽기가 실패하는 경로에서는 이전에 시작하지 않던 요약 요청 1건이 끝까지 진행된다. 결과는 쓰지 않는다.
- 토큰이 무효인 재실행에서는 이전에 보내지 않던 사용자 조회 1건이 나간다. 결과는 버린다.

## 시험

- `useAuth.loginGuard.test.tsx` (기존 순서 시험 교체)
  - 세션 확인을 붙잡아 둔 동안 사용자 조회가 이미 나갔는지 확인한다. 사용자 상태는 확인 뒤에만 설정된다.
  - 만료 토큰이면 성공한 조회를 버리고 로그인 화면으로 간다.
  - 조회가 실패하면 저장된 사용자로 복원한다.
- `useStore.recipient.test.tsx`
  - 카드 응답을 붙잡아 둔 동안 요약이 확인된 범위 ID로 이미 요청됐는지 확인한다.
  - 요약 실패 시 오류가 나고 카드를 적용하지 않는다.
  - 카드 실패 시 요약이 끝난 뒤에만 실패한다.
  - 기존 '범위 밖 카드 거부' 시험은 '요약은 확인된 범위로만 요청되고 적용되지 않음'으로 조정했다.
- 변이
  - 직렬 복원 / 확인 전 적용 / 무효 토큰 무시 → 각각 실패
  - 조기 요약 제거 / 범위 없는 조기 요약 / 실패 대기 제거 → 각각 실패
  - 요약 오류 무시 → 다음 줄에서 오류가 나 결과가 같은 등가 변이
- 전체 295파일 3,000개 시험, TypeScript, lint 통과.

## 전후 측정

조건:
- 빌드: 같은 데모 프로필로 단계별로 빌드했다.
- 브라우저: Chromium 390×844, CPU 4배. 서비스워커 끔, 앱 파일 로컬 제공, 데모 DB.
- 측정 구간: 앱 재실행(세션 유지) 후 홈 표시 시점(`.mh-page` 등장·로딩 해제).
- 반복: 교차 3쌍.

| 단계 | 역할 | 지연 없음 (중앙값) | 요청마다 120ms | 요청 |
|---|---|---|---|---|
| ① 사용자 조회 동시 (`f0ef3fd` → `dadf2d3`) | 봉사자 | 590 → 547ms | 1,126 → 990ms | 37 → 37 |
| | 인도자 | 647 → 578ms | 885 → 787ms | 24 → 24 |
| | 관리자 | 632 → 581ms | 904 → 777ms | 24 → 24 |
| ② 카드 요약 조기 시작 (`dadf2d3` → 이 변경) | 봉사자 | 525 → 428ms | 993 → 869ms | 37 → 37 |

- 봉사자 두 단계를 합치면 약 590 → 428ms, 1,126 → 869ms다.
  - ①의 '후'(547/990)와 ②의 '전'(525/993)은 같은 빌드다. 실행 사이의 편차가 있다.
- 봉사자 화면 5개(홈·나의 봉사·캘린더·설정·재진입)의 표시 글자와 화면별 요청 수가 전후 동일했다.
- 실물 아이폰, 운영 규모, 동시 접속, 과금량은 측정하지 않았다.

## 남은 단계 (이번에 바꾸지 않음)

- **동기화 시각 → 개인 범위 색인**: 기준 시각을 읽기 전에 잡아야 변경을 놓치지 않는 설계라 유지한다.
- **건물 상세 → 카드**: 개인 범위가 건물 상세까지 받은 뒤에 '허용됨'이 되는 구조다. 권한 판단 순서와 얽혀 있어 별도 검토 대상이다.
