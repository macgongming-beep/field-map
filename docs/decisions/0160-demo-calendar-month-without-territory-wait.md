- 날짜: 2026-11-23
- 번호: 처음 0159로 작성했으나, 원본 브랜치의 0159(운영 반영 기록)와 겹쳐 0160으로 옮겼다.
- 작성: Claude. 브랜치 `claude/perf-review-nov23`.
- 상태: 데모 반영 대상. 운영 미적용.
- 기준: `3b60b37` (0158 보완까지 포함).
- 범위: 모바일 `/calendar` 화면의 관문 위치. 조회, SQL, 권한, 설정, 저장 경로 변경 없음. PC 캘린더 변경 없음.

## 원인

0156에서 인도자·관리자 홈이 구역 자료(카드, 건물 이름과 세대, 방문 기록, 카드 요약)를 뒤로 미뤘다. 그 결과 캘린더 첫 진입이 이 자료를 받는다.

지연 대조 실험(일부 응답에 1.5초 지연, 데모, 인도자)으로 무엇이 첫 표시를 막는지 확인했다.

|---|---|---|
| 일정 | +1.5초 | +1.5초 |
| 일정 배정 | +1.5초 | +1.5초 |

- 인도자 캘린더는 앱 전체 경로 관문(`RouteReadGate`) 때문에 구역 자료를 모두 기다렸다.
- 그런데 모바일 캘린더에서 카드·건물·방문 기록을 쓰는 곳은 세 곳뿐이다.
  - 일정 상세 시트 `AdminEventDetailSheet`
  - 집단 일정 상세 `GroupServiceDetail`
  - 팀 배정 편집기 `AssignmentEditor`
- 달력과 일정 목록은 일정만으로 그려진다.

## 결정

- 모바일 `/calendar`는 경로 관문에서 구역 자료 대기를 빼고, 일정 준비만 기다린다(`routeSkipsTerritory`).
  - 구역 자료는 기존처럼 진입과 동시에 받는다. 시작 시점과 요청은 같다.
- 위 세 소비자는 새 `TerritoryReadGate`로 감싼다.
  - 구역 자료가 준비되기 전에는 대기 시트를 보여 준다. 실패하면 다시 시도할 수 있고, 닫을 수도 있다.
  - 부분 자료로 상세나 편집기를 그리지 않는다.
- 다음은 바꾸지 않았다.
  - 다른 경로(`/`, `/zone`, `/map`, `/territory` 등)와 PC 캘린더
  - 앱 첫 시작 관문(`startup && needsBuildings`)

## 시험

- App
  - 모바일 캘린더는 구역 자료 대기·실패 중에도 달력을 보여 준다. 구역 소비자만 막히고, 다시 시도와 준비 후 표시가 동작한다.
  - `/`·`/zone`·`/map`은 여전히 경로 전체를 막는다.
  - 관문 규칙은 모바일 `/calendar`에만 적용된다.
- AdminMobileCalendar
  - 일반 상세, 집단 일정 상세, 팀 배정 편집기가 대기 중 렌더되지 않는다. 오류 시 다시 시도할 수 있고, 준비 후 열린다.
  - 달력 자체는 대기 중에도 그려진다.
- 변이 7개를 모두 검출했다.
  - 일반 상세·집단 상세·편집기 관문 제거
  - 규칙을 항상 거짓으로 / 데스크톱 포함으로 / 모든 경로로
  - 구역 준비를 항상 참으로
- 전체 294파일 2,986개 시험, TypeScript, lint 통과.
