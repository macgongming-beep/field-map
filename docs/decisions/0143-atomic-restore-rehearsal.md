# 원자적 복원과 백업 누락 범위 보완

- 날짜: 2026-11-20
- 상태: 로컬 구현 및 격리 검증. **운영 접속·데모/운영 DB 변경·배포 없음**.
- 선행: [0142 기존 복원 경로의 실패](0142-offline-production-backup-rehearsal.md)
- 사용자 요청: 복원 도구·백업 범위를 보완하고 중간 실패·재시도를 다시 확인한다.

## 결정과 변경 범위

앱의 화면·권한 RPC·DB 마이그레이션은 바꾸지 않았다. 백업/복원 도구, 시험과 문서만 바꿨다.

1. `event_meeting_access`, `place_change_requests`, `territory_report_shares`를 백업/복원 대상에 추가했다.
   REST 읽기 권한에 의존하지 않고 기존 집단 관련 표와 같은 소유자 읽기 전용 스냅샷으로 받는다.
   새 백업 폴더 0700, 데이터 파일 0600을 적용한다. 같은 이름의 기존 파일도 권한을 좁힌다.
2. 모든 public 데이터 쓰기를 **단일 `psql --single-transaction`** 호출로 처리한다.
   `--write --maintenance`와 같은 프로젝트 DB 소유자 연결이 필요하다. 모르는 표는 거절한다.
3. 대상 표를 잠그고 원래 사용자 트리거 상태를 보관한 뒤 복원 중에만 중지한다.
   이것은 소유자가 직접 실행하는 오프라인 복구 경로다. 앱/RPC에 우회 권한을 추가하지 않는다.
   알림·세션·변경 신호를 다시 생성하지 않으며 FK·고유키·CHECK·NOT NULL 제약은 유지한다.
   성공하면 원래 O/D/A/R 상태로 복구하고, 실패하면 트리거 변경도 트랜잭션과 함께 취소한다.
4. 실제 FK로 순서를 계산하고 기본키/칼럼을 검사한다. `OVERRIDING SYSTEM VALUE`로 생성 전용 ID도 보존한다.
   `--replace` 없이 기존 행을 덮어쓰지 않는다. `--replace`도 없는 행을 삭제하지 않는다.
5. 다음 ID는 기존 시퀀스와 적재 자료보다 크게 `ALTER SEQUENCE ... RESTART`한다.
   `setval`과 달리 트랜잭션 실패 시 번호 변경도 취소된다. SQL Editor 후처리는 없앴다.
6. 집단 설정은 목록에서 재생성하고 기존 소속을 연결한다. 구역/배정 수정 번호는 역행시키지 않는다.
   로그인 PIN은 기존 bcrypt 해시만 허용하고 평문을 그대로 넣지 않는다.
7. 전체 복원은 대상에 설치된 허용 표의 백업 파일이 빠졌으면 실패한다. 일부 표만 복구하는
   `--table`은 선택한 표만 처리한다. 집단 관련 복원의 부모 파일 검사는 그대로 유지한다.

`--maintenance`는 접속 차단을 자동으로 해 주는 기능이 아니다. 운영자가 앱 접속·cron·백그라운드
쓰기와 사용 중인 화면을 멈췄음을 확인하는 옵션이다. 복원 중 읽기도 대기하므로 실제 이용 중 실행 금지.
복원 후 로그인과 화면을 새로 시작해야 하며, 누락 파일에 임의로 빈 배열을 만들어 완전 백업처럼 취급하면 안 된다.
SQL 오류와 연결 단절은 구분한다. 커밋 직후 응답만 유실될 수 있으므로 연결 단절 뒤에는 대상 상태를 확인한다.

## 격리 입력과 결과

- 원본: `backups/2026-11-20` JSON 43개 / 29,548행과 병합 감사 SQL 18행.
- 구조: 저장된 11/18 덤프의 스키마 + 11/19 후속 마이그레이션. 현재 운영 스키마 재조회는 하지 않았다.
- 원본 SHA-256 전후 동일. 별도 임시 PostgreSQL, Unix socket만 사용하고 종료 후 삭제했다.
- 실제 `restore.js`와 소유자 SQL 실행기를 사용했다. 로더는 `.env` 접근을 막고 연결과 입력 경로만 로컬로 바꾼다.
- 원본에 없는 새 업무 표 3개는 **각 1행의 명확한 시험 자료**를 임시 복사본에 추가했다.
  기존 백업만의 전체 복원은 거절된다. 시험 자료 성공은 실제 누락 자료 복구를 뜻하지 않는다.

## 시험과 변이

- `atomicRestore.sql.test.ts`: 실제 PostgreSQL 호환 실행으로 ID·부작용·FK·전체 취소·소속·버전·소유자·번호 보호.
- `backupCommands.test.ts`: 실제 명령 본체의 스냅샷 연결, 새 표 포함, 파생 설정 제외, 유지보수 확인.
- `mutateAtomicRestore.mjs`: 13개 변이 전부 검출. ID override, 트리거 중지/복구, 번호 정리/원자성/역행, FK 우회,
  누락 파일 검사, 구역/배정 수정 번호, 평문 PIN 차단, 유지보수 확인, 백업 스냅샷 연결을 제거했다.
- 기존 집단 백업 변이 10개 전부 검출.
- 실제 로컬 복원 명령에서 중복 처리 제거 변이도 두 번째 재시도가 실패해 검출했다.
- 최종 전체 시험: 288개 파일, **2,879개 통과**. 시퀀스 역행을 막는 추가 시험까지 포함한다.
- lint·build 통과. 빌드의 기존 큰 번들/서비스워커 옵션 경고는 남아 있으며 배포는 실행하지 않았다.
- 최종 실제 복구 기록: `backups/recovery-rehearsal-1795147694992/report.json`.
  원본 29,548행 + 시험 3행의 46개 데이터셋을 비교했고, 원본 SHA-256과 임시 클러스터 삭제까지 확인했다.

```bash
REHEARSAL_PG_BIN=/path/to/postgresql/bin node scripts/rehearseProductionBackup.mjs
node scripts/mutateAtomicRestore.mjs
node scripts/mutateGroupTerritoryBackup.mjs
REHEARSAL_PG_BIN=/path/to/postgresql/bin node scripts/rehearsal/mutateRetry.mjs
```

## 남은 운영 복구 관문

- **실제 누락 3개 표는 아직 재백업하지 않았다.** 다음 승인된 읽기 전용 백업에서 실제 자료를 확보하고 다시 대조해야 한다.
- 전체 JSON이 같은 시점의 스냅샷은 아니다. 이번 스냅샷 묶음 외의 표는 기존 페이지 읽기이며 FK 불일치는 복구 중 거절된다.
- private 병합 감사 SQL은 별도 단계로 빈 감사 표에 적재해 18행을 확인했다.
  public 원자적 복원 트랜잭션에는 포함되지 않으며 SQL 재적재는 별도로 중복 여부를 확인한다.
- 세션 토큰·푸시 비밀 설정은 의도적으로 제외한다. private 설치 manifest/전환 상태·신호 초기화는
  대상 프로젝트 설치 절차가 책임진다. 전체 앱 서비스 재개를 검증한 것은 아니다.
- 실물 앱·실제 Supabase HTTP·현재 운영 정책·운영 규모 잠금/중단 시간은 이번 범위가 아니다.
  결과의 `readyForProductionRecovery`는 계속 **false**로 둔다.

## ced5eed 리뷰 후 보강

- 이름순과 FK 순서가 다른 `cards → buildings → units` 시험을 추가했다. 위상 정렬을 제거하면 실패한다.
- 집단 담당 연결만 복원해도 구역 수정 번호가 올라가고 오래된 저장 요청이 거절되는 시험을 추가했다.
  **이 시험에서 실제 부분 복원 오류를 발견했다.** `card_group_assignments`만 선택하면 수정 번호를 바꿀
  `cards`가 잠금/트리거 복구 대상에 없어서 `Group revision is server managed`로 실패했다.
  연결만 복원할 때도 `cards`를 대상에 포함하는 3줄을 추가했다. 앱 권한·마이그레이션은 변경하지 않았다.
- 미등록 파일 및 `--table` 선택 거절을 각각 시험한다. 화상 암호 등 데이터 파일 0600, 폴더 0700,
  기본 생성 권한 0077을 명령 본체 시험에서 확인한다. 실제 파일 내용/연결은 모의 객체인 시험이다.
- 변이 19개 전부 검출. 새 6개는 FK 순서 제거, 연결만 복원할 때 cards 제외, 연결 복원의 수정 번호 증가 제거,
  미등록 파일 허용, 미등록 선택 표 허용, 파일 chmod 제거다.
- 보강 후 전체 시험 288개 파일 **2,884개 통과**, lint·build 통과. 앱 화면 코드는 바뀌지 않았다.

### 실제 격리 리허설과 시간

기록: `backups/recovery-rehearsal-1795148146830/report.json`.
원본 해시 동일, 임시 PostgreSQL 종료/삭제 완료. 기존 정상/중간 실패/두 번 재시도/자료 비교를 다시 통과했다.
저장된 운영 구조에는 집단 담당 기능이 없어, 별도의 로컬 사본에만 1600/1700을 설치하고 실제 CLI로
연결만 복원했다. 공동 담당 2개 유지, 수정 번호 1→2, 모든 트리거 상태 유지, 직접 번호 변경 차단을 확인했다.

| 명령 구간 | 경과 시간 |
| --- | --- |
| 정상 전체 복원 | 493ms |
| 전체 중간 실패 | 540ms |
| 전체 재시도 | 555ms |
| 전체 두 번째 실행 | 397ms |
| 집단 연결만 복원 | 127ms |
| 준비·대조·실패 시나리오·정리 포함 리허설 전체 | 7,084ms |

시간은 로컬 CLI 실행 전후의 단조 시계로 측정하며 프로세스 실행·파일 읽기·로컬 DB 연결도 포함한다.
순수 SQL 실행 시간이나 원격 Session pooler 성능은 아니다. 모든 명령의 `durationMs`와 전체 시간을 보고서에 저장한다.

`runOwnerSql`의 제한은 SQL 문장/DO마다 120초, 잠금 대기 10초다. 전체 트랜잭션이 단일 DO인 것은 아니지만
표별 적재 반복문은 한 DO 안에 있으므로 그 구간에 120초 제한이 적용된다. 이번 결과만으로 제한을 늘리지 않았다.
실제 원격 복구 전에는 별도 승인된 비운영 원격 대상에서 송신·잠금 시간을 측정해야 한다.
명시적 표 잠금 루프를 제거하는 동시성 변이는 이번에도 검증하지 않았다. 두 연결 시험의 남은 범위로 유지한다.

운영 재백업·접속·배포는 실행하지 않았다. 누락된 실제 운영 자료 3개의 확보는 여전히 별도 승인 단계다.
