# 실시간 복구 조회의 시간 범위와 중복 비용

- 상태: 데모 검증 중, 운영 미적용
- 결정일: 2026-09-30
- 대체: 0008의 과거 신호 전체 복구
- 마이그레이션: `20260930_2300_territory_recovery_watermark.sql`

## 배경

0008은 live 신호를 건물별로 묶지만, 첫 구독/복귀 때 과거에 변경된 모든 건물을
다시 받았다. 신호 표가 누적되면 전체 재조회에 가까워지므로 운영 차단 사유다.

## 결정

- 신호에 `changed_at`을 추가한다. 메타데이터 공개 범위에 변경 시각이 추가되지만
  이름/주소/방문 내용은 계속 없다. 쓰기 권한은 이전과 같다.
- 이미 있던 신호는 `-infinity`로 시작한다. 초기 전체 스냅샷에 포함되므로
  마이그레이션 시점의 변경으로 위장하여 모두 다시 받지 않는다.
- 서버 `clock_timestamp()`를 반환하는 invoker RPC로 기준시각을 얻는다.
  기기 시계가 빠르거나 느려도 복구 범위가 달라지지 않는다.
- 전체 buildings+visits 조회 **시작 전** 시각을 조회 성공 후에만 baseline으로
  저장한다. 끝난 시각을 쓰면 읽는 도중 발생한 변경을 놓칠 수 있다.
- clock RPC 미등록/스키마 캐시 지연/통신 실패는 기본 자료 로드를 막지 않는다.
  이번 baseline만 null로 두고 조회를 계속한다. 기존 성공 기준점은 유지하며,
  처음부터 기준점이 없다면 증분 복구는 건너뛴다. 다음 성공한 전체 조회에서 복구한다.
- 복구는 카드별 성공 시각과 baseline 중 최신 값에서 30초를 빼서 조회한다.
  시간 조건은 SQL/PostgREST에 전달한다. 브라우저에서 전체를 받아 거르지 않는다.
- 30초 겹침에 걸린 신호도 이미 반영한 revision+changed_at이면 다시 읽지 않는다.
  checkpoint는 store 수명 동안 유지하여 지도 재진입/필터 전환에도 남는다.
  로그인 해제 시 초기화한다. 읽기 실패/중단 시 성공 시각을 전진시키지 않는다.
- 기존 전체 복구가 진행 중이면 기다린 뒤 새 baseline을 사용한다. 동시에 들어온
  전체/삭제/세대생성 복구는 slice별 진행 중 요청을 공유한다. 저장 후 mutation
  조회는 저장 전 요청에 합치지 않는다. 공유한 이전 조회의 시작 시각을 잘못
  앞당기지 않도록 그 호출은 baseline을 전진시키지 않는다.

## 남는 비용과 한계

- 기존 2분 foreground 전체 갱신은 유지한다. 다른 도메인의 배정/공지/설정 등을
  갱신하는 계약을 이 수정에서 없애지 않는다. 따라서 전송량 문제 전체 해결이나
  모든 복귀 조회가 delta-only라는 주장은 하지 않는다.
- slice 공유는 **동시에 진행 중인** 요청만 합친다. 시간차를 둔 별도 복구가 모두
  하나로 합쳐지는 것은 아니다. 공통 복구 스케줄러/도메인별 증분화는 후속 과제다.
- PC 지역/카드 필터 변경은 여전히 채널을 다시 만든다. 복구 데이터는 해당 카드의
  증분으로 제한되지만 채널 재구독 자체는 남는다.
- 30초는 커밋 경계의 안전 여유다. 30초를 넘는 장기 트랜잭션이 연결 단절 중
  커밋하는 임의 관리 SQL까지 완전한 변경 로그처럼 보장하지 않는다. 대량 이관
  뒤에는 전체 새로고침이 필요하다. 삭제는 기존 삭제 신호/복구가 담당한다.
- 빈 복귀에도 clock RPC와 카드 100개당 신호 조회는 있다. 0건이라는 실측은
  **buildings 본문 요청** 수이며 전체 HTTP 요청이 0이라는 뜻이 아니다.

## 검증

단위 시험: 서버 시간 조건, 카드별 cursor, 겹침 중복 제거, 실패 시 cursor 보존,
전체 조회 대기, 복구 조회 공유 및 mutation 분리. 조건을 제거한 변형 세 개에서
각각 대응 시험 하나씩 실패하는 것을 확인했다.

데모 smoke는 기존 상태/빈 건물/세대/오프라인 복구에 더해, 변경 없는 복귀 3회와
2분 foreground 분기를 실제 배포에서 API 응답 수로 확인한다. 2분 분기는 브라우저
Date.now만 125초 이동한다. DB 기준시각은 실제 서버 시각 그대로다.

2026-09-30 최종 데모: 변경 없는 복귀 3회는 buildings 요청 각각 0건.
2분 분기 복귀는 2건(전체 1회 + 최근 변경 2개 건물의 묶음 1회). live 부재 반영
1,022ms, 빈 건물/첫 세대/취소/오프라인 복구/범위 밖 무조회/URL 범위 보존 통과.
이 시험은 동일 봉사자 계정의 독립 브라우저 2개를 썼고 합성 자료를 정리했다.
전체 시험 1,072개 / 149파일, lint/build, SQL 계약 시험, 설치 패키지 검사 통과.
실측 요청 수는 작은 데모 자료 기준이며 1,000행 초과 데이터는 페이지 수만큼 늘어난다.

보안 수정 `107e24b`를 포함한 main을 먼저 병합했다. 운영 main/DB는 수정하지 않는다.
백업: 비공개 `backups/2026-09-30-demo-realtime/before-watermark.dump`.
복구는 기능 플래그를 끄고 배포 후 0008 전체 rollback을 실행한다. 새 clock 함수도
함께 제거하며 원본 건물/방문 자료는 삭제하지 않는다.
