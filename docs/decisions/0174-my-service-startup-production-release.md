## 작성자 재점검 (반영 뒤, 코드 변경 없음)

독립 리뷰가 아니다. 작성자가 반영 뒤 다시 본 것이다. 운영은 읽기만 했다.

- **관문 밖 저장 흐름**(나의 봉사): 관문 밖에서 저장할 수 있는 것은 두 가지다. 둘 다 건물 자료를 쓰지 않는다.
  - 진행 중 식당 세션의 결과 저장: 저장된 세대 번호만 쓴다.
  - 신청 식당 메모 저장
- **관문 안 저장 흐름**: 정기방문 별명·주소 수정, 방문 기록 추가·수정·삭제, 정기방문 종료는 모두 관문 안의 정기방문 목록에서만 열린다.
- **식당 추가 신청**은 입력값만 보낸다. 구역 경계는 가벼운 진입에서도 기기 캐시·변경분 방식으로 좌표까지 받는다(`cardBoundaryRecovery`).
- **운영 규모 추정**(데모 자료 47배 확대, 합성 조건, 각 1~2회. 운영 실측 아님)

| 인도자 | P | 이번 반영 |
|---|---|---|
| 나의 봉사 첫 진입 | 765 / 1,649ms, 12건, 1,686 KB | 358ms, 7건, 6.8 KB |
| 배정 지도 처음 열기 | 114ms, 0 KB | 694ms, 10건, 1,509 KB |
| 지도 → 식당 시트 | 43ms | 45ms, 0건 |

  - 큰 자료를 받는 시점이 나의 봉사 진입에서 지도를 처음 여는 때로 옮겨 갔다. 지도를 열지 않는 인도자는 그만큼 받지 않는다.
  - 실제 휴대폰·느린 통신에서는 지도 처음 열기 대기가 이보다 길 수 있다.
- **측정 도구 결함**(앱 결함 아님)
  - 확대 기능이 번호를 지정한 이름표 조회(`id=in.(…)`)까지 복제해, 요청하지 않은 번호의 행을 돌려줬다. 앱은 그런 행을 거부하게 되어 있어 첫 진입이 끝나지 않는 것처럼 보였다.
  - 실제 서버는 요청한 번호만 돌려준다. 번호를 지정한 조회는 복제하지 않도록 측정 도구를 고쳤다(`perf-fx-admin.mjs`).
