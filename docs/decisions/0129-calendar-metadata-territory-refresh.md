# 일정 표시 정보 변경 시 개인 구역 재조회 생략

- 결정일: 2026-11-18
- 상태: 데모 검증. 운영 main/환경변수/DB/배포 변경 금지 유지.
- 기준: 운영 배포 뒤 `d9756ca` 작업본. DB/권한/배정 쓰기는 변경하지 않는다.

## 이유와 범위

일정 변경 신호는 현재 캘린더를 새로 읽고, 봉사자의 경우 개인 배정·직접 배정·
활성 세션·정기방문·식당 배정으로 구역 범위를 다시 확인했다. 제목이나 메모만
바뀌어도 이 과정과 건물 변경 확인·카드 요약·구역선 조회가 이어졌다.

`VITE_CALENDAR_METADATA_REFRESH_ENABLED=true`로 명시한 빌드만 새 경로를 쓴다.
DEMO_MODE와 무관하며 기본 OFF다. 이번 데모에서만 ON으로 빌드한다.

## 보존하는 계약

1. Realtime의 `calendar_events UPDATE` 중 유효한 일정 ID가 있는 신호만 후보로 전달한다.
   같은 2초 묶음에 배정/연결 카드/식당 배정/일정 INSERT·DELETE/알 수 없는 신호가
   하나라도 들어오면 기존 구역 재확인을 유지한다. 재연결에도 생략 근거를 넘기지 않는다.
2. 기존 캘린더 조회와 그 일정들의 배정·연결 카드 조회를 먼저 끝낸다. 이 조회는 줄이지 않는다.
3. 첫 로딩 성공 + 이전 구역 조회 성공 + 개인 범위 확정 + calendar 단독 realtime 호출이어야 한다.
   화면에 없는 일정, 추가/삭제된 일정, 달 이동, 수동 새로고침, 앱 복귀는 기존 경로다.
4. 변경 전후 캘린더의 모든 일정을 비교한다. 신호에 있는 일정의 제목·시각·종료 시각·장소·
   지도 링크·메모·편집 버전만 달라질 수 있다. 날짜, 집단, 인도자, 신청자, 배정,
   공유 상태, 배정 리비전, 팀 범위 등은 모두 같아야 한다. 새로 추가되는 표시 모델 필드도
   기본적으로 비교 대상이다. 다른 일정에 예고하지 않은 변경이 있어도 재확인한다.
5. 직전 구역 갱신이 실패했다면, 다음 변경이 메모뿐이어도 구역을 재확인한다.
6. 기존 대기열, 최신 응답 판정, 서버 권한, 개인 구역 계산, 실시간 건물 변경·복구는 그대로다.
   인도자/관리자 조회 경로는 변경하지 않는다. 자료를 더 오래 보관하는 TTL도 추가하지 않는다.

## 실측

`scripts/measureCalendarMetadataDemo.mjs`는 실제 데모 DB에 회중·집단 시험 일정 두 개를 만들고,
별도 관리자 HTTP 연결에서 메모를 수정한다. 실제 WebSocket 신호를 받은 앱의 useStore와
useCalendarRealtime을 JSDOM에서 실행한다. 메모 수정은 푸시 알림을 보내지 않는다.

11/18 운영의 boolean 설정으로 OFF/ON을 번갈아 측정했다. 개인 구역 내용이 전후 같고,
새 메모가 실제 일정 자료에 반영됐는지 확인했다. 봉사자는 3쌍, 회중/집단 각 3회다.
인도자와 실제 관리자도 각 1쌍, 회중/집단 각각 확인했다.

| 대상 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 봉사자, 변경 한 번의 HTTP 조회 | 17건 (6회 모두 동일) | 3건 (6회 모두 동일) |
| 봉사자, 응답 원문 중앙값 | 11,105.5B | 8,857.5B |
| 봉사자, 첫 조회 시작~마지막 응답 완료 중앙값 | 977ms | 205.5ms |
| 인도자, HTTP 조회 | 3건 | 3건 |
| 인도자, 응답 원문 중앙값 | 9,681.5B | 9,681.5B |
| 관리자, HTTP 조회 | 3건 | 3건 |
| 관리자, 응답 원문 중앙값 | 9,682.5B | 9,681.5B |

봉사자 요청 82.4%, 응답 원문 약 20.2% 감소. 인도자/관리자의 시간 차이는 통신 편차이며
개선으로 주장하지 않는다. 메모 내용 길이 때문에 대조군 응답에 1~수 B 차이가 있다.
줄어든 것은 개인 범위 확인과 그 후속 조회다. 캘린더·배정·연결 카드 3개는 그대로 읽는다.

모든 HTTP 진행 상태와 응답 본문 완료를 추적하고, 마지막 완료 후 600ms 동안 조용해야
다음 구간으로 넘어간다. 30초 내 안정되지 않으면 측정을 실패시킨다.
이 값은 앱 전체/아이폰 화면 표시 시간, 압축 전송량, WebSocket 사용량, 과금 egress가 아니다.
기존 2초 신호 합치기 대기 시간도 위 readMs에 포함하지 않는다. 하루 전체 사용량이
20.2% 감소한다는 뜻이 아니다. 배정 변경/복귀/첫 로딩의 요청은 그대로다.

원본: `scratch/calendar-metadata-measurement.json` (역할별 결과만 포함, 토큰 없음).
재현:

```sh
DEMO_ENV_FILE='../chinese-territory-app/.env.test.local' \
FLAGS_FILE='backups/nov18-evening-release/production-after.env.local' \
node scripts/measureCalendarMetadataDemo.mjs --confirm-demo
```

초기 시도는 기존 집단 시간대와 겹쳐 유일 제약에서 거부됐다. 시험 시간을 분리했다.
다음 시도는 변경 신호 대기 20초를 넘겨 실패했다. 신호/연결 상태 진단과 30초 한도를 넣은
완주 실행만 위 표에 썼다. 실패 시도와 완료 실행 모두 시험 일정은 정리했으며 잔여 0건을
데모에서 별도 확인했다. 데모 로그인/접속 기록은 남는다.

## 시험과 한계

- 새 판정/신호 전달/구역 갱신 시험 305개 통과 (기존 관련 시험 포함).
- 배정 취소·추가·연결 카드 감소·팀 범위 변경은 리비전이 같아도 재확인한다.
- 날짜·인도자·집단·신청자 변경, 일정 제거, 모르는 ID, 묶인 배정 신호, 수동/복귀는 유지한다.
- 구역 갱신 실패 뒤 메모 변경이 실패한 구역을 재사용하지 않는지 확인한다.
- 변이: 표시 정보 비교를 제거하면 권한/취소/불명 신호 관련 6개 시험 실패.
- 변이: 구역 조회 전 준비 상태 무효화를 제거하면 실패 후 복구 시험 실패.
  두 변이는 복구했고 관련 시험을 다시 통과했다.
- 실제 HTTP+Realtime 실측은 메모 변경만 쓴다. 배정 취소와 권한 경계 검증은 자동 시험이며,
  실제 두 휴대폰에서 배정 변경/계정 전환까지 재현한 검사는 아니다.
- 측정 중 React act 환경 경고는 있었지만 요청 실패/정합성 단언 실패는 없는 완주 결과다.
- 전체 269파일 2,645개 시험 통과. lint, TypeScript, 데모 production 빌드 통과.
  번들 크기/Workbox 옵션 경고는 기존 빌드 경고이며 새 오류는 없다.

## 운영 상태

운영 설정·DB·배포는 변경하지 않는다. 운영 적용은 별도 리뷰와 사용자 결정 후 진행한다.
기능을 끄면 기존 재확인 방식으로 돌아간다. DB 마이그레이션이나 권한 확대는 없다.
