# 자주 쓰는 화면 조회 개선 1차

- 결정일: 2026-11-18
- 상태: 데모 검증, 운영 적용 금지.
- 기준: `2b85477`의 요청 구간 정정 도구와 `cbb9c19` 앱 코드.

## 범위

설정 → 캘린더 → 나의 봉사 → 구역/지도 순으로 점검했다.
각 화면에 반드시 수정 한 개씩을 만들지는 않는다. 불필요한 읽기와 직렬 대기를
확인한 곳만 바꾸며, 필요한 자료/최신성/권한/저장 검사를 줄이지 않는다.

## 변경

1. 개인 설정/내 정보/알림/위치 권한/개인정보 화면은 건물 전체 자료를 요구하지 않는다.
   인도자/관리자의 기존 building-demand 설정이 켜진 경우에만 적용된다.
   이미 읽은 더 풍부한 자료는 store가 그대로 보존한다. 이후 지도/나의 봉사/관리 화면은
   원래 필요한 자료가 완성되어야 열리고, 실패/재시도도 그대로다.
   알려지지 않은 설정 하위 경로, 쿼리, 관리 편집기는 보수적으로 전체 자료를 요구한다.
   개인 설정 경로 목록은 일정 범위 유지 기능과 공유하고, 그 기능의 기존 플래그는 유지한다.
2. 캘린더 최초 진입 때 선택 월이 아직 비어 있으면 이번 달 전체를 바로 요청한다.
   건물 조회 완료 후 캘린더가 마운트되어야 월 조회가 시작되던 대기 한 단계를 없앤다.
   선택된 과거 월, 월 캐시, 월 전체 참가자/배정, 수정 시 전체 범위, 알림의 과거 일정 링크는 유지한다.
3. 모바일 관리자의 처리 건수 조회는 숫자가 실제 보이는 `/settings`에서만 활성화한다.
   설정으로 돌아오면 새로 읽으며, 설정에 머무르는 동안 변경 신호/앱 복귀 갱신도 유지한다.
   숫자가 계속 보이는 PC 설정 사이드바는 바꾸지 않는다. 일반 알림함 조회도 바꾸지 않는다.

DB/권한/신청/배정/댓글/알림 저장 로직 변경 없음. main/운영 환경변수/운영 배포 변경 없음.

## 유지/보류한 부분

- 캘린더 월 이동은 이미 완전한 범위만 재사용한다. 읽지 않은 월까지 빈 일정으로
  취급하거나 오래된 참가자/배정을 계속 쓰도록 캐시를 늘리지 않는다.
- 나의 봉사의 건물 좌표/메모/정기방문·과거 배정은 실제 소비자가 있다. 이 자료를
  삭제하는 대신, 후속에서는 화면 소비 범위를 더 분리할 수 있는지 별도로 설계한다.
- 구역에서 지도로 갈 때에는 좌표·출입 이력 등 추가 자료가 필요하다.
- 지도 재진입의 2건/약 36B는 동기화 시점과 변경 신호다. 현장 변경 누락을 막는
  읽기라 제거하지 않는다. 지도 타일/실제 핀 렌더링 시간은 별도 검증 대상이다.

## 시험 및 리뷰 기준

- 개인 설정은 건물 조회를 시작하지 않고 기존 카드 집계를 보존한다.
- 지도에서 설정으로 돌아가도 좌표/상태 자료가 줄지 않는다.
- 설정 이후 나의 봉사는 메모를 포함한 전체 자료 준비를 기다린다.
- 관리자/인도자, PC/모바일 경로, 알려지지 않은 경로/쿼리를 시험한다.
- 캘린더 컴포넌트가 건물 로딩으로 아직 열리지 않아도 이번 달 범위가 먼저 전달된다.
- 윤년/연말/과거 선택 월/댓글 링크/편집 전체 범위를 시험한다.
- 처리 건수는 숨겨진 동안 읽지 않고, 설정 재진입과 변경 신호 때 다시 읽는다.
- 세 최적화를 각각 원래 동작으로 되돌린 변이에서 새 시험 6개가 실패함을 확인했다.
  원래 개선 코드를 복구한 전체 2,556개 시험(263개 파일), lint, 데모 빌드 통과.
- 기존 저장·권한·실시간 갱신·초기 로딩 실패 시험 유지.

기록: `scratch/speed-routes-{before-settings-final,after-settings,before-calendar-final,after-calendar,before-zone,after-zone,after-service}.json`.
도구 `scripts/measureServiceNavigationDemo.mjs`에 `JOURNEY=settings|calendar|service|zone`을 지정한다.
HEAD 건수 조회는 본문이 없으므로 응답 헤더에서 센다. Chromium이 200 헤더를 전달하고
HEAD를 ERR_ABORTED로 보고하는 경우도 누락하지 않으며, 실제 비정상 상태 코드는 실패한다.
초기 두 관리자 측정은 이 HEAD 처리 문제로 검증에 실패해 버렸고, 표에는 보완 후 결과만 사용했다.

Claude는 특히 개인 설정으로 분류된 페이지가 건물 전체 자료를 소비하지 않는지,
캘린더 최초 월과 표시 월이 어긋나지 않는지, 설정의 관리 건수가 재진입 때 갱신되는지
검토한다. 3·4순위는 검증/보존이며 성능 개선 완료로 표시하지 않는다.
