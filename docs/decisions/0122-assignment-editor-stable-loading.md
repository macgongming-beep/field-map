# 팀 구성·구역 배정 진입 화면 유지

- 상태: 데모 검증, 운영 미적용
- 결정일: 2026-11-18
- 기준 커밋: 83c33d9

## 배경

배정 편집기 진입 때 다른 화면을 거쳤다가 돌아오는 느낌을 확인했다.
실제 URL 이동은 없었다. 최신 일정 조회 중에는 전체 화면 편집기를 표시하지만,
조회 후 FullBuildingGate가 건물 자료를 기다리는 동안에는 일반 로딩 div로
바뀌어 아래 일정 화면이 약 0.6~0.7초 노출됐다. 자료가 오면 편집기가 다시 덮었다.

모바일 프레임 기록(클릭 이후 ms, editor = 전체 화면 편집기 존재):

| 역할·회차 | editor=true | editor=false | 다시 true |
| --- | ---: | ---: | ---: |
| 인도자 1 | 16 | 399 | 992 |
| 인도자 2 | 13 | 396 | 1118 |
| 관리자 1 | 12 | 662 | 1237 |
| 관리자 2 | 14 | 398 | 1004 |

## 결정과 불변 계약

- 최신 일정과 전체 건물 자료는 서로 독립적으로 읽기 시작한다.
- 두 자료가 모두 준비된 뒤에만 편집기 본문을 연다. 최신 참가자와 배정 리비전을
  사용하는 기존 저장 보호는 유지한다.
- 읽는 동안과 실패한 경우에도 같은 전체 화면, 제목, 뒤로 버튼을 유지한다.
- 일정 실패는 일정만, 건물 실패는 기존 건물 재시도 경로로 재시도한다.
- 닫힌 화면에는 늦은 응답을 반영하지 않는다.
- 조회 대상·권한·DB·배정 저장·공유·나의 봉사 데이터 경로는 바꾸지 않는다.

## 속도와 사용량

Chromium, 390px, REST 요청별 120ms 지연, 역할별 전후 2회.
요청 완료 후 600ms 조용한 구간까지 추적하며, 30초 내 안정되지 않은 측정은 실패한다.
실제 아이폰/LTE 측정이 아니다. 응답량은 압축 전 본문 크기다.

| 역할·회차 | 첫 진입 전→후 | 요청 전→후 | 응답 바이트 전→후 |
| --- | --- | --- | --- |
| 인도자 1 | 999→615ms | 9→9 | 38,371→38,371 |
| 인도자 2 | 1,129→613ms | 9→9 | 38,371→38,371 |
| 관리자 1 | 1,245→628ms | 9→9 | 39,443→39,443 |
| 관리자 2 | 1,013→662ms | 9→9 | 39,443→39,443 |

재진입은 전후 모두 3건·1,487바이트다. 수정 후 모든 프레임에서 편집기가 유지되고
URL은 바뀌지 않았다. PC 1365px에서도 인도자·관리자의 첫 진입/재진입을 확인했다.
PC는 수정 후 기능 검사이며 전후 성능 비교는 아니다.

정상 진입의 사용량은 같지만 동시 요청 수는 늘 수 있다. 즉시 닫기나 일정 조회 실패 시
이미 시작한 건물 조회는 계속될 수 있으므로, 모든 취소·실패 상황의 사용량까지
같다고 주장하지 않는다. 자동 재시도나 추가 구독은 도입하지 않았다.

측정 원본(로컬 scratch, 커밋하지 않음):
`speed-assignment-before.json`, `speed-assignment-after.json`,
`speed-assignment-after-desktop.json`.

## 나의 봉사 확인

봉사자·인도자·실제 관리자, 모바일 390px·PC 1365px의 6조합을 전후 검사했다.
봉사자의 나의 봉사→배정 지도→돌아오기는 `/map?assignmentMap=198`→`/territory`였고
홈이나 캘린더를 거치지 않았다. 왕복 요청은 모바일 3건, PC 2건으로 전후 같았다.
재사용 조건에서 추가 일정·식당 배정 조회가 없고 콘솔 오류와 가로 넘침도 없었다.
인도자 시험 계정에는 배정 지도 링크가 없어 해당 지도 왕복은 검사하지 못했다.
관리자는 기존 구역 관리 화면이며 나의 봉사 메뉴를 새로 만들지 않았다.

원본: `myservice-assignment-before-ui.json`, `myservice-assignment-after-ui.json`.
다른 집단 탭을 선택한 뒤 편집기에서 복귀할 때의 탭 유지 여부는 이번 기본 탭
검사와 별도다. 모든 진입 경로의 문제가 해결됐다고 확대 해석하지 않는다.

## 자동 시험

새 시험 5개: 일정/건물 응답 순서 두 경우, 일정 실패·재시도, 건물 실패·재시도,
읽는 중 닫기. 두 자료 준비 전 편집·공유 차단, 최신 참가자·리비전 사용을 확인한다.
로딩 wrapper에서 전체 화면 클래스를 일부러 제거하면 응답 순서 시험 2개가 실패한다.
원복 후 전체 2,580개(264파일), lint, 데모용 build 통과.
기존 큰 청크 및 inlineDynamicImports 폐기 예고 빌드 경고는 남아 있다.

## 운영 상태

운영 앱·DB·환경변수·main은 변경하지 않는다. 기능 브랜치의 데모 배포만 진행한다.
실제 아이폰에서 새 데모를 받은 뒤 일정 상세→팀 구성·구역 배정→뒤로 흐름의
체감 확인은 별도로 필요하다.
