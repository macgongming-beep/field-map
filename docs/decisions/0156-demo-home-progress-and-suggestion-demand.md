# 홈 구역 현황 제거와 제안 열 때 읽기

- 날짜: 2026-11-22
- 상태: 데모 검증 중. 운영 미적용.
- 기준: `c7e5b85` (0155의 두 조회 최적화 ON인 데모 설정).
- 요청: 인도자 홈의 담당 구역/진행률을 제거하고, 대화 방법 제안은 열 때 읽는다.
  통계의 구역별 방문 현황은 유지한다.

## 표시와 의미

- 관리자 운영 현황은 0115에서 이미 제거됐고, 이번에는 남아 있던 인도자의 담당
  구역 진행률 카드와 상위 화면의 카드 필터 계산을 제거한다. 모바일/PC 공통이다.
- 오늘의 봉사, 모임 글 입구, 대화 방법 제안 입구는 유지한다. 제안은 기본 접힘이며
  펼쳐야 읽기 컴포넌트가 마운트된다. 닫으면 해제하고 다시 열 때 공개 여부를 재확인한다.
- 예전 순회방문 모음의 `collapse_suggestions` 값은 저장 형식/DB에 그대로 남긴다.
  이제 항상 접혀 시작하므로 새 앱의 모음 편집 화면에서 그 체크박스만 제거한다.
  이전 앱을 위해 값을 덮어쓰거나 마이그레이션하지 않는다.
- 제안의 최신 공개 글 선정, 다국어 표시, HTML 정리는 유지한다. 읽기 오류는 빈 목록이
  아니라 오류/다시 시도로 표시한다. 닫힌 화면의 늦은 결과는 기존 generation 검사로 버린다.
- 순회방문 모임 글은 별도 기능이다. 홈의 모음/글 개수/읽음 표시는 기존 메타데이터
  조회를 유지하고, 본문은 기존처럼 글을 열 때 읽는다. 이번에 모임 글을 삭제하지 않는다.
- 통계의 구역별 방문률은 선택한 기간의 방문 이력 기준이다. 제거한 홈의 현재 카드
  진행률과 동일한 숫자라고 설명하지 않는다. 구역 목록/지도 진행률도 바꾸지 않는다.

## 조회 경계

- `VITE_ROUTE_LIGHTWEIGHT_ENABLED=true`이고 건물 단계별 읽기를 쓰는 관리자/인도자에게
  `landing` 단계를 추가한다. 기본 홈, 개인 설정, 기존 허용된 관리자 경량 화면만 사용한다.
- 이 단계에서는 카드 목록/지역 사전/진행률 합계와 방문 이력을 읽지 않는다. 기존 시스템
  준비 검사에서 수행하는 작은 카드 ID 조회, 일정/세션/모임 메타데이터 등은 유지한다.
- 더 상세한 화면으로 이동하면 기존 대기 장치 안에서 카드·건물·방문 이력을 읽는다.
  캘린더의 서버 합계, 구역 목록/지도 상태, 통계의 전체 자료, 배정 편집기의 전체 자료를
  준비한 뒤에만 화면을 연다. 이후 홈으로 돌아와도 이미 확보한 자료를 버리지 않는다.
- 자료를 확보하지 않은 홈에서는 구역 변경 신호 때문에 건물/진행률을 미리 받지 않는다.
  상세 단계의 복구 기준 시각은 그 단계의 스냅샷 전에 새로 잡는다.
- 운영의 해당 설정이 OFF이면 기존 조회를 유지한다. 봉사자 개인 구역 조회와 개발자
  전체 읽기는 그대로다. SQL/RLS/배정 저장/신청/알림/운영 설정은 변경하지 않는다.

## 검증과 측정

- 전체 294파일 2,960개 시험, TypeScript, lint 통과.
- 새 시험은 홈에서 건물/진행률/방문 이력을 기다리지 않는 것, 명시적 새로고침과
  변경 신호에도 미루는 것, 홈→캘린더/구역/통계로 이동할 때 필요한 자료를 확보하는 것,
  실패 후 재시도, 홈 복귀 시 더 자세한 자료를 버리지 않는 것을 확인한다.
- 제안의 첫 열기, 닫는 중 늦은 응답, 읽기 실패/재시도, 한국어/중국어 빈 상태를 확인한다.
- 분리 복사본 관련 76개 시험 통과 후 변이 9개 모두 검출: 홈 카드 읽기 복원(6개 실패),
  홈 방문 이력 복원(4), 홈 경량 경로 제거(9), 캘린더 이동 시 합계 생략(5), 자료 완료 전
  화면 열기(2), 세션 중복 조회(4), 접힌 제안 마운트(2), 제안 기본 펼침(2), 오류 숨김(1).

측정 도구는 `scratch/measure-home-demand-nov22.mjs`,
원본 로그/화면은 `scratch/home-demand-nov22/`에 보관한다. 이전 버전과 같은 데모
설정, 같은 데모 DB로 비교하며 운영 DB에 업무 요청을 보내지 않는다.

중간 구현은 진행률만 미뤄 캘린더 진입 때 카드 목록이 중복 조회됐다. 이 버전의 인도자
3쌍 결과는 `intermediate-summary-only-leader.json`으로 분리하고 최종 개선 근거에서 제외했다.
홈에서 쓰지 않는 카드 목록도 함께 미룬 최종 버전으로 전후 모두 다시 측정한다.
이어진 중간 구현의 3쌍 측정도 `intermediate-session-repeat-*.json`에 별도로 보관한다.
여기서 확인한 캘린더 진입의 세션 중복 읽기를 제거한 뒤 최종 화면/요청 비교를 다시 한다.
중간 버전의 시간을 최종 버전의 성능으로 사용하지 않는다.

### 최종 요청 비교

기준/최종 빌드를 같은 설정으로 각 1회씩 비교했다. Chromium 390px, CPU 4배,
REST 요청당 120ms 추가 지연, 서비스워커 OFF, 앱 파일은 로컬 제공이다. 마지막
요청 완료 후 800ms 동안 요청이 없어야 측정 구간을 닫는다. 데모 로그인으로 세션/접속
기록은 생기지만 업무 쓰기는 차단했다. 아래 크기는 압축 전 응답 원문이며 과금량이 아니다.

| 경로 | 요청 전후 | 응답 바이트 전후 |
| --- | --- | --- |
| 인도자 홈 | 29 → 24 | 53,256 → 43,723 |
| 관리자 홈 | 29 → 24 | 54,587 → 43,636 |
| 인도자 홈 이후 캘린더 | 5 → 9 | 29,281 → 38,812 |
| 인도자 홈 이후 나의 봉사 | 10 → 10 | 39,199 → 39,200 |
| 인도자 홈 이후 구역 | 10 → 10 | 31,616 → 31,616 |
| 관리자 설정 / 사용자 관리 / 구역 | 2 / 2 / 7 → 동일 | 사실상 동일(0~1바이트 차이) |

- 홈→캘린더 합계는 34→33건, 82,537→82,535바이트다. 홈의 감소 대부분은
  삭제가 아니라 필요할 때까지 미루는 효과다. 제안까지 열면 빈 제안 조회 1건/2바이트가
  더해져 전체 요청과 응답량이 기존과 같다. 데모에는 현재 공개 제안이 없어 본문이 있는
  경우의 요청/전송량은 실측하지 않았다. 해당 내용/실패/닫기/재시도는 시험으로 확인했다.
- 홈 표시 시각은 인도자 1,353→1,305ms, 관리자 1,353→1,335ms였다. 각 1쌍이므로
  속도 향상의 확정 근거로 쓰지 않는다. 실물 아이폰/운영 규모/동시 접속/하루 과금량은 미측정이다.
- 통계는 원래 기간 방문 이력과 전체 구역을 요구하므로 상세 단계로 승격해 읽는 구조를
  유지한다. 홈에서 진행률을 없앤다고 통계 자료를 줄이지 않는다.
- PC Chromium 1440px 관리자 홈→통계→카드별 상세를 전후 각각 열어 13행의 표시
  전체가 동일함을 확인했다. 모바일 인도자/관리자 홈과 PC 통계 캡처를 육안 확인했다.
- 봉사자 WebKit 390px 전후 1쌍: 홈 38→37건(45,365→45,363바이트), 캘린더 16건,
  나의 봉사 18건으로 동일했다. 제안 펼치기에서 미룬 1건/2바이트를 읽는다. 홈 표시
  814→911ms로 오히려 느린 실행이었으며, 개인 구역 읽기를 바꾼 것이 아니므로 봉사자
  속도 개선을 주장하지 않는다. WebKit 실행도 실물 아이폰 검증은 아니다.
