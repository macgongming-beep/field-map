# 나의 봉사 개인 배정 재조회 제거

- 결정일: 2026-11-18
- 상태: 데모만 검증/배포. 운영 변경 금지.
- 기준 앱: `6c8184f` (앱 소스는 `d6949b9`).

## 역할별 실제 화면

- 봉사자(user): 개인 범위 store로 나의 봉사와 배정 지도를 사용한다.
- 인도자(leader): 나의 봉사는 있지만 개인 범위 store는 사용하지 않는다.
- 관리자(admin): PC/모바일 기본 화면은 구역 관리이며 나의 봉사 메뉴가 없다.
  모바일 `/territory`는 구역으로 이동하고 PC 같은 경로는 구역 관리다.
- developer는 admin과 동일한 계정이 아니다. 이번 실제 관리자 화면 검증은
  데모 seed의 관리자 계정으로 로그인하고 서버가 반환한 role=admin을 확인했다.
  기존 측정 도구의 `admin` 이름은 developer 계정이므로 새 `administrator` 항목과 구분한다.

## 변경

나의 봉사의 service 일정 조회는 날짜로 자르지 않은 모든 개인 카드 배정 ID를 읽고,
해당 일정의 팀/여러 카드 연결까지 완성한다. 그런데 일반 봉사자의 구역 범위를 준비할 때
이 결과를 버리고 같은 개인 배정·연결 카드·일정을 다시 읽고 있었다.

`VITE_SERVICE_CALENDAR_REUSE_ENABLED=true`이면 **동일 작업에서 방금 완료한** service 조회를
개인 구역 범위 계산에 전달한다. 기존 `recipientReader.refresh(calendar)` 계약을 이용하며
새 캐시, 새 RPC, DB 변경은 없다. 설정의 기본값은 false이고 데모 빌드만 명시적으로 켠다.

다음 조건을 모두 지킨다.

- scope의 사용자 이름이 실제 recipientUser와 정확히 일치한다.
- 오늘만/한 달만 조회한 window는 개인 전체 배정의 근거가 아니므로 재사용하지 않는다.
- 화면 재진입용 캐시는 권한 범위 계산에 전달하지 않는다.
- 읽기 완료 전 scope/read version 검사를 통과해야 한다. 실패하면 부분 결과를 넘기지 않는다.
- `calendarSnapshotComplete`는 false로 유지한다. 개인 전체 배정이지 전체 회중 일정은 아니다.
- 독립 카드 배정, 활성 세션, 정기방문, 개인 식당 배정은 기존대로 확인한다.
- 변경 후 조회는 새 작업 결과만 전달한다. 마지막 배정이 없어지면 새 빈 결과로 재계산한다.
- 목록→배정 지도는 기존 완전한 service 캐시를 공유한다. 지도 진입 비용을 늘리지 않는다.
- 최초 로딩 실패, 재시도, 권한/계정 변경, 쓰기/실시간 무효화는 기존 계약을 유지한다.

scope 파서는 조회/캐시/재사용 조건이 다르게 해석하지 않도록 한 파일로 공유했다.
파싱 가능한 범위는 기존 3항목 service 키 그대로이며, 임의 추가 모드는 거부한다.

## 보류한 분리

다른 사람의 식당 배정 날짜를 지도 진입까지 미루는 overview 범위를 로컬에서 시험했다.
목록에서는 1건 줄지만 목록→지도에서 기존 범위 재사용이 깨지고 구역 재조회까지 늘 수 있다.
사용자의 실제 후속 작업을 느리게 하므로 이 변경은 제거했고 데모에 배포하지 않았다.
`speed-myservice-after*`는 이 폐기한 시안의 기록이며 최종 성과로 사용하지 않는다.

건물/세대 메모와 방문 이력은 정기방문·식당 화면에서도 쓰므로 제거하지 않았다.
따라서 이번 결과를 '모든 자료 지연 로딩 완료'나 '모든 역할 속도 향상'으로 표현하지 않는다.

## 검증

- 전체 2,567개 시험 / 263개 파일, lint, 데모 빌드 통과.
- 재사용을 강제로 끄면 새 fresh-personal-calendar 시험 2개가 실패했다.
- 개인 과거/미래 배정, 전체 팀/연결 카드, 식당 날짜, 명시적 과거 지도 링크 유지.
- window/다른 이름/설정 OFF는 독립 discovery 유지.
- 실패한 배정 읽기는 기존 건물을 유지하고 오류를 표시하며 recipient refresh를 호출하지 않는다.
- 취소 후 새 빈 결과가 전달되는 것, 기존 반환 기록/카드 범위 시험 유지.
- Chromium PC 1365px / 모바일 390px에서 user/leader/admin 총 6조합을 전후 검사했다.
  표시 내용과 검사 결과가 완전히 일치했다. 식당 목록 열기/닫기, 배정 지도/돌아오기,
  홈 왕복, 실제 관리자의 구역 관리 화면을 확인했다. 신청·일정·배정·방문 기록 쓰기는 하지 않았다.
- 해당 demo actor에는 지난 배정이 없어 실제 화면의 지난 봉사 달력 검사는 생략했다.
  과거/미래/다른 팀 자료 보존은 자동 읽기 시험으로 확인했다.

## 측정 계약

같은 데모 DB, Chromium 390×844, REST 요청 시작마다 120ms 추가 지연, 역할별 3회.
첫 화면 표시(`readyMs`)와 이 전환에서 시작된 모든 데이터 응답 본문 수신 완료
(`dataReadyMs`)를 구분한다. 후자는 화면 자체가 그 시간까지 막힌다는 뜻이 아니다.
기존 요청 완료 뒤 600ms 안정 구간으로 경계를 나누며, 30초 내 안정되지 않으면 실패한다.

측정 파일: `scratch/speed-myservice-before-final.json`,
`scratch/speed-myservice-reuse-final.json`. 실제 관리자 구역 경로는 별도 1회 비교한다.
화면 기록: `scratch/myservice-{before,after}-ui.json` 및 역할/크기별 이미지.

| 역할/경로 | 요청 전→후 | 첫 화면 전→후 | 전체 데이터 응답 완료 전→후 |
| --- | --- | --- | --- |
| 봉사자 나의 봉사 첫 진입 | 22→19 | 628→628ms | 2,385→1,996ms |
| 인도자 나의 봉사 첫 진입 | 14→14 | 647→630ms | 854→837ms |
| 봉사자/인도자 나의 봉사 재진입 | 0→0 | 약 45~48ms | 추가 응답 없음 |
| 실제 관리자 구역 첫 진입 (각 1회) | 11→11 | 598→649ms | 807→841ms |
| 실제 관리자 지도 첫 진입 (각 1회) | 9→9 | 633→634ms | 1,173→1,115ms |
| 실제 관리자 지도 재진입 (각 1회) | 2→2 | 별도 기록 참조 | 변경 신호 확인 유지 |

봉사자 원문 응답량 중앙값은 14,114→12,679B다. 제거된 3건은 개인 배정,
배정 연결 카드, 해당 일정의 중복 조회다. 첫 화면이 빨라졌다고 주장하지 않는다.
인도자/관리자는 변경 대상이 아니며 작은 시간 차이는 개선 효과로 해석하지 않는다.
실제 아이폰/운영 규모/동시 접속의 속도를 이 수치로 보장하지 않는다.

자료 응답 완료 시점 추가 전 측정도 따로 보존했다. 최종 표는 해당 필드를 추가하고
전후를 다시 잰 기록만 사용한다. 폐기 시안의 18건/13건 수치는 최종 앱 결과가 아니다.

## 운영 상태

운영 DB/환경변수/main/운영 배포는 변경하지 않는다.
운영 적용은 이 작은 변경과 실제 역할별 결과를 다시 리뷰한 뒤 별도로 결정한다.
