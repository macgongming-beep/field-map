# 건물 페이지 동시 읽기 (기기별 건물 수 기억)

- 날짜: 2026-11-23
- 번호: 처음 0160으로 작성했으나 0161로 옮겼다(0159 중복 정리).
- 작성: Claude. 브랜치 `claude/perf-review-nov23`.
- 상태: 데모 반영 대상. 운영 미적용.
- 기준: `a91702f` (0160까지).
- 범위: `useStore`의 건물 전체 읽기(모든 모드: 전체·지도·구역·캘린더 열). SQL, 권한, 설정, 열 구성 변경 없음.

## 원인

인도자 나의 봉사 첫 진입을 지연 대조 실험으로 확인했다(47배 확대 자료).

| 늦춘 응답 (1.5초) | 첫 표시 지연 |
|---|---|
| 건물 | +3.0초 |
| 방문 기록 | +1.5초 |
| 카드 | +1.2초 |
| 나의 봉사 일정 | +1.1초 |
| 카드 요약 | 변화 없음 |

- 건물이 +3.0초인 것은 1,000행 페이지를 앞 페이지 응답 뒤에 차례로 요청하기 때문이다.
- 운영 건물 1,271개는 2페이지, 47배 자료 2,115개는 3페이지다.
- 방문 기록은 세대 ID로 범위를 정하므로 건물을 다 받은 뒤에 시작한다. 이번 범위가 아니다.

### 처음 시도를 버린 이유

첫 페이지에서 전체 개수를 받아 나머지를 동시에 받는 방식을 먼저 시도했다.

- 2페이지짜리(운영)에서는 2페이지가 여전히 1페이지 응답 뒤에 시작하므로 이득이 없다.
- 측정 도구도 47배 자료를 한 응답에 몰아 넣고 있어, 실제 페이지 동작을 재현하지 못했다.
- 그래서 측정 도구를 실제 PostgREST처럼 1,000행 단위로 잘라 응답하도록 고치고, 그 변경은 되돌렸다.

## 결정

- 마지막으로 읽은 건물 수를 기기(`localStorage`, 키 `fieldmap:buildingTotal`)에 기억한다.
  - 값은 건물 수 숫자 하나다. 개인 정보가 아니다.
- 기억값이 1,000을 넘으면, 필요한 페이지를 첫 페이지와 동시에 요청한다. 단, 기억값으로 미리 시작하는 페이지는 최대 3개다.
  - 운영 1,271개 → 0·1000 두 페이지를 함께 요청한다. 요청 수는 이전과 같다.
- 기억값이 없거나 1,000 이하면, 첫 페이지를 혼자 읽는다.
  - 이때 첫 페이지에서 전체 개수(`count=exact`)를 받는다.
  - 개수가 더 많으면 남은 페이지를 한 번에 최대 4개씩 나눠 요청한다.
- 안전장치는 다음과 같다.
  - **기억값이 작을 때**: 첫 페이지가 알려 준 개수까지 모두 읽는다.
  - **그 사이 추가됐거나 개수를 받지 못했을 때**: 마지막 페이지가 꽉 차 있으면 이전처럼 짧은 페이지가 나올 때까지 이어 읽는다.
  - **겹친 행**: 페이지 사이에 행이 밀려 같은 건물이 두 번 오면 하나만 남긴다. 이전 직렬 읽기에도 있던 경우다.
  - **누락은 막지 못한다**: 페이지를 읽는 사이에 앞쪽 건물이 삭제되면, 다음 건물이 페이지 경계 너머로 밀려 오류 없이 빠질 수 있다.
    - 오프셋 페이지가 스냅샷이 아니기 때문이며, 이전 직렬 읽기와 같은 기존 한계다.
    - 중복 제거는 누락을 복구하지 못한다. 시험에 '알려진 한계'로 고정했다(Codex 재현).
  - **실패**: 동시 요청은 모두 끝난 뒤에만 실패를 던진다.
  - **저장소를 못 쓸 때**: 저장소가 막혀 있으면 직렬 읽기로 동작한다.
- 비용
  - **기억값이 실제보다 클 때**: 빈 페이지 요청이 최대 2건 늘어난다. 그 직후 기억값이 갱신된다.
    - Codex 리뷰 전 판(`f8678f6`)에는 상한이 없었다. 기억값 10,001·실제 45에서 11건을 동시에 요청했다.
    - 따라서 처음 쓴 '빈 페이지 1건'은 일반적인 상한이 아니었다. 상한을 둬 보완했다.
  - **DB 작업량**: 첫 페이지의 `count=exact`는 DB가 행 수를 새로 센다. HTTP 요청 수가 같아도 DB 작업량이 같다는 뜻은 아니다.
    - 운영 규모(건물 1,271개)에서의 비용은 측정하지 않았다.

## 시험

- `src/hooks/useStore.buildingPages.test.tsx`에 시험 9개를 추가했다. 보완 후 3개를 더해 12개다.
  - 보완 시험: 큰 기억값은 최대 3페이지로 제한, 많은 페이지는 동시 4개 이하로 나눠 읽음, 삭제에 따른 누락(알려진 한계)
  - 기억값 없음: 첫 페이지 단독 읽기, 개수 기반 나머지 동시 읽기, 기억값 저장
  - 1,271개 기억값: 0·1000 동시 시작, 요청 2건
  - 1페이지 기억값: 직렬 1건
  - 큰 기억값: 빈 페이지 1건 뒤 기억값 축소
  - 작은 기억값: 개수까지 모두 읽음
  - 개수 없음: 직렬 이어 읽기
  - 중복 행: 하나만 남김
  - 동시 실패: 전부 끝난 뒤 실패
  - 저장소 차단: 직렬로 동작
- 변이 7개 중 의미 있는 6개를 검출했다.
  - 검출: 기억값 무시, 개수 기반 동시 읽기 제거, 이어 읽기 제거, 중복 제거 제거, `Promise.all`, 기억값 저장 제거
  - `hint >= 1` 변이는 결과가 같은 등가 변이다.
- 전체 295파일 2,995개 시험, TypeScript, lint 통과.
- 보완 변이 7개를 모두 검출했다.
  - 기억값 상한 제거, 4개 단위 제거, 개수 기반 읽기 제거, 기억값 무시
