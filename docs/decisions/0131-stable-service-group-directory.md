# 집단 관리와 봉사 일정의 이름·추가 연동

- 상태: [0133](0133-expanded-meeting-info-production-release.md)에서 운영 적용 완료
- 결정일: 2026-11-18
- 이전 결정: [0130](0130-saved-service-labels-and-compact-calendar.md)의 고정 4개 집단 이름 매칭을 대체한다. 저장 제목 표시·PC 달력 밀도 변경은 유지한다.

## 문제와 결정

사용자 관리의 `app_settings.user_groups`와 봉사 일정의 `service_groups`가 별도 목록이었다.
네 집단의 번역만 맞추면 임의 이름 변경과 새 집단 추가는 연결되지 않는다.

`service_groups.code`를 영구 식별자로 유지하고 관리자가 정한 `display_name`을 그대로 표시한다.
언어 설정은 버튼·안내 문구에만 적용하고, 저장한 집단명이나 일정 제목을 번역하지 않는다.
사용자 관리의 기존 집단 관리 화면에서 추가·이름 변경·삭제를 처리한다.

## 데이터 계약

- `manage_service_group_tx` 하나로 집단 목록과 소속 성원의 이름을 함께 저장한다.
- 이름 변경은 같은 code를 유지한다. 기존 일정의 `target_groups`, 신청자, 배정은 바꾸지 않는다.
- 기존 사용자 필드는 `group_name`을 유지한다. 원자적 이름 변경과 소속 입력 검증으로 서버의 기존 집단 조회 권한 조건과 일치시킨다.
- 새 집단에는 새 code를 발급한다. 고정 네 개 제한을 없애고 활성 집단 최대 20개, 이름 12자로 제한한다.
- 새 집단 추가는 일정 추가의 선택 목록에 반영된다. **기존 날짜의 일정을 자동 생성하거나 다른 집단 신청을 옮기지 않는다.** 일정이 등록된 집단만 그 시간의 상세 탭에 나타난다.
- 삭제는 비활성화다. 성원 소속은 미지정으로 바꾸지만 기존 일정·신청·배정 기록과 집단 이름은 남긴다. 지난 일정에서는 비활성 집단 탭도 볼 수 있다.
- 비활성 집단을 새 일정에 지정할 수 없다. 같은 집단이 이미 지정된 기존 일정의 다른 내용은 수정할 수 있다.
- 비활성 집단의 이름은 중복 사용하지 않는다. 복원·집단 병합 기능은 이번 범위가 아니다.
- 신청, 팀 편성, 구역 배정, 공유, 댓글의 `event_id` 및 기존 역할별 권한은 변경하지 않는다.

## 권한과 동시 수정

- 승인·활성 관리자/개발자만 집단 관리 RPC를 실행한다. 인도자에게 집단 관리 권한을 추가하지 않는다.
- 관리 화면이 읽은 목록 revision을 서버에서 비교한다. 다른 관리자가 먼저 수정하면 덮어쓰지 않고 재확인을 요구한다.
- 집단 관리와 새로운 사용자 소속 지정은 같은 트랜잭션 잠금을 사용한다.
- 다른 집단의 code/기존 언어별 라벨/표시 이름과 충돌하는 이름은 거부한다.
- 내부 publish/guard 함수의 직접 실행 권한은 회수한다. 기존 service_groups 직접 쓰기 금지도 유지한다.
- 설치 후 `user_groups` 또는 `service_group_directory`를 직접 수정·삭제할 수 없다. 목록과 실제 소속이 따로 저장되는 우회 경로를 차단한다.

## 조회와 갱신

기존 `app_settings` 조회에 `service_group_directory` JSON을 함께 담는다. 초기 로딩에 별도 집단 조회나 새 구독·주기적 조회를 추가하지 않는다.
사용자 관리 화면은 기존 한 번의 설정 조회에서 두 key를 읽는다. 관리 RPC는 최신 목록을 반환하고 같은 앱에 전달한다. 사용자 목록 갱신은 기존 `app-users-changed` 경로를 쓴다.
늦은 설정 응답이 최신 이름을 되돌리지 않도록 revision을 비교한다.

**다른 기기의 즉시 갱신을 보장하지 않는다.** 다른 기기는 기존 데이터 새로고침/다시 열기에서 최신 목록을 받는다.
이름/추가가 저장되기 전에 목록을 낙관적으로 바꾸지 않으며, 실패하면 입력을 남긴다.
목록 JSON만큼 응답 바이트는 소폭 증가한다. 이번 변경의 전후 통신량 실측은 하지 않았으며, 요청·전송량이 완전히 같다고 주장하지 않는다.

## 설치 순서와 복구

1. 대상이 데모인지 확인하고 public/private 백업을 만든다.
2. `20261118_2300_service_group_directory.sql`을 단일 트랜잭션으로 적용한다.
3. 새 앱을 데모에 배포한다.
4. 실DB 검증과 화면 확인 후 운영 여부는 별도로 결정한다.

DB 설치 후 구버전 앱의 집단 관리 직접 저장은 오류로 막힌다. **운영에서는 DB와 앱 전환 시간을 함께 정하고, 구버전 관리자에게 업데이트를 안내해야 한다.**
신청/배정 RPC는 이번 마이그레이션에서 교체하지 않는다.
새 앱을 옛 앱으로 되돌리는 것만으로 집단 관리가 복구되지는 않는다. 새 집단/이름 변경이 생긴 DB에서 열을 삭제하거나 임의 역변환하지 말고, 관리 화면 업데이트로 복구한다.
다른 운영 쓰기를 통째로 되돌리는 백업 복원은 자동 실행하지 않는다.

## 구현과 검증

- 집단 SQL: 초기 기존 언어 혼용, 임의 이름 변경, 빈 집단 변경, 다섯 번째 집단, 비활성화 후 이력 보존, 관리자 권한, 같은 집단 명단 접근, 이름 충돌, 오래된 revision 차단.
- 화면: 임의 code/이름, 새 집단별 독립 일정 생성, 자기 집단 선택, 비활성 과거 탭, 변경 후 선택 유지, 빈 집단 저장, 실패 입력 보존.
- 늦은 설정 응답 차단, 실패/다른 로그인 세션 응답의 화면 갱신 금지, 성공 결과 로컬 전달 시험.
- SQL 변이: revision 비교 제거, 소속 변경 제거, 인도자 관리 허용을 각각 넣으면 해당 시험이 실패한다. 원본 파일이나 DB를 변이하지 않고 시험 입력 문자열만 바꾼다.
- 최종 전체 시험: 273개 파일, 2,663개 통과. `git diff --check` 통과.
- lint, TypeScript 포함 데모 빌드 통과.
