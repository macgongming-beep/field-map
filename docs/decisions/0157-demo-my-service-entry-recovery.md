# 나의 봉사 첫 진입 조회 분석과 복구 대기 단축

- 날짜: 2026-11-22
- 상태: 데모 검증 중. 운영 미적용.
- 기준: `7cc77e1`, 실제 앱 소스 `7d9f703`. 0156과 같은 데모 기능 설정.

## 분석

- 모바일 나의 봉사는 `/territory`의 `MobileTerritory`, PC는 `DesktopMyService`다.
  관리자는 모바일에서 구역으로 이동하므로 별도 나의 봉사 최적화 대상이 아니다.
- 봉사자는 날짜 제한 없는 본인 배정과 오늘 일정/식당 배정 일정의 작은 색인을 읽고,
  해당 일정과 공유 팀 배정을 읽는다. 이어서 개인 구역 범위를 새로 확인한다.
  이 존재/범위 확인을 생략하거나 홈의 제한된 일정으로 대신하지 않는다.
- 개인 구역이 같으면 전체 건물을 다시 받지 않고 동기화 시각, 변경 신호, 건물 ID
  목록을 대조한다. 그 뒤 경계선, 카드, 합계를 읽는다. 0156의 관측에서는 봉사자
  첫 진입 18건이었으며 화면은 먼저 뜨고 나머지 확인이 뒤에서 끝났다.
- 인도자는 이 개인 범위 읽기를 사용하지 않는다. 첫 진입에 전체 건물/세대 상세와
  방문 이력을 읽는 별도 경로다. 모바일의 정기방문 세대 메모, 주소/좌표 비교, 식당
  봉사 이력 등 실제 소비자가 있으므로 이번에 단순히 이름만 남기지 않는다.
  세대 메모 등 상세를 열 때 읽는 변경은 화면별 완전성 보호를 설계한 별도 작업으로 남긴다.

## 이번 변경

1. 기준 시각을 먼저 확보한 뒤, 같은 카드 범위의 변경 신호와 건물 ID 목록을 동시에
   읽는다. 100개 카드 단위와 각 조회의 페이지 순서는 유지한다. 양쪽이 끝나고 범위
   검사를 통과하기 전에는 건물 동기화나 기준 시각 갱신을 하지 않는다.
2. 현재 작업에서 새로 확인한 구역 범위로 경계선을 읽는 것은 건물 변경 동기화와
   서로 의존하지 않는다. 두 작업을 함께 시작하되, 둘 다 성공해야 경계선을 반영하고
   카드/합계 단계로 간다. 실패하면 다른 작업도 끝난 뒤 기존 개인 범위 전체 복구로 간다.

공통 개인 구역 복구 경로이므로 나의 봉사 첫 진입뿐 아니라 기존 캘린더 이동,
앱 복귀/실시간 복구에도 적용된다. 초기 전체 로딩, 수동 전체 새로고침, 변경 후 저장
경로의 읽기 선택은 그대로다. SQL/RLS/권한/배정·방문 저장/지도 줌/GPS를 바꾸지 않는다.

## 사용량 경계

- 정상 성공 시 요청 종류/조건/페이지/응답 내용은 동일하고 시작 시점만 달라진다.
- 실패 시 이미 시작한 다른 조회를 취소하지 않고 끝까지 기다린다. 예전 직렬 경로라면
  시작하지 않았을 조회가 한 묶음 안에서 추가로 완료될 수 있다. 무조건 모든 실패에서
  사용량이 같다고 주장하지 않는다. 실패한 작업과 복구 작업이 겹치지 않게 한다.
- 카드 범위 변화/배정 취소/삭제/개인 세션 변화 시 기존 전체 개인 범위 재조회로
  돌아가는 조건과 30분 이력 안전 조회는 유지한다. 데이터 신선도를 낮추지 않는다.

## 검증

- 관련 2파일 300개 시험 통과. 기준 시각 전 조회 금지, 서로 독립적인 두 조회의
  동시 시작, 양쪽 완료 전 반영 금지, 양방향 실패/대기/복구를 직접 확인한다.
- 분리 복사본의 변이 6개 모두 검출: 색인 직렬화(1개), 색인 실패 조기 반환(2),
  색인 오류 무시(2), 경계선 직렬화(1), 경계선 실패 조기 반환(2), 경계선 오류 무시(2).
- 전체 294파일 2,966개 시험, TypeScript와 lint 통과.
- 변경 전후 비교와 데모 배포 결과는 아래에 추가한다. 원본은
  `scratch/service-entry-nov22/`, 도구는 `scratch/measure-service-entry-nov22.mjs`다.

## 전후 측정

동일한 데모 설정/DB로 전후를 번갈아 3쌍 측정했다. Chromium 390×844, CPU 4배,
REST 요청마다 120ms 지연, 앱 파일 로컬 제공, 서비스워커 OFF다. 다른 시험/빌드는
측정과 겹치지 않았다. 진행 중 요청을 추적하고 마지막 완료 뒤 800ms 동안 조용해야
다음 구간으로 넘어간다. 30초 안에 끝나지 않으면 실패한다. 업무 쓰기는 차단했고,
로그인/세션 확인에 따른 데모 세션·접속 기록 외에 DB 변경은 하지 않았다.

| 항목 | 변경 전 3회 | 변경 후 3회 |
| --- | --- | --- |
| 봉사자 첫 화면 표시(ms) | 656 / 622 / 653 | 795 / 634 / 666 |
| 봉사자 전체 조회 완료(ms) | 1,985 / 1,943 / 1,968 | 1,752 / 1,724 / 1,595 |
| 봉사자 요청 / 응답 원문 | 매번 18건 / 6,194B | 매번 18건 / 6,194B |
| 인도자 첫 화면 표시(ms) | 649 / 636 / 726 | 650 / 650 / 641 |
| 인도자 전체 조회 완료(ms) | 838 / 832 / 932 | 861 / 827 / 905 |
| 인도자 요청 / 응답 원문 | 매번 10건 / 39,200B | 10건 / 39,198~39,200B |

- 봉사자 전체 조회 완료 중앙값 1,968→1,724ms(244ms, 약 12% 감소). 첫 표시
  중앙값은 653→666ms여서 **첫 화면 표시 개선이라고 주장하지 않는다**. 현재 첫 표시
  이전의 일정 색인→일정→팀 배정 단계는 이번에 그대로다.
- 인도자는 읽기 경로가 달라 개선 대상이 아니며, 수치 변화는 실행 편차로 해석한다.
- 화면 글자 전체의 해시는 역할별 전후 6회 모두 동일했다. 캡처도 육안 확인했다.
  홈으로 돌아갔다가 나의 봉사 재진입은 모두 DB 요청 0건, 42~59ms였다.
- 전후 홈 읽기는 봉사자 37건, 인도자 24건으로 동일했다. 앱 파일 요청 수도 동일했다.
  코드 증가로 앱 초기 원문 합계는 283B 늘었다. 응답량은 압축 전이며 과금량이 아니다.
- 데모 시험 봉사자는 과거 배정 1건, 해당 카드에 건물이 없는 상태다. 실제 다수 건물의
  변경분 동기화 속도, 운영 규모/동시 접속/실물 아이폰/하루 사용량은 측정하지 않았다.
  건물 추가·변경·삭제, 범위 변경·회수와 실패 복구는 기존/새 자동 시험으로 확인했다.
- WebKit 390px, CPU/REST 추가 지연 없는 전후 1쌍도 화면 글자와 요청 18건이 같았다.
  첫 표시 311→408ms, 전체 완료 775→853ms로 느린 실행이었다. 바꾸지 않은 앞단의
  범위 확인 완료부터 392→535ms로 늦었다. 해당 이후 완료는 383→318ms지만,
  한 쌍으로 전체 성능 개선이나 실물 아이폰 효과를 주장하지 않는다. 재진입은 0건이다.

## 다음 병목

- 첫 표시를 앞당기려면 일정 색인/일정/공유 배정 읽기를 별도로 분석해야 한다.
  오늘 밖 배정, 삭제된 일정, 같은 팀 공유 조회를 유지해야 하므로 이번에는 재사용
  기간을 늘리거나 존재 확인을 생략하지 않았다.
- 인도자의 건물 상세는 식당·재방문 기능의 의존 자료를 분리한 뒤 미룰 수 있다.
  현재 자료를 이름만 있는 건물로 대체하면 세대 메모 등 기존 기능이 빠진다.
