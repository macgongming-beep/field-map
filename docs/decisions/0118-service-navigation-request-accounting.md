# 나의 봉사 요청 증가 재검증과 측정 구간 정정

- 결정일: 2026-11-18
- 상태: 데모 검증. 운영 변경 없음.
- 대상: `cbb9c19` + `16289ee`의 나의 봉사 14→16건 기록.

## 결론

실제 조회 증가가 아니라 측정 구간 오류다. 안정화한 동일 조건에서 최적화 이전과
이후 모두 인도자의 나의 봉사 첫 진입은 14건, 재진입은 0건이다(각 3회).
이 두 요청을 없애려고 앱의 읽기·알림 갱신을 변경하지 않는다.
이번 변경은 측정 도구, 회귀 시험, 문서뿐이며 `useStore.ts`의 최종 변경은 없다.

## 원인

옛 도구는 `request.timing().startTime`을 기준으로 요청을 화면에 배분하고,
`networkidle` + 100ms만으로 앞뒤 요청이 끝났다고 판단했다.
인위적인 120ms 지연과 React의 뒤늦은 효과 실행, 응답 본문 측정이 이 경계를 넘었다.

- 16건에는 직전 홈에서 발생한 `service_suggestions`와 알림함 조회가 섞였다.
- 옛 14건 중에는 이 직전 요청을 포함하면서, 나의 봉사 준비 뒤의 점검 공지와
  알림함 조회를 아직 집계하지 않은 것도 있었다. 따라서 단순히 16에서 2를 빼는
  보정이 아니라 전후 전체를 다시 측정했다.
- 실제 화면 추적에서는 로딩 중 헤더가 사라졌다가 자료 준비 후 한 번 복귀했다.
  나의 봉사 자료가 같은 화면에서 두 번 로드된 증거는 없었다.

## 새 측정 방식

`scripts/measureServiceNavigationDemo.mjs`:

1. Playwright의 `request` 이벤트에서 단조 시계로 시작을 기록한다. 지연을 넣은 뒤의
   네트워크 시작 시각은 화면 분류에 사용하지 않는다.
2. 모든 진행 중 요청과 응답 본문 읽기를 추적한다. 각 안정화 진입 시점부터 최소
   600ms, 마지막 요청 완료 후에도 600ms의 조용한 구간을 기다린다.
3. 전환 전 요청이 모두 끝난 뒤 클릭하고, 전환 후 부가 요청까지 끝나야 집계를 닫는다.
   30초 안에 안정화하지 못하면 실패하며 부분 집계를 성공으로 기록하지 않는다.
4. 화면 준비 시간은 클릭부터 준비된 내용의 다음 프레임까지로, 위 안정화 시간은
   포함하지 않는다. 응답량은 원문 바이트이며 압축 전송량/소켓 비용은 아니다.
5. 접속은 로컬 미리보기 또는 데모 주소와 데모 Supabase만 허용한다.
   로그인과 앱의 기존 자동 세션 정리는 데모에만 발생할 수 있다.
   일정·신청·배정·댓글을 저장하는 시험 동작은 없다.

## 재측정

동일 데모 DB·설정, Chromium 390×844, 요청별 120ms 지연, 각 계정/버전 3회.
이전 빌드는 `cbb9c19`의 `useStore.ts` 변경만 정확히 되돌려 만들고 즉시 복원했다.
최종 작업본에서 앱 소스가 기존 HEAD와 같은지 다시 확인했다.

| 계정/화면 | 이전 요청 수(3회) | 이후 요청 수(3회) | 이전→이후 원문 바이트 중앙값 |
| --- | --- | --- | --- |
| 인도자 상세 첫 진입 | 11 / 11 / 11 | 6 / 6 / 6 | 20,208→11,308 |
| 인도자 상세 재진입 | 2 / 2 / 2 | 2 / 2 / 2 | 448→448 |
| 인도자 나의 봉사 첫 진입 | 14 / 14 / 14 | 14 / 14 / 14 | 46,937→46,937 |
| 인도자 나의 봉사 재진입 | 0 / 0 / 0 | 0 / 0 / 0 | 0→0 |
| 일반 성원 상세 첫 진입 | 2 / 2 / 2 | 2 / 2 / 2 | 455→455 |
| 일반 성원 나의 봉사 첫 진입 | 22 / 22 / 22 | 22 / 22 / 22 | 14,140→14,140 |
| 일반 성원 나의 봉사 재진입 | 0 / 0 / 0 | 0 / 0 / 0 | 0→0 |

일반 성원은 기존 제한 자료 조회 경로를 사용하므로 요청 수는 더 많아도 자료량은 작다.
이번 시험은 수 증가 여부에 대한 검증이다. 같은 실행에서 시간도 기록하지만,
다른 검증 작업과 일부 겹쳤으므로 새 속도 개선 수치로 주장하지 않는다.

인도자 14건의 구성:

- 자료 12건: 동기화 시점 1, 일정 ID/상세 2, 배정 ID/상세 2, 식당 배정 ID 1,
  건물 1, 지역 1, 카드 1, 방문 기록 1, 봉사 세션 1, 배정 카드 1.
- 부가 2건: 준비 후 헤더의 알림함 1, 점검 공지 1.

같은 표를 두 번 읽는 일정/배정 요청은 ID 범위 결정과 상세 자료 조회가 다르다.
이유 없이 중복으로 간주해 삭제하지 않았다. 알림과 점검 공지의 기존 새로 읽기도
그대로 유지한다. 구조적으로 더 줄이는 개선은 별도 범위로 다룬다.

## 회귀 검증

- 홈 첫 로딩이 실패하면 상세로 이동해도 이름만 읽는 최적화에 진입하지 않는다.
  오류와 차단 상태가 유지되고, 전체 재시도가 성공해야 카드 집계와 세션이 준비된다.
- `loadedOnceRef` 검사를 일부러 제거하면 이 새 시험이 실패했다. 원래 코드를 복원했다.
- 전체 2,547개 시험(262개 파일), lint, 데모 설정 빌드 통과.
- 일반 성원의 나의 봉사에 공유 배정/카드/지도 버튼이 유지되는 화면 확인.
- 배포된 데모에서도 Mac WebKit으로 인도자·일반 성원 각 1회 확인했다.
  인도자 첫 진입 14건/재진입 0건, 일반 성원 첫 진입 22건/재진입 0건으로 일치했다.
  실패한 데이터 요청·브라우저 오류·가로 넘침 없음. 실제 아이폰 측정은 아니다.
  기록: `scratch/speed-settled-live-webkit.json`.
- DB·권한·신청·배정·알림 로직 변경 없음. 운영 DB/환경변수/배포/main 변경 없음.
- 앱 실행 코드가 같으므로 이 측정 정정을 위한 별도 앱 배포는 하지 않는다.

## 재현 및 리뷰

환경변수 `TEST_ENV_FILE`은 데모 인증 정보 파일, `FIXTURE_FILE`은 데모 actor 명단,
`PLAYWRIGHT_MODULE`은 설치된 Playwright 모듈 경로다. 비밀은 출력/커밋하지 않는다.
`PREVIEW_URL`, `REST_DELAY`, `REPEATS`, `ROLES`, `ENGINE`으로 실행 조건을 지정한다.

```sh
ROLES=leader,user REPEATS=3 REST_DELAY=120 node scripts/measureServiceNavigationDemo.mjs comparison
```

로컬 원본: `scratch/speed-settled-before-delayed.json`,
`scratch/speed-settled-after-delayed.json`; 화면별 시작 시점·쿼리·바이트·헤더 변경 추적 포함.
재현에는 로그인 가능한 데모 계정과 오늘의 집단 일정 fixture가 필요하다.
