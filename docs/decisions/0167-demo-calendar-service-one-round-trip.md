## 원인 귀속 (직접 실행)

도구 `perf-wait.mjs`는 매 프레임 다음을 기록한다: 주소, 보이는 `role=status`/`.app-loading` 문구, 화면 표식(홈·캘린더·나의 봉사·상세·시트·지도), 달 제목.
단계마다 다음을 따로 계산한다.
- 주소 변경
- 이전 화면이 마지막으로 보인 시각
- 새 화면 틀
- 대기 표시 시간
- 사용 가능: 목표 화면이 있고 대기 표시가 없는 상태가 끝까지 유지된 시작 시각
- 전체 응답 완료: 단계 시작 뒤 시작한 요청의 마지막 완료

단계마다 앞 요청이 끝나기(800ms 조용함)를 기다린 뒤 시작한다.

- 캘린더(모든 역할)의 대기는 '일정 → 그 일정들의 팀 배정' 직렬 2회 왕복이다(`CalendarReadGate`).
- 봉사자 나의 봉사의 대기는 '색인 3개 → 본문·팀' 2회 왕복이다(`RouteReadGate`의 `needsCalendar`).
- 인도자 나의 봉사는 기준 시각(`territory_sync_clock`) → 건물·카드 → 세션·방문 기록 3회 왕복이다(`routeNeedsBuildings`).
  - 기준 시각은 읽기 전에 잡아야 변경을 놓치지 않는다(0162에서 유지).
  - 방문 기록은 건물 결과에 의존한다.
  - **바꾸지 않았다.**
- 달 이동: 요청 0건인데도 대기 문구가 한 프레임(17~19ms) 그려졌다.
  - 원인: `CalendarReadGate`가 새 달을 `useEffect`로 알려, 그 사이 '달이 다르다'로 판단했다.
- 일정 상세의 '불러오는 중…'(약 150ms)은 상세 자체의 요청 3건(댓글·모임 접근·인도자 연락처)이다. 바꾸지 않았다.
- 빠른 탭 전환 뒤 홈의 대기(약 134ms)는 버려진 서비스 읽기를 기다리는 것으로 보인다. **원인 확정 안 함, 바꾸지 않았다.**

## 결정

1. **창 범위(홈·월) 일정 읽기**: `event_card_assignments(*)`, `event_card_assignment_cards(*)`를 일정 조회에 끼워 받는다(둘 다 `event_id` 외래키). 요청 2건과 왕복 1회가 줄어든다.
2. **봉사자 서비스 읽기**: 색인 → 본문 대신 일정 조회 4개를 동시에 보낸다. 각 조회가 본문과 전체 팀을 함께 받는다.
   - 오늘: `event_date=eq.<오늘>`
   - 본인: `mine:event_card_assignments!inner(user_name)` + `mine.user_name=eq.<나>`. 별칭 조인이라 끼워 받은 팀은 전체가 남는다.
   - 식당(0164 유지): `restaurant:event_restaurant_assignments!inner(event_id)` + `event_date=gte.<오늘>`
   - 대상: `id=eq.<대상>`
3. **검증(전부 실패 시 '완전한 자료'로 쓰지 않음)**
   - 오늘 행 날짜, 본인 별칭이 비었거나 남의 것, 식당 행 날짜·별칭 불일치, 대상 불일치는 거부한다.
   - 끼워 받은 배열이 없거나, 그 안의 행이 다른 일정 것이면 거부한다.
   - 끼워 받은 배열이 1,000행(페이지 한도)이면 서버가 잘랐을 수 있으므로 예전 표별 페이지 읽기로 다시 읽는다.
   - 실패는 형제 조회가 모두 끝난 뒤 알린다(`settleAll`, 재시도 겹침 방지).
4. **`CalendarReadGate`**: 새 달을 `useLayoutEffect`로 그리기 전에 알린다. 아직 받지 않은 달은 그대로 대기 문구를 보인다. 문구를 숨기거나 최소 표시 시간을 넣지 않았다.

### 늘어나는 조건 (한계)

- **빈 배열**: 팀 배정이 없는 일정마다 `"event_card_assignments":[],"event_card_assignment_cards":[]`(58B)가 붙는다. 월 35개 일정에서 +2.3KB(+7%)였다.
- **같은 일정의 반복 수신 (나의 봉사, 가장 큰 한계)**
  - 같은 일정이 오늘·본인·식당·대상 조회에 겹치면, 겹친 조회마다 본문과 전체 팀을 다시 받는다.
  - 데모의 실제 일정(팀 4행, 끼워 받은 한 행 3,265B)으로 잰 결과(`demo-dup-cost.mjs`):

| 겹침 | 옛 방식 | 새 방식 | 차이 | 출처 |
|---|---|---|---|---|
| 오늘만 | 3,338 B | 3,265 B | −73 B | 실제 응답 |
| 본인만 | 3,343 B | 3,301 B | −42 B | 실제 응답 |
| 오늘 + 본인 | 3,378 B | 6,566 B | **+3,188 B** | 실제 응답 |
| 오늘 + 본인 + 식당(식당 1행) | 3,439 B | 9,862 B | +6,423 B | 식당 부분 합성 |
| 오늘 + 본인 + 식당(10행) + 대상 | 3,988 B | 13,271 B | +9,283 B | 식당 부분 합성 |

  - 일정 하나당 중복량은 대략 '(겹친 조회 수 − 1) × 끼워 받은 행 크기'다. 행 크기는 참가자와 팀 수에 비례한다.
  - **'오늘 + 본인'은 배정받은 봉사자라면 봉사 있는 날마다 생긴다.** 배정 지도(대상)로 들어가면 3중이 된다.
  - 데모 측정에는 오늘 배정이 없어 이 비용이 드러나지 않았다. 운영 효과로 부르지 않는다.
- **줄일 수 있는 후보 (구현 안 함, 검토용)**
  - 본인 조회에 `event_date=neq.<오늘>`을 붙이고, 식당 조회를 `gt.<오늘>`로 바꾸면 오늘과의 겹침이 없어진다.
  - 대상이 다른 조회에 이미 있으면 중복이 남는다.
- **1,000행 되돌림**: 끼워 받은 배열이 1,000행일 때만 표별 페이지 읽기가 추가된다(데모·운영 일정에서는 일어나지 않을 규모).
- **실패 시**: 형제 조회가 모두 끝난 뒤 실패를 알린다. 서비스 읽기는 예전에 색인이 실패하면 본문을 시작하지 않았는데, 이제는 4개가 함께 끝까지 진행된 뒤 버려진다(최대 4건).
- 압축 후 전송량, 조인에 따른 DB 작업, 과금은 재지 않았다.
