# 집단 봉사 전환 보완과 단계별 리허설

- 상태: 데모 적용·격리 전환 검증. 운영 미적용.
- 결정일: 2026-11-17
- 선행 점검: [0104](0104-group-service-release-preflight.md)
- 사용자 범위: 확인된 세 문제 보완과 전환 순서 시험. 운영 변경 금지 유지.

## 바뀐 계약

1. 전시대 표가 없어도 일반 봉사·재방 연구·대신 신청과 일정 알림이 동작한다. 전시대 표를 새로 만드는 부수 효과는 없다. 표가 있으면 같은 일정의 전시대 중복 검사는 그대로 유지한다.
2. 집단 탭 표시와 배정 저장 전환을 분리한다. `VITE_ASSIGNMENT_REVISION_ENABLED=true`가 새 저장·참가자 관리·배정 권한·리비전 읽기를 켠다. `VITE_GROUP_SERVICE_ENABLED=false`여도 동시 저장 보호는 유지된다. PC·모바일 인도자의 전체 구역 선택과 종료 시간·신청 마감 변경 알림 확인도 새 저장 설정을 따른다. 운영의 기본값은 둘 다 꺼짐이며, 데모 로그인/초기화 기능을 운영에서 켤 필요가 없다.
3. 새 앱의 참가자 제외는 항상 단일 RPC다. 버전 경로에서는 기존 versioned RPC, 호환 경로에서는 팀 RPC 또는 새 generic atomic RPC를 사용한다. 함수가 없거나 권한이 거부되면 직접 표 삭제로 후퇴하지 않는다. 옛 다중 요청 삭제 구현은 제거했다.

## 구현

- `20261117_1600_optional_cart_service_contract.sql`: 비공개 선택적 전시대 조회 함수, 정확히 한 곳씩의 설치 본문 치환, 호환 기간용 원자적 참가자 제외. 알림 대상은 설치된 댓글 함수에서 보존하며 다른 환경의 본문을 복사하지 않는다.
- `20261117_1700_assignment_rollout_control.sql`: 비공개 전환 상태와 운영자 전용 단계 변경 함수. 기존 데모에 적용하면 기본은 `strict`이며 옛 API가 다시 열리지 않는다.
- `scripts/groupServiceRolloutBundle.mjs`: 기존 설치 이력 18개 파일의 해시를 고정하여 준비·엄격 차단·호환 복귀 SQL을 생성한다. 네트워크·로그인·적용 모드가 없는 생성 전용 도구다.
- `scripts/checkGroupRolloutDemo.mjs`: 데모 주소와 DB 사용자·포트를 강제 확인. 적용 전 백업, 설치 후 감사, 전환 시험 및 복구 파일 시험. 운영 주소는 거부한다.
- 함수 목록 감사는 `environment`와 `phase`로 구분한다. 운영 목록에는 데모 reset 함수가 없어야 하고, 호환 단계만 옛 팀 저장 endpoint의 공개 실행권한을 허용한다. 이는 향후 운영 실제 카탈로그 대조가 필요한 후보 목록이지 이번에 운영에서 검증한 결과가 아니다.

## 단계 순서

**준비 DB 적용과 확인 전에는 이 변경을 `main`에 병합하거나 운영 앱으로 배포하지 않는다.** `main` 병합 자체가 Vercel 자동 배포를 시작한다. 기능 설정을 모두 꺼도 새 앱은 `remove_service_participant_compat_tx`를 호출하므로 배포 순서를 대신할 수 없다. 데모 브랜치를 통째로 병합하지 않고 승인된 운영 후보 커밋을 따로 고정한다.

### 0. 운영 승인 전 준비

운영 기준 커밋·설치 함수·기존 권한을 다시 대조하고, 최신 백업과 복구 자료를 준비한다. 운영에 준하는 자료량 성능, 실제 휴대폰 알림, 사용자 앱 업데이트 확인을 완료한다. 이번 작업에서는 운영에 접속하거나 변경하지 않았다.

### 1. 준비 DB 묶음

생성된 `01-prepare.sql` 전체를 **외부 단일 트랜잭션**으로 실행한다. 개별 마이그레이션을 따로 실행하면 중간의 옛 RPC 회수가 노출되므로 금지한다. 도구 생성 결과를 그대로 SQL Editor에 나누어 붙이지 않는다.

- 새 기능·리비전·권한 검사를 설치하되, 커밋 시 최종 상태는 `compatibility`다.
- 옛 RPC 네 개와 호환 참가자 제외는 기존 승인 세션·권한 검사를 거쳐 실행 가능하다. 모든 공개 `PUBLIC` 실행권한을 여는 방식은 아니다.
- 옛 배정 쓰기도 리비전을 올려 새 편집기의 오래된 저장을 거부한다.
- **옛 편집기 자체는 예상 리비전을 보내지 않으므로, 이 기간에는 완전한 동시 저장 보호가 아니다.** 짧은 전환 기간에는 같은 일정을 여러 인도자가 동시에 편집하지 않도록 안내해야 한다.
- 일정 편집은 관리자만이라는 새 권한이 적용된다. 옛 앱의 인도자 화면에 편집 버튼이 남더라도 서버는 거부한다.
- 옛 제외 화면의 자동 세션 삭제 호환은 **원래 그 일정에 이름이 있는 활성 인도자 + `source='assigned'`**만 한시 허용한다. 다른 인도자나 수동 기록의 수정·삭제 권한을 넓히지 않는다. 엄격 단계에서는 이 예외도 사라진다.

### 2. 새 앱 전환

준비 묶음 커밋 후, `0104`의 첫 배포 관문을 통과한 다음에만 운영 후보를 `main`에 반영한다. 확인 명령은 다음과 같으며 이번 작업에서는 운영에 실행하지 않았다. `PREFLIGHT_ENV_FILE`은 검토한 대상 환경 파일 경로이고 비밀값을 명령 인자로 전달하지 않는다.

```bash
node scripts/preflightGroupReleaseReadOnly.mjs production --read-only --require-compat-ready
```

새 저장 설정을 켜고 배포한다. 집단 UI는 별도로 켜거나 보류할 수 있다. 새 저장 설정은 팀 저장 계약도 함께 사용한다.

운영 Vercel 설정 변경도 승인 대상이다. `VITE_DEMO_MODE=false`를 유지하고, `VITE_ASSIGNMENT_REVISION_ENABLED=true`와 집단 화면 공개 여부를 배포 기록에 남긴다. 데모 주소 제한이 운영 전환을 대신 막아 주지 않으므로 대상 프로젝트·DB 주소를 별도로 대조한다.

- 함수가 없거나 버전이 없는 경우 오류로 멈추며, 옛 저장으로 자동 우회하지 않는다.
- 사용자들이 실제로 앱을 업데이트했는지 확인하고 기록한다. 코드 배포 완료만으로 기기 업데이트가 완료됐다고 판단하지 않는다.
- 새 앱의 봉사·재방 연구 신청, 본인 취소, 대신 신청/게스트, 팀/개인 배정, 공유, 마감 후 예외를 확인한다.

### 3. 엄격 차단

DB·기기·백업·감사 확인 기록을 `app.rollout_evidence`에 명시한 뒤 생성된 `03-strict.sql`을 단일 트랜잭션으로 실행한다. 설치 묶음 해시가 다르거나 기록이 비어 있으면 거부한다. 이 기록은 운영자의 확인 기록이지 기기 보급을 자동으로 증명하는 장치는 아니다.

- 동일 잠금 범위에서 단계 상태와 다섯 옛/호환 RPC의 실행권한을 함께 바꾼다.
- 버전 없는 배정 직접 쓰기와 관리 작업을 차단한다. 본인 신청/취소, 허가된 유지보수, 실제 FK 연쇄 정리는 기존 예외를 유지한다.
- 새 versioned RPC만 배정 관리에 사용한다. 옛 앱은 거부되므로 2단계 확인을 생략할 수 없다.
- 이 시점 이후 집단 UI만 끄는 것은 가능하지만 **배정 리비전 설정까지 끄면 안 된다.**

#### 단일 트랜잭션 실행 명령

아래는 별도 운영 승인 후 사용할 명령 예시이며 이번 작업에서는 실행하지 않았다. 검토한 Session pooler의 `PGHOST`, `PGPORT=5432`, `PGUSER`, `PGDATABASE`, `PGSSLMODE=require`, `PGPASSWORD`를 환경에 준비한다. 비밀번호를 명령줄에 쓰지 않는다. `ROLLOUT_EVIDENCE`에는 실제 기기 업데이트·백업·감사 결과의 기록 위치를 넣는다. 빈 값은 셸에서 거부한다.

```bash
: "${PGHOST:?검토한 접속 환경이 필요합니다}"
: "${PGUSER:?검토한 접속 계정이 필요합니다}"
: "${ROLLOUT_EVIDENCE:?실제 전환 확인 기록이 필요합니다}"
psql -X --single-transaction --set=ON_ERROR_STOP=1 \
  --set=rollout_evidence="$ROLLOUT_EVIDENCE" \
  --file=- --file=scratch/group-service-rollout/03-strict.sql <<'SQL'
select set_config('app.rollout_evidence', :'rollout_evidence', true);
SQL
```

같은 `psql` 호출 안의 두 `--file`을 `--single-transaction`이 함께 감싼다. 확인 기록의 `set_config(..., true)`도 그 트랜잭션에서만 유효하다. 이를 별도 `psql` 호출로 나누거나 SQL Editor로 옮기지 않는다. 준비 단계는 `psql -X --single-transaction --set=ON_ERROR_STOP=1 --file=scratch/group-service-rollout/01-prepare.sql`로 전체 묶음을 한 번에 실행한다.

### 되돌리기

`rollback-to-compatibility.sql`은 설치 묶음 해시와 확인 기록을 요구한다. 자료·댓글·리비전·집단 메타데이터를 삭제하지 않고, 호환 쓰기 허용 상태로 복귀한다. 그 후 필요한 앱 조치를 한다. 일반 사용자나 인도자는 단계 변경 함수/표에 접근할 수 없다.

호환 복귀는 설치 전 스키마 전체 복원과 다르다. 새 집단 자료가 생긴 뒤 구버전 화면으로 무조건 돌아가도 안전하다는 뜻이 아니며, 일정 편집 권한은 계속 관리자 전용이다. 새 자료가 있는 운영에서 전체 백업 복원을 선택할지는 별도 판단한다.

호환 복귀도 위 단일 호출 명령을 사용하되, 기록은 실제 복구 승인 근거로 바꾸고 두 번째 파일만 `scratch/group-service-rollout/rollback-to-compatibility.sql`로 지정한다.

## 실행 검증

- 전체 자동 검사: 263파일 / 2,599개 통과. lint·build 통과. 데모 모드를 끄고 새 배정만 켠 조합에서, 명단에 없는 인도자의 PC 전체 구역 선택과 종료 시간·마감 알림 확인을 포함한다.
- 격리 PGlite에서 실제 생성된 18개 파일 준비 묶음 전체를 실행했다. 전시대 표/칼럼 있는 경우와 없는 경우 모두 준비 → 옛/새 앱 혼용 호출 → 엄격 차단 → 호환 복귀를 통과했다.
- 핵심 카드 저장·범위·팀·참가자 정리는 실제 과거 SQL 함수를 사용했다. 주변 스키마는 합성 자료, 외부 알림은 로컬 수신함으로 대체했다. 운영 사본 성능 시험이라고 주장하지 않는다.
- 격리 댓글 알림 시험은 전시대 수신자가 없는 과거 본문을 사용한다. 전시대 댓글 대상 보존은 데모의 실제 설치 함수로 별도 확인했으며, 운영 본문 원문 대조는 아직 남아 있다. 재리뷰 후 첫 배포 관문의 함수 존재·실행권한 조회를 미설치/호환/엄격 단계로 나누어 검증했고 전환 시험 3개가 통과했다. 이 후속 보완은 점검 도구·시험·문서뿐이며 DB와 앱 배포를 변경하지 않았다. 준비 묶음 SQL 해시도 그대로다.
- 전시대 없음에도 본인 신청·대신 신청·게스트·일정/반복 일정 알림 성공, 있을 때 중복 거부, 재방 연구/일반 신청 중복 거부 확인.
- 참가자 삭제 마지막에 강제 오류를 넣어 세션·카드가 일부만 변경되지 않음을 확인했다.
- 준비 마지막 강제 오류 시 신규 스키마·권한 전체 롤백, 옛 저장 유지 확인.
- 전시대 없음 예외를 고의 제거하면 해당 시험 실패. 준비 완료 시 호환 전환을 고의 제거하면 두 환경 시험 실패. 시험이 실제 결함을 잡는 것을 확인했다.
- 실제 데모 전환 리허설: 9개 통과. 모든 임시 전환·자료는 한 트랜잭션에서 롤백했고 종료 상태는 `strict`다.
- 실제 데모 기존 권한/동시 저장: 21개 통과. 관리 작업: 34개 통과.
- 실제 데모 적용 전 백업: `backups/group-rollout-demo-1794891730536/before.dump`. 복구 SQL → 두 보완 파일 재적용 → 트랜잭션 롤백을 실행했고, 종료 시 함수 정의 해시·권한 감사가 원래 상태와 같았다.
- 복구 파일 첫 검사에서 함수 정의 끝의 구분자 누락을 발견했다. 생성기와 해당 복구 파일을 수정한 뒤 실제 복구 재시험을 통과했다. 실패한 첫 시험도 트랜잭션 롤백되어 데모 최종 상태는 변하지 않았다.
- 데모 앱 `8e5edb8` 배포 뒤 Playwright 화면 검사 12개, 댓글·알림·사용량 검사 34개가 통과했다. 두 인도자의 동시 공유 충돌과 초안 보존, 마감 후 대신 신청·게스트 추가, 회중 봉사의 명단 외 인도자 배정을 포함한다. PC·320px 큰 글씨 화면도 확인했다.
- 댓글 변경은 해당 댓글만 다시 읽고 캘린더 전체를 다시 읽지 않았다. 화면 복귀 시 기존 20개/40개 분량만 읽고, 실제 소켓 재연결 시에도 댓글은 불러온 두 페이지에 한정됐다. 재연결의 기존 캘린더 복구 조회는 별도로 발생한다. 휴대폰 푸시는 실제 수신이 아니라 발송 요청 대기열까지만 확인했다.

## 아직 운영 승인으로 보지 않는 항목
