# 봉사자 구역 요약과 상세 조회 분리

- 상태: 데모 시험 (요약 RPC/범위 미리 받기와 독립 읽기 화면, 기존 봉사 화면 미전환)
- 결정일: 2026-10-05
- 관련 기능: 나의 봉사, 지도, 카드 진행률, 정기방문, 식당, 실시간 복구

## 배경

`useStore`는 로그인 뒤 역할과 관계없이 `ALL_SLICES`를 조회한다. 건물 조회에는
전체 세대가 중첩되고 카드 진행률은 `recomputeCardStats`가 그 자료로 계산한다.
화면에서 배정 카드만 보이게 하는 것은 서버 조회량을 줄이지 않는다.

첫 로딩에 `card_id` 조건만 붙이는 방법도 안전하지 않다.
`recoverTerritoryBuildings`는 전체 건물 ID와 로컬 ID를 비교하여 로컬에 없는 것을
새 건물로 받는다. 부분 로딩된 카드의 통계도 현재 코드에서는 0세대/100%로 바뀔 수 있다.

## 목표 구조

1. 로그인: 사용자 본인 배정과 화면에 필요한 일정/자원 메타데이터, 카드 요약 조회.
   이 단계에서 전체 건물 본문이나 전체 구역선 좌표를 미리 받지 않는다.
2. 지도 진입: 요청한 카드/건물/세대의 상세와 필요한 구역선만 조회.
3. 복귀/실시간: 로드한 범위 안에서 변경분 복구. 배정이 바뀌면 범위도 새로 계산.
4. 관리자/인도자는 첫 전환에서 기존 전체 조회를 유지. 실제 계정 역할로 분기하고
   관리자 화면의 '봉사자 뷰'만으로 데이터 범위를 바꾸지 않는다.

## 조회 범위 계약

`src/utils/recipientTerritoryReadPlan.ts`는 네트워크 없이 아래 계획만 계산한다.
호출자는 메타데이터 로딩 성공을 먼저 확인해야 한다. 로딩 실패를 빈 배정으로 해석하지 않는다.

| 화면 | 상세 조회 대상 |
| --- | --- |
| 배정 구역 전체 지도 | 해당 일정의 본인 배정 카드 ID 전체 |
| 배정 카드 하나 | 위 범위 안의 선택 카드 ID 하나 |
| 내 카드 | 개인 카드 배정 + 오늘의 활성 봉사 세션 대표 카드 |
| 지난 봉사 | 사용자가 연 과거 일정의 배정. 과거라는 이유로 제거하지 않음 |
| 정기방문 | 본인 담당 자료의 건물/세대 ID + 모든 정기방문 ID |
| 식당 배정 | 해당 일정의 본인 식당 건물/세대 ID |
| 비공식 | 일반 건물 조회 없음. 비공식 부모/자식 자원은 별도 경로 유지 |

- 빈 ID 목록은 요청 0건이다. `.in()` 조건을 빼서 전체 조회하는 fallback은 금지한다.
- 주택/상가 필터는 상세의 표시 범위다. 첫 단계에서는 선택 카드의 모든 세대를 받아
  혼합 건물, 실제 빈 건물, 전체 진행률과 봉사 유형별 진행률을 구분한다.
- 정기방문의 ID 연결이 오래됐거나 없는 자료를 버리지 않는다. 현재의
  `findReturnVisitBuilding` 주소 fallback과 구형 `regular_visits` 경로를 대체할
  서버 측 대상 조회가 필요하다. 모호한 주소는 임의 연결하지 않고 미연결 상태를 유지한다.
- 식당 전체보기, 정기방문 직접 링크, 통합 검색은 화면 진입 시 별도 대상 조회가 필요하다.
  현재 계획 함수의 일정별 식당 범위만으로 식당 전체보기를 대체하지 않는다.
- URL ID와 이 함수는 권한 검사가 아니다. 기존 서버 권한/RPC 검증을 유지한다.

## 구현 순서와 통과 조건

### 1. 요약 조회

카드 ID/이름/배정/지역과 건물 수, 세대 수, 완료 수, 주택/상가 수를 조회한다.
서버 집계는 `recomputeCardStats`, `unitUsage`, 구형 출입불가 세대 제외 규칙과 같아야 한다.
식당은 상가에 포함한다. 빈 카드의 기존 의미도 유지한다.
기존 `regularVisitPoints`에는 이름/호수 목록이 있으므로 숫자 집계에 몰래 포함하지 않는다.
상세가 필요한 화면에 분리해서 제공한다.

### 2. 부분 캐시와 대상 조회

건물 배열 외에 '어느 범위를 완전히 읽었는지'를 따로 보관한다.
미로딩/로딩 중/빈 결과/실패를 구분한다. 읽지 않은 카드의 요약을 로컬 0건으로 덮지 않는다.
범위별 generation과 요청 공유 키에 계정/프로젝트/범위가 포함되어야 한다.
로그아웃, 계정 교체, 배정 해제 때 이전 범위의 늦은 응답을 폐기한다.

### 3. 복구/저장 연결

변경 신호와 건물 색인 조회도 동일한 범위로 제한한다. 전체 색인과 비교하면 다시
전체 건물을 다운로드하므로 현재 `fetchBuildingRecoveryIndex`를 그대로 쓰지 않는다.
범위 진입/이탈, 세대 이동, 건물 삭제, 새 건물 생성, 기존 주소 충돌 후 기존 건물로 이동을
각각 검증한다. 부분 조회 오류는 해당 범위 재조회로 복구하고 일반 봉사자에게 전체 조회로
조용히 확대하지 않는다. 서버 시각 기준점도 범위별 성공에 맞춰 전진시킨다.

### 4. 데모 측정 후 전환

- 배정 카드 1개/여러 개에서 요청 URL에 실제 범위 조건이 붙는지 확인.
- 미배정/비공식만 배정이면 일반 건물 요청 0건.
- 정기방문 미연결 자료, 식당 전체보기, 지난 일정 직접 진입 확인.
- 두 기기 동시 기록/취소, 배정 변경, 삭제, 새 건물 직후 첫 세대 등록 확인.
- 첫 실행/복귀/저장별 Transferred를 같은 데이터와 역할로 비교.
- 기능 플래그로 데모에서 먼저 활성화. 운영은 별도 승인 후 적용.

## 이번 작업의 한계

범위 계산 시험은 조회 대상 계약만 검증한다. 아래의 별도 SQL 시험이 집계를 검증하지만,
기존 봉사 화면의 캐시 격리와 실시간 복구 연결은 아직 검증하지 않았다. 기존 앱의
초기 로딩을 전환하지 않았으므로 운영 사용량을 줄이지 않는다. 전체 절감률이나 무료
한도 충족을 예측하지 않는다. 운영 DB 변경/배포, 구역 좌표의 단말 영구 저장은 하지 않았다.

## 요약 RPC 준비 (2026-10-05)

- 마이그레이션: `20261005_1200_card_summaries.sql`
- 롤백: `supabase/tools/rollbacks/_ROLLBACK_20261005_1200_card_summaries.sql`
- 호출 코드: `src/lib/cardSummaries.ts`, `src/lib/recipientCardPrefetch.ts`
- `get_card_summaries(token, card_ids)`는 명시한 최대 200개 카드의 요약만 JSON 배열로 반환한다.
  클라이언트는 200개씩 나눠 받고 중복 ID를 제거한다. 부분 실패는 전체 호출 실패로 남긴다.
  빈 배열은 전체 조회가 아니며, NULL/음수/과대 요청은 서버에서 거부한다.
- 카드 이름/지역/상태, 건물/세대/완료/정기방문 수, 주택/상가별 세대/완료/건물 수만 반환한다.
  배정 메타데이터는 별도 기존 카드 조회 계약이며 이 RPC에 방문자 이름이나 상세를 넣지 않는다.
- 기존 `verify_session`으로 세션을 검사한다. 이 helper는 세션 만료 연장/사용 시각 갱신이
  있을 수 있으므로 RPC 전체를 STABLE/read-only로 표시하지 않는다.
- `SECURITY INVOKER`로 현재 SELECT 권한/RLS를 보존한다. 배정 ID를 보안 경계로 삼거나
  기존보다 넓은 접근을 허용하지 않는다. 익명 키만으로는 세션 검사를 통과하지 못한다.
- PGlite를 **개발 의존성**으로 추가해 실제 PostgreSQL SQL을 메모리에서 실행했다.
  시험용 최소 스키마와 세션 helper stub을 사용한다. 통계 비교, RLS, 명시적 실행권한,
  잘못된 입력, 1000세대 초과, 이동/삭제, 롤백을 검증한다.
  Supabase 전체 스키마/실제 세션 helper/PostgREST 실배포 검증을 대신하지 않는다.
- 실제 연결 전 데모 DB에서 현재 테이블 권한, 만료/비활성 세션, 전체 카드 요약과 기존
  화면 숫자 일치, 응답 Transferred를 확인한다.

## 데모 범위 미리 받기 시험 (2026-10-05)

- `scripts/applyRecipientSummaryDemo.mjs`로 데모 프로젝트 ID를 이중 확인하고,
  public/private 스키마 custom dump 및 archive 목록 확인 후 단일 트랜잭션으로 요약 RPC만 적용했다.
  백업은 `backups/recipient-summary-demo-2026-10-05T03-13-37.798Z/before.dump`에 보관했다.
  archive 목록 검사는 복원 리허설을 의미하지 않는다. 운영은 변경하지 않았다.
- `recipientCardPrefetch`는 요약을 먼저 반환하고 해당 카드의 건물/세대/구역선/최근 1년 유효
  방문기록을 즉시 미리 받는다. 세대는 별도 페이지 조회하여 한 건물의 1000세대 잘림을 피한다.
  같은 범위 또는 하위 카드 지도는 진행 중/완료된 요청을 재사용한다.
- 캐시는 메모리에만 있다. 계정 토큰 확인과 generation으로 로그아웃/범위 변경 후 늦은 응답을
  폐기한다. 빈 범위는 요청 0건, 오류는 해당 범위 실패이며 전체 자료 fallback은 하지 않는다.
  시각 RPC 실패는 자료 조회를 막지 않으며 기준점은 null로 유지한다.
- `VITE_DEMO_MODE=true`와 `/recipient-preview`가 동시에 맞을 때만 독립 시험 화면을 연다.
  이 경로에서는 기존 전체 store와 전역 복구 구독을 끄고 실제 본인 일정 배정만 읽는다.
  목록/전체 지도/개별 카드 지도/건물과 세대 열람만 가능하다. 저장/실시간/통계 시험은 아니다.
  그 외 경로 및 운영의 기존 화면은 바꾸지 않는다. 비공식/식당/정기방문 진입도 기존 흐름을 유지한다.
- 다중 카드 연결은 `event_card_assignment_cards(event_id,user_name)`이다.
  이 표에는 `assignment_id`가 없다. 실제 데모 연결 중 확인하고 회귀 시험에 고정했다.

### 실제 응답 본문 비교

`scripts/measureRecipientPrefetchDemo.mjs`는 앱의 TS 조회 코드를 실행하며 서버가 gzip으로
보낸 응답을 압축 해제 전에 센다. 로그인은 기존 데모 봉사자 계정(role=user)으로 했다.
사용자 PIN/토큰/주소/좌표/방문 내용은 보고서에 남기지 않는다.

| 시나리오 | 전체 건물/세대/구역선/방문기록 | 범위 조회 + 요약 RPC + 시각 RPC | 본문 감소 |
| --- | ---: | ---: | ---: |
| 실제 배정 카드 1개, 8건물/16세대 (전체 9카드/38건물) | 3,753 B | 2,063 B | 약 45% |
| 비교용 카드 2개, 4건물/16세대 | 3,753 B | 1,207 B | 약 68% |

- 공통 카드 메타데이터 424 B는 위 두 열에서 제외했다. 실제 시험 화면의 배정 메타데이터
  조회 및 인증/알림/지도 타일 등도 위 표에 포함되지 않는다.
- 이는 **HTTP 압축 응답 본문**이다. HTTP 헤더/프로토콜, 브라우저 Transferred, 청구 Egress,
  전체 앱 전송량을 의미하지 않는다. 요청 수는 3개에서 6개로 늘었다.
- 실제 배정 1개 측정에서 요약 52ms, 상세 완료 229ms였다. 비교 전체 조회는 135ms였다.
  작은 데모에서는 왕복 횟수 때문에 상세 완료가 더 늦었다. 순차 시나리오/서버 warm 상태도
  다르므로 이 숫자는 휴대폰 성능 평가가 아니다. 미리 받기 완료 후 전체/개별 지도 자료 재사용은
  추가 API 요청 0건이었다. 화면 그리기 0ms라는 뜻이 아니다.
- 구역선 좌표, 건물/세대/방문기록 ID, 건물/세대/완료/정기방문 수/진행률을 원본과 비교했다.
  `regular_visits` 중첩 응답은 object 또는 array일 수 있어 기존 `toUnit` 계약대로 검증한다.
- 데모의 작은/단순 구역선과 자료 분포는 운영과 다르다. 이 비율을 하루 272MB나 월 사용량에
  그대로 곱하지 않는다. 기존 복귀/저장 동작도 이 시험으로 검증했다고 하지 않는다.

### 기존 화면 전환 전 남은 관문

1. 상세 준비 전 즉시 지도 진입과 모바일 통신 지연에서 사용감 확인.
2. 배정 변경/참가 취소/계정 변경, 부분 캐시의 실시간 복구와 두 기기 저장 연결.
3. 정기방문 미연결 자료, 식당 전체보기, 검색/중복 주소 이동, 통계의 전체 자료 계약 유지.
4. 기존 앱 첫 실행/복귀/저장 전체 흐름에서 같은 계정/같은 구간으로 전송량 비교.

### 2026-10-05 데모 수신 연결 검증

- 독립 시험 화면에 기존 `useTerritoryRealtime`과 서버 watermark를 연결했다. 배정 카드 신호만
