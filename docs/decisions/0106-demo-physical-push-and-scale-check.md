# 데모 휴대폰 푸시 준비와 자료량 성능 측정

- 날짜: 2026-11-17
- 상태: 자료량 측정 완료, 실제 아이폰 수신·탭 이동 확인 대기.
- 범위: 데모 프로젝트만. 운영 접속·설정·DB·배포 변경 없음.
- 선행: [0105 전환 순서](0105-group-service-staged-rollout.md)

## 실제 푸시 준비

데모에는 send-push 함수, VAPID 공개키, DB 발송 주소·키가 없었고 구독도 0건이었다. 기존 댓글 검사는 요청 대기열까지만 확인했으므로 실제 기기 수신을 입증하지 못한다.

기존 설정을 `backups/demo-physical-push-1794895491191`에 보존한 뒤 운영과 별개인 데모 전용 키를 생성했다. 데모 Supabase에 send-push와 비밀 설정, 데모 Vercel에 공개키를 등록하고 데모 앱을 재빌드했다. 운영 키는 읽거나 재사용하지 않았다. 생성 키·백업·구독 주소는 커밋하지 않는다.

- 배포: `dpl_54CPhDr1JuEG6gCD9L1Vf2W6PqJV`, 데모 대표 주소 유지.
- 무인증 호출 401 확인.
- 실제 키 설정을 거치는 존재하지 않는 수신자 검사 200 / 발송 0 확인.
- 배포된 앱의 공개키가 데모 전용 키와 일치함을 확인.
- `[데모] 휴대폰 알림 확인` 일정 네 집단 생성. 신갈 일정에 테스트관리자만 신청. 실제 댓글 발송은 등록된 기기가 있어야 하며 다른 수신자가 생기면 발송 트랜잭션 전체를 취소한다.
- 사용자: 아이폰, 데모 관리자. 알림을 켰다고 응답했으나 서버 구독은 아직 0건이라 실제 푸시는 발송하지 않았다. 알림 설정 화면 확인을 요청했다.

`scripts/demoPhysicalPush.mjs`는 데모 주소·DB 계정·포트·Vercel 프로젝트를 검사한다. bootstrap/configure는 최초 데모 준비용이고, status/probe는 구독·설정 확인용이다. prepare는 제한된 시험 일정을 만들며 send comment/mention은 사용자 준비 확인 후에만 사용한다. 단순 준비 검사와 실제 발송 명령을 구분한다.

## 성능 방법

운영에 다시 접속하지 않고 0104에 남긴 운영 집계(일정 686, 참가 1,365, 카드 배정 1,123, 추가 카드 985, 세션 1,592, 댓글 342)를 기준으로 합성 자료를 생성했다. 데모의 실제 설치된 권한 정책·함수·인덱스로 측정했다.

- 80명 합성 사용자와 1배/5배 자료를 **커밋하지 않는 트랜잭션** 안에서만 추가.
- 표본 추가 중에만 세션 한정 트리거 억제. 알림·외부 요청·실시간 변경을 만들지 않으며, 측정 전 정상 상태로 복귀.
- 실제 anon 역할과 승인 세션을 사용하고 admin/leader/user 각각 조회. 소유자 권한으로 조회 시간을 재지 않는다.
- 집단 80%·기존 회중 20%, 날짜·집단 분산. 댓글은 한 일정 40개 및 다른 일정에 분산된 글을 함께 측정.
- 9개 조회 × 3권한 × 3회 × 2규모 = 162개 `EXPLAIN ANALYZE BUFFERS` 결과. 네트워크·화면 렌더링 시간 제외.
- 매 회차 롤백 후 기존 표 행 수 일치 확인. 통계도 원래 자료량으로 다시 갱신.
- 초기 도구 검사에서 JSON 불리언 출력 형식과 임시 스키마 권한 지정을 수정했다. 실패 실행은 커밋되지 않았으며 최종 측정은 두 규모 모두 완료했다.

## 결과

기존 데모 자료에 표본을 더한 실제 측정 크기: 1배는 일정 717 / 카드 배정 1,133 / 세션 1,625, 5배는 일정 3,461 / 카드 배정 5,625 / 세션 7,993이다. 아래는 세 권한의 3회 중앙값 범위이며 모든 값은 DB 내부 ms다.

| 조회 | 운영 유사 규모 | 5배 규모 |
| --- | ---: | ---: |
| 집단 탭 정보 | 1.7–2.7 | 1.7–3.8 |
| 댓글 첫 페이지 | 0.5–1.0 | 0.5–0.6 |
| 댓글이 적은 일정 | 0.3–0.5 | 0.3–1.2 |
| 본인 봉사 기록 | 2.4–2.6 | 8.3–15.4 |
| 전체 배정 조회 | 87–106 | 381–445 |
| 전체 봉사 기록 조회 | 112–119 | 513–678 |

댓글이 적은 일정의 쿼리는 `comments_event_page` 인덱스를 사용했다. 본인 기록은 사용자·날짜 인덱스를 사용했다. 제한된 상세 조회에서 병목은 발견하지 못했다. 다만 전체 이력 조회는 행별 권한 검사 비용이 자료량에 따라 증가했고 5배에서 최대 739ms였다. 따라서 전체 이력 반복 조회를 가벼운 조회라고 취급하거나 동시 접속 성능까지 합격했다고 판단하지 않는다.

이 결과는 실제 운영 자료 복제, 운영 서버 측정, 동시 접속 부하 시험, 휴대폰 응답 시간, 비용 측정이 아니다. 합성 표본 분포와 데모 서버 상태에 한정한다. 기존 전체 조회는 자료량 증가 시 범위 축소·서버 집계를 우선 검토한다. 이번에는 권한 정책이나 앱 조회 동작을 추가로 변경하지 않았다.
