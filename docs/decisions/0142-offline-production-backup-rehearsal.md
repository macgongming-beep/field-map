# 운영 JSON 백업의 격리 복구 리허설

- 날짜: 2026-11-20
- 상태: 격리 리허설 완료, **기존 도구의 전체 운영 복구 사용은 보류**
- 선행: [0141 집단 구역 및 백업 보완](0141-demo-shared-group-territories.md)
- 사용자 요청: 오늘 백업으로 정상/실패 복구를 시험하되 운영 데이터·배포는 변경하지 않는다.

## 입력과 격리

- 데이터: `backups/2026-11-20`, JSON 43개 / 29,548행과 private 병합 감사 SQL.
  한 JSON은 `user_notification_prefs` 뷰여서 실제 적재 표는 42개다.
- 구조: 로컬에 이미 있던 `backups/service-series-production/before.dump`의 **구조만** 추출하고
  그 덤프 직후 적용했던 `20261119_0010_service_series_edit_targets.sql`을 로컬에서 적용했다.
  덤프의 옛 사용자 자료·로그인 토큰·비밀 설정은 가져오지 않았다.
- 운영에는 재접속하지 않았다. 현재 운영 구조와 동일하다는 주장은 하지 않는다.
  이번 JSON의 모든 표/칼럼이 이 저장된 구조와 호환되는 것은 확인했다.
- PostgreSQL 17.6을 임시 폴더의 Unix socket으로만 실행했다. TCP 수신 없음.
  실행마다 DB를 새로 만들고 끝나면 서버를 종료하고 임시 클러스터를 삭제한다.
- 실제 `restore.js` 본체는 그대로 실행한다. 로더가 파일 위치와 연결 부분만 로컬로 연결한다.
  `.env.local` 읽기와 외부 fetch를 차단하고, REST 쓰기는 같은 형태의 SQL을 서비스 역할로
  실행한다. 따라서 **실제 PostgREST/운영 RLS까지 검증한 것은 아니다**.
- 푸시·cron 확장은 설치하지 않는다. `net.http_post`는 외부로 보내지 않는 로컬 기록 함수다.
  암호 연산은 호출 시 실패하도록 두었다. 백업의 사용자 PIN 73개는 기존 해시 그대로다.
- 보고서·원문 로그는 Git 제외된 백업 폴더에만 보관한다. 폴더 0700, 파일 0600.
  원본 JSON 및 감사 SQL의 SHA-256을 시작/종료 때 대조해 변경 없음을 확인했다.

## 기존 복원 경로에서 발견한 중단

| 단계 | 결과 | 의미 |
| --- | --- | --- |
| 원래 도구 + 빈 DB | `review_tasks`, `428C9` | GENERATED ALWAYS 식별자에 백업 ID를 직접 넣을 수 없음 |
| 로컬에서만 식별자 제한을 완화한 진단 | `event_participants`, `42501` | 신청자 버전 관리 보호가 직접 삽입을 차단 |
| 로컬에서만 관리 작업 표시도 켠 진단 | `event_card_assignments`, `23505`, `service_sessions_pkey` | 배정 트리거가 봉사 세션을 생성하면서 아직 조정하지 않은 번호와 충돌 |

뒤 두 단계는 다음 문제를 찾기 위한 **진단용 우회**다. 제품 복원 도구나 운영 정책을 고친
것이 아니다. 특히 서비스 역할이면 모든 업무 트리거를 통과할 것이라는 가정은 틀렸다.
일괄 복원 중 알림·세션 자동 생성·번호 조정까지 함께 설계해야 한다.

## 백업 데이터 적재 가능성 (별도 진단)

- 별도의 빈 로컬 DB에서만, 한 트랜잭션 안에서 업무 트리거를 잠시 끄고 FK 순서대로
  데이터를 넣었다. `OVERRIDING SYSTEM VALUE`로 기존 식별자를 보존했다.
- FK·고유키·NOT NULL 제약은 유지했다. 이후 업무 트리거의 활성 상태를 원래와 대조했다.
- SQL 형식으로 정규화한 전체 행을 양방향 비교했다. **43개 자료 / 29,548행 차이 0건**.
  감사 기록 18건도 복원했다. 공개 표의 시퀀스 39개를 조정하고 각각 다음 번호가 기존
  최대 번호보다 큰지 확인했다. 외부 HTTP 전송 0건.
- 이 경로는 데이터 손상이 없는지 확인하는 실험이다. **업무 트리거를 통째로 끄는 방식을
  운영 복구 방안으로 승인한 것이 아니며, 기존 복원 도구의 성공으로 계산하지 않는다.**

## 중간 실패·재시도

| 시험 | 결과 |
| --- | --- |
| 세대 501번째 자료의 건물 FK를 틀리게 함 | 첫 500행만 반영, 두 번째 묶음 전체 거절(`23503`) |
| 같은 복사본을 정상 자료로 바꾸고 재시도 | 중복 없이 3,684행, 원본과 정규화된 행 차이 0건 |
| 중간의 review_tasks 표를 로컬에서 이름 변경 | 후속 표 쓰기 중단, 앞선 집단 설정 변경은 이미 반영됨 |
| JSON 파일 손상 | 쓰기 없이 중단 |
| 같은 행을 판단할 키가 없는 시험 표 | 쓰기 없이 중단 |
| 집단 목록 복원에 중복 이름 삽입 | 해당 트랜잭션 실패, 집단·소속·설정 원복, 모든 업무 트리거 상태 유지 |

원본 백업을 손상시키지 않고 임시 복사본만 변경했다. 정상 retry를 해도 전체 복원이
한 트랜잭션이 된다는 뜻은 아니다. 운영 복구 도구는 부분 완료를 안전하게 식별해야 한다.

## 백업 범위의 남은 문제

저장된 구조에 있지만 이번 JSON에 없는 업무 자료:

- `event_meeting_access`: 화상 모임 접속 정보
- `place_change_requests`: 장소 변경 요청
- `territory_report_shares`: 구역 보고 공유 스냅샷

각 표가 현재 운영에서 몇 행인지 이번에는 조회하지 않았다. **파일이 없어서 이 백업만으로는
그 값들을 되살릴 수 없다**는 범위 문제다. 누락 자료 추가 백업은 별도 승인 후 진행한다.
`auth_sessions`·`app_private_settings`는 의도한 제외이므로 무작정 복원 대상에 넣지 않는다.
변경 신호 표, private 배포/관리 상태와 비밀값은 재생성·재설정 절차를 별도로 정해야 한다.

## 재현 도구와 기록

```bash
REHEARSAL_PG_BIN=/path/to/postgresql/bin node scripts/rehearseProductionBackup.mjs
```

- 완전한 PostgreSQL 서버 도구와 Homebrew libpq의 psql/pg_restore가 필요하다.
  운영 URL·키·`.env`를 읽지 않으며, 이 스크립트를 운영 복원용으로 사용하지 않는다.
- 최종 기록: `backups/recovery-rehearsal-1795146599070/report.json`.
  `completed=true`는 리허설 수행 완료다. `guardedFullRestorePassed=false`,
  `readyForProductionRecovery=false`가 복구 준비 상태다.
- 첫 실행의 pg_restore 출력 옵션 누락과 다음 실행의 진단용 identity override 누락은
  시험 도구 문제였다. 실패 기록도 삭제하지 않았고 수정 후 전체를 반복 실행했다.
- 관련 55개 시험·lint·빌드 통과. `scripts/rehearsal/mutateRetry.mjs`는 분리 복사본에서
  중복 처리(ON CONFLICT)를 제거했고, 실제 500행 이후 재시도가 `23505`로 실패해
  리허설이 실패 판정을 내리는 것을 확인했다. 변이 DB와 복사본도 종료·삭제했다.
- 앱 코드·복원 제품 코드·DB 마이그레이션·환경변수·배포는 바꾸지 않았다.
