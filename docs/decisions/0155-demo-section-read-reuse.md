# 봉사자 조회 재사용과 관리 화면 경량 조회 재검증

- 날짜: 2026-11-22
- 상태: 데모 적용. 운영 미적용.
- 기준: `e12dee0` (0154 홈 코드 선로딩 포함).
- 요청: 봉사자 캘린더/나의 봉사, 첫 홈, 설정/관리 화면을 데모에서 순서대로 개선하고 비교.

## 적용 범위

1. **개인 구역 확인:** 기존에는 개인 배정/연결 카드 뒤 일정의 제목, 장소, 참가자까지
   읽었다. 구역 ID 판정에는 일정 존재 여부만 필요하므로 `assignmentCardIds`는 일정의
   `id`만 읽는다. 같은 작업에서 방금 확인한 캘린더 일정 ID는 중복 확인하지 않는다.
   월 범위를 개인 배정 전체로 취급하지 않으며, 월 밖의 과거/미래 일정은 별도로 확인한다.
   본인 배정과 연결 카드는 여전히 새로 읽는다. 캐시된 담당 범위를 오래 믿는 TTL을
   추가하지 않으며, 반환된 ID를 다음 작업의 확인 생략에 쓰지 않는다.
2. **첫 실행:** 0140의 `VITE_RECIPIENT_DISCOVERY_REUSE_ENABLED=true`를 현재 코드로
   재검증해 데모 빌드에서 켠다. 최초 상세 조회보다 앞선 동기화 시각을 재사용하고,
   배정 ID에만 의존하는 연결 카드/일정을 함께 읽는다. 건물에 의존하는 카드 합계와
   방문 이력의 대기는 유지한다. 이번에는 로그인이나 카드 요약의 순서를 추가로 바꾸지 않는다.
3. **관리 화면:** `VITE_ROUTE_LIGHTWEIGHT_ENABLED=true`를 현재 집단 구역 기능과
   함께 재검증한다. 집단 선택의 `groupCode`가 붙어도 목록은 불필요한 전체 일정
   이력을 읽지 않는다. 모바일 건물 조회도 목록 필드를 유지한다. 중복 쿼리 키와
   알 수 없는 모드/상세는 전체 조회로 보수적으로 처리한다.

두 설정은 명시적 opt-in이며 운영 기본값은 계속 OFF다. DEMO_MODE로 자동 켜지지 않는다.
기존의 전체 개인 일정 재사용(`SERVICE_CALENDAR_REUSE`)은 유지한다. 그 경로를 이미
쓰는 나의 봉사는 이번에 더 줄일 조회가 없어 결과가 동일하다.

## 기능 보존

- SQL/RLS/배정 저장/리비전/신청/취소/알림/지도/공동 집단 담당 데이터는 바꾸지 않는다.
- 전체 미리보기용 `assignments()`는 기존 열/필터/날짜 무제한/정렬/카드 범위를 유지한다.
  ID 전용 판정에도 같은 배정 병합과 `assignedServiceScope`를 쓴다. 이 함수의 입력
  타입만 실제로 쓰는 `cardAssignments`로 좁혔으며 계산은 바꾸지 않았다.
- 조회 페이지(1,000), 일정 배치(100), 본인 이름 조건, 없는 일정 제외를 유지한다.
  알려진 일정 ID 자체가 구역을 부여하지는 않는다. 새 개인 배정/연결 행이 있어야 한다.
- 읽기 실패/계정 변경은 기존처럼 거절한다. 범위 변경이나 복구 실패는 전체 개인
  스냅샷을 다시 읽으며, 운영의 전체 구역으로 넓히지 않는다. 새로고침/재연결의
  변경 신호·건물 ID 확인·방문 이력 안전 조회를 제거하지 않는다.
- 인도자/관리자 배정 편집기는 여전히 전체 자료와 최신 참가자/리비전을 기다린다.
  개발자의 전체 건물 조회도 기존대로다.
- 명단의 60초 재사용과 명시적 새로고침은 0140 그대로이며 이번에 기간을 늘리지 않았다.
  초기 로딩 실패, 편집 초안, 홈 선로딩 관문도 유지한다.

## 전후 결과

Chromium 390x844, CPU 4배 감속, 로컬 앱 파일, 서비스워커 OFF, 실제 데모 DB다.
유효한 데모 세션의 새 context로 앱을 다시 열었다. 전후 교차 3쌍씩 순차 측정했고,
각 섹션은 홈을 새로 로딩한 뒤 진입해 앞 화면의 완전한 자료 캐시 효과를 배제했다.
요청 완료 뒤 800ms 조용한 구간을 확인한다. 30초 안에 안정되지 않으면 실패한다.
아래 시간은 중앙값이며 실제 아이폰/PWA나 운영 규모의 시간을 뜻하지 않는다.

화면 표시와 전체 자료 완료를 구분한다. 캘린더는 즉시 통신 조건에서 전체 완료가
754 → 846ms, 120ms 지연 조건에서 2,117 → 2,016ms였다. 나의 봉사는 각각
699 → 723ms, 1,974 → 2,077ms다. 이 두 화면이 확실히 빨라졌다고 주장하지 않는다.
캘린더의 효과는 중복 요청/본문 감소, 나의 봉사는 기존 기능/사용량 유지다.
관리자 구역도 이미 빠르게 표시되므로 속도 개선보다 불필요한 자료 절감으로 설명한다.

WebKit 인도자 390px 1쌍은 화면/기능 smoke다. 홈 29건, 캘린더 5건, 나의 봉사 10건,
구역 10건 및 각 응답 바이트가 전후 같다. 실제 화면을 정상 표시하고 오류가 없었다.
반복 성능 근거로 사용하지 않는다. 관리자 구역 화면도 목록/집단 선택/집계가 정상이다.

## 사용량과 안전

- 정상 측정의 모든 구간에서 DB 요청 수와 원문 응답은 같거나 줄었다. 기존 조회
  확인을 없애지 않았으므로 모두 0건이 되거나 모든 화면이 빨라지는 변경은 아니다.
- 앱 파일 요청 수는 Chromium 전후 18건, WebKit 전후 19건이다. 전체 JS는 17개,
  원문 합계 2,509,414 → 2,510,577바이트(+1,163), gzip 합계
  708,820 → 709,256바이트(+436)다. 앱 코드까지 바이트가 전혀 늘지 않는다는 뜻은 아니다.
- DB 원문은 압축·캐시·과금량과 다르다. 동기화 시각 응답 길이에 따라 1~2바이트
  차이가 있다. 실제 운영 하루 사용량/동시 접속/지도 타일은 이번 측정에 포함하지 않는다.
- 업무 표/Storage 쓰기는 차단하고 읽기/인증 RPC만 허용했다. 자동 세션 정리는
  응답 0으로 대체했다. 데모 인증의 세션/접속 기록은 발생한다. 운영 DB에는 접속하지 않는다.
- 관리자 첫 측정은 HEAD 응답을 브라우저 종료 이벤트만으로 판정해 실패로 처리했다.
  응답 이벤트에서 HEAD를 한 번만 세도록 고친 뒤 3쌍을 다시 쟀다. 실패 실행은 제외했다.
- 성능 실행 중 전체 시험/변이는 돌리지 않았다. 인도자는 실물 아이폰이 아닌 WebKit이다.

## 외부 리뷰와 OFF 경로 시험 보강

사용자가 전달한 Claude 리뷰는 `7229d96`을 승인했다. 같은 소스의 두 설정 ON/OFF
빌드로 13개 화면의 표시 내용이 같음을 확인했고, 관련 1,584개 시험을 통과했다고

경로이므로 비교 조건이 다르다. 실패 주입 시 기존 자료를 보여 주는 동작도 ON/OFF가
같았으며, 이를 새로운 재시도 기능이나 오류 처리 개선으로 해석하지 않는다.

`refresh`가 기존 `assignments()`를 호출하고 ID 전용 경로는 호출하지 않는지 본다.
