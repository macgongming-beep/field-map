# 배정 편집 중 새로고침·재연결과 초안 보존

- 상태: 데모 검증, 운영 미적용
- 결정일: 2026-11-18
- 기준 커밋: 43f98f6
- 관련: 0122 배정 화면 진입 수정과 Claude 후속 리뷰

## 확인 범위

사용자 요청은 편집 중 새로고침·재연결 때 초안이 사라지는지 확인하고 문제만 고치는 것이다.
운영 앱·DB·환경변수·main은 수정하지 않는다. 실제 데모 인도자·관리자 계정으로
브라우저 안의 임시 배정만 편집한다. 공유·배정 저장·신청자 변경 요청은 시험 도구가
차단한다. 데모 로그인·기존 자동 세션 종료는 발생할 수 있다.

## 결과와 근거

기존 데모에서 초안 유실은 재현되지 않았다.

1. 사람을 새 팀으로 묶고 구역 편집 화면을 연 뒤 당겨서 새로고침:
   전체 초안 JSON이 같고, 구역 편집 화면의 기존 DOM도 연결된 상태로 유지됐다.
2. 건물 읽기 응답을 HTTP 503으로 바꿔 새로고침 실패:
   초안과 편집 화면은 유지됐다. 다만 아래의 처리되지 않은 오류가 발생했다.
3. 브라우저를 오프라인으로 바꾸고 열린 WebSocket을 닫은 뒤 온라인 복구:
   새 WebSocket 생성과 실제 재조회가 발생한 상태에서 초안·편집 화면이 유지됐다.
   focus 복귀도 시험하며 브라우저 시계만 125초 앞당겨 기존 2분 제한을 넘겼다.
4. 브라우저 전체 새로고침 뒤 배정 편집기를 다시 열기:
   기기에 저장된 동일한 초안이 복원됐다. 편집기가 자동으로 다시 열리는 것은 아니다.
5. 다른 사람이 수정한 상황을 읽기 응답의 revision +1로 모사:
   선택창이 뜨고, 선택 전에 다시 새로고침해도 원래 로컬 초안은 보존됐다.
   '내 임시 저장 이어서'를 선택한 뒤에만 기준 revision이 갱신됐다.
   실제 서버 배정은 바꾸지 않았으며 이 검사는 DB 동시 저장 시험을 대신하지 않는다.

코드상 full reader는 한 번 full 자료를 확보하면 갱신 시작/실패 때 ready를 false로
내리지 않는다. 기존 스냅샷을 보존하므로 일반적인 재조회가 편집기를 unmount하지 않는다.
가정상 ready를 강제로 false로 바꿨다가 복구하는 컴포넌트 시험에서도 이미 저장된
초안 내용은 복원됐다. 이는 활성 탭·실행 취소 같은 휘발 상태까지 보존한다는 뜻이 아니다.

## 발견한 문제와 수정

`PullToRefresh`는 `onRefresh()` 실패 시 finally로 회전 표시를 끝내지만, 이벤트
핸들러 밖으로 거절된 Promise가 빠져나갔다. 실제 데모의 실패 응답 시험에서
`Building data load failed`가 pageerror로 기록됐다. 초안 유실과는 다른 문제다.

앱 코드 변경은 `PullToRefresh.tsx`의 catch 처리 2줄뿐이다. 실제 호출자인
useStore.fetchAll이 이미 실패 안내를 하고 기존 화면을 보존하므로 알림을 중복 추가하지
않고 이벤트 핸들러에서 거절을 마무리한다. 저장·초안 복원·권한·revision·조회 범위는
바꾸지 않았다. 새로운 요청·구독·자동 재시도도 없다.

## 시험

- PullToRefresh 2개: 실패 후 회전 표시 종료·수동 재시도, 진행 중/5초 이내 중복 방지.
  수정 전에는 2개 assertion은 통과해도 unhandled rejection 1개로 실행이 실패했다.
  이 실패를 숨기도록 시험 설정을 바꾸지 않았다.
- buildingDemand 3개: 수동·foreground·realtime 전체 읽기 fallback의 대기·실패·복구 동안
  full 준비 상태와 기존 건물 참조 유지, 성공 후 실제 새 건물 반영.
  baseline을 비워 전체 읽기 경로를 시험한다. 델타 경로는 기존 시험과 브라우저 복귀로 확인한다.
- AssignmentEditor 3개: 가정상 ready 하락 후 저장 초안 복원, 새 revision 충돌 선택 전
  다시 닫아도 로컬 보존, 편집 중 새 event prop을 받아도 예전 기준 revision으로 공유를
  시도하고 충돌 시 초안/화면을 유지.
- 변이: 건물 읽기 시작 때 준비 상태를 초기화하면 새 store 시험 3개가 실패한다.
  실제 실패는 추가 promotion으로 건물 참조가 바뀌는 검사에서 발생했다.
- 변이: 공유 충돌 시 로컬 초안을 삭제하면 새 편집기 시험 1개가 실패한다.
  변이 후 앱 코드는 모두 원복했다.
- 원복 후 전체 2,588개(266파일), lint, 데모용 build 통과. 기존 큰 청크와
  inlineDynamicImports 폐기 예고 경고는 남아 있다.

## 브라우저 검증 도구와 한계

`scripts/verifyAssignmentDraftRecoveryDemo.mjs`는 데모 주소만 허용하고 비즈니스 쓰기를
거부한다. 매 계정마다 새 브라우저 context를 쓰고 마지막에 닫아 시험 초안을 폐기한다.
정상/실패 새로고침, 소켓 복구·복귀, 전체 새로고침, 충돌 선택을 하나의 흐름에서 검사한다.
터치는 실제 DOM 이벤트 핸들러로 보내되 자동화로 발생시켰다. 실제 아이폰의 앱 강제 종료,
저장 공간 부족, OS의 저장소 정리, 세션 만료는 이번 브라우저 검사 범위가 아니다.

원본은 로컬 scratch의 `draft-recovery-before.json`, `draft-recovery-after-local.json`.
초기 도구 실행은 Touch 생성 인자 누락으로 중단됐다. 그다음 충돌 모사는 단일 객체 응답을
놓쳐 선택창 대기에서 중단됐다. 두 도구 오류를 수정한 뒤 기준 데모를 다시 검사했고,
최종 기준 실행은 초안 보존 검사를 통과한 뒤 위 unhandled rejection 검증에서 실패했다.
수정본의 첫 로컬 검사에서는 관리자 로그인 ID를 표시 이름으로 잘못 사용해 임시 저장
키를 찾지 못했다. 도구가 로그인 응답의 실제 이름을 쓰도록 고쳤다. 앱 초안 유실은 아니다.

정상 수동 새로고침 요청은 기준 인도자에서 19건이었다. 이번은 속도 최적화 작업이 아니며
재연결·focus 요청은 시점에 따라 합쳐질 수 있어 요청 수 감소나 속도 개선을 주장하지 않는다.
실제 앱 변경은 오류 종료 처리뿐이다.
