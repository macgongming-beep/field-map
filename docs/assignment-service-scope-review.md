# 팀별 봉사 범위 및 나의 봉사 개편: 구현 전 리뷰

- 상태: 제안, Claude 1차 설계 리뷰 반영. 운영/DB 변경 없음.
- 기준 코드: 40c82e9, codex/assignment-view-polish.
- 목적: 팀에 주택/상가/전체 카드 묶음과 비공식을 함께 배분하고 식당은 개인에게 배분한다.

## 1. 합의된 화면 계약

- 헤더의 선택 팀 이름과 구성원 표시는 유지한다.
- 카드/비공식/식당 탭 위치는 고정한다. 지도/목록 전환은 카드에서만 표시한다.
- 카드 탭의 봉사 범위 전체/주택/상가는 실제 배정 속성이다.
- 기존 카드 구성 조회 메뉴는 범위 저장이 연결된 단계에서 제거한다.
- 구 버튼은 별도의 지역 조회 필터이며 배정 내용을 변경하지 않는다.
- 주택/상가 범위에는 해당 세대가 하나라도 있는 카드가 포함된다. 혼합 카드를 제외하지 않는다.
- 팀 하나에 카드와 비공식을 함께 배분할 수 있다. 비공식만 있는 팀도 보존한다.
- 식당은 해당 일정의 참가자 개인을 선택한다. 팀 전원에게 암묵적으로 복제하지 않는다.
- 탭 전환만으로 기존 배정을 지우거나 저장하지 않는다.
- 팀 요약 예: 주택 카드 3개 / 비공식 2개. 식당 개인 배정은 따로 표시한다.
- 범위 변경으로 대상 세대가 없어지는 선택 카드는 명시적으로 확인하며 몰래 제거하지 않는다.

## 3. 저장 설계 제안: 먼저 리뷰할 핵심

팀을 개인 배정 행에서 추론하는 방식만으로 비공식 팀 배정을 완성하지 않는다.
일정에 속한 안정 팀 ID와 팀 단위 범위의 기준 자료가 필요하다. 새 팀/팀원/카드 표 전체를
즉시 도입하는 안과 기존 team_key를 보존하고 최소 팀 메타데이터만 추가하는 안을 비교한다.
표 수가 적다는 이유만으로 개인별 scope 복제를 기준 자료로 삼지 않는다.
팀 번호는 표시 이름이고 식별자가 아니다. 삭제된 팀 2와 새 팀 2의 ID는 반드시 다르다.

- 팀 카드 묶음에 cardScope = all/residential/commercial 하나를 둔다.
- 팀 비공식 배정은 부모 카드 ID를 연결한다. 자식 거점/대화장소는 개별 배정하지 않는다.
- 식당은 일정+사용자+식당 세대 ID에 연결한다. 과거 건물 단위 배정은 별도 호환한다.
- 팀원 이동/삭제/추가 시 팀 배정의 현재 수신자를 서버에서 원자적으로 갱신한다.
- 개인 식당 배정은 팀 변경만으로 이동/해제하지 않는다.
- 참가 취소/계정 비활성/일정 삭제 처리도 같은 계약에 포함한다. 과거 방문 기록은 유지한다.
- 카드+비공식+개인 식당 모두 초안에서 편집하고 공유 RPC 한 번으로 확정하는 방향을 권장한다.
- 공유 RPC는 역할, 일정 접근 권한, 유효한 참가자, 장소, 팀 ID, 범위를 검증한다.
- 버전 또는 공유 시각을 이용해 동시 편집 충돌을 검출한다. 실패하면 전체 롤백하고 초안 유지.
- 범위는 목록 제한이지 새 접근 권한 체계가 아니다. 화면 필터를 RLS 보호라고 설명하지 않는다.

구버전 호환은 설계 승인 조건이다. 기존 개인 배정 테이블은 읽기 호환용으로 유지할 수 있지만,
신규 팀 자료와 두 군데서 독립적으로 수정하면 안 된다. 같은 트랜잭션에서만 투영한다.
구버전 저장 호출이 새 범위를 전체로 덮거나 비공식을 지우지 않도록, 인수 생략은 보존한다.
팀 구성 충돌 등 보존이 불가능한 구버전 변경은 업데이트 안내와 함께 명시적으로 거부한다.
새 범위를 이해하지 못하는 구버전 봉사자 화면에 좁은 배정을 제공하기 전 업데이트 유도도 필요하다.
신규 RPC 부재 때 범위를 버리고 옛 직접 INSERT 경로로 저장하는 폴백은 사용하지 않는다.
실제 스키마 명칭과 기존 RPC 확장/신규 RPC 선택은 모든 쓰기 경로 조사 후 확정한다.

## 4. 나의 봉사 미리보기 계약

```text
오늘의 봉사 / 팀 1
김OO · 박OO · 이OO

주택 봉사 · 카드 3개       [배정 구역 지도 보기]
비공식 증거 · 카드 2개
  배분테스트 비공식 1      [열기]
  배분테스트 비공식 2      [열기]

내 식당 배정 · 1곳         [장소 보기]
```

- 모바일과 PC 모두 일정별로 묶고 다른 일정의 배정은 섞지 않는다.
- 카드 지도는 해당 묶음의 모든 카드 경계를 옅게 표시하고 해당 세대만 필터링한다.
- 지도 핀, 하단 목록, 개수, 범위 내 진행률은 같은 세대 집합을 사용한다.
- 주택/상가만 완료했다고 카드 전체 상태를 완료 처리하지 않는다.
- 최초 진입에만 전체 범위를 맞춘다. 기록 저장/실시간 갱신 때 재확대하지 않는다.
- 하단은 작게 시작하고 핀 선택은 요약, 요약 선택은 세대 목록을 연다.
- 비공식 지도는 선택한 비공식 부모와 자식만 표시한다. 구역 건물 핀과 섞지 않는다.
- 배정 카드 0개/해제/권한 변경 시 전체 지도 폴백을 금지한다.
- 봉사자 임의 전체 보기 전환은 이번 범위에서 제외한다.
- 첫 데모는 데이터 저장 없이 주택+비공식, 상가+비공식, 비공식만, 식당 개인 사례를 시각 확인한다.

## 5. 통계: 배정과 실제 활동을 구분

통계 화면 확대는 후속 단계다. 다만 새 기록부터 필요한 문맥을 보존하는 설계는 지금 정한다.

- 계획: 주택/상가 배정 팀 수, 고유 참가자 수, 배정 카드/대상 세대 수.
- 실적: 실제 방문 이력의 주택/상가 분류와 결과. 배정됐다는 이유로 방문 실적을 만들지 않는다.
- 방문 시점의 세대 용도와 일정/배정 문맥을 서버에서 기록한다. 용도 계약은
  effectiveUnitUsage: 식당이면 상가, 그 외 usage_type 우선, 없으면 건물 type이다.
  서버 저장도 동일한 계약을 지키도록 공통 fixture로 TS/SQL 결과를 대조한다.
- 카드 범위와 실제 방문 용도는 다른 필드다. 전체 봉사에서도 주택/상가 방문을 구분한다.
- 식당은 상가의 부분집합이다. 상가 수+식당 수를 더해 총 방문 수로 계산하지 않는다.
- 비공식은 방문 실적의 정의부터 별도로 정한다. 카드 열기를 봉사 완료나 방문으로 세지 않는다.
- 팀원 4명에게 같은 카드가 보인다고 카드/세대 실적을 4배로 집계하지 않는다.
- 과거 이력에 분류가 없으면 미분류로 보존한다. 현재 용도로 추정하는 경우 별도 표시한다.
- 봉사 유형별 시간은 이번에 제공하지 않는다. 주택+비공식 세션 전체 시간을 각각에 중복 합산하지 않는다.
- 다중 카드 세션에는 대표 카드만이 아닌 실제 허용 카드 집합을 연결한다.
- 일정/팀/범위가 바뀌어도 과거 기록이 재분류되지 않도록 세션/방문 스냅샷을 유지한다.

## 6. 단계 및 검증

1. 이 문서 리뷰: 기준 저장 구조, 구버전 쓰기, 공유 원자성, 통계 단위 확정.
2. 데모 UI 미리보기: 배분 화면과 나의 봉사를 PC/모바일에서 확인. 운영 변경 없음.
3. 테스트 DB: additive 스키마/RPC/권한/조회·쓰기 호환, 실제 백업 및 복원 리허설.
4. 데모 end-to-end: 범위 저장→공유→다른 사용자 로그인→지도→두 번째 카드 기록→다시 열기.
5. 통계 기록 계약 검사 및 기존 전체 통계 회귀 확인. 새 통계 대시보드는 후속 작업.
6. 구현 코드 Claude 재리뷰 후 별도 운영 승인. DB 먼저, 호환 코드 배포, 실제 사용자 소규모 확인.

필수 사례:
- 같은 카드에 팀 A 주택 / 팀 B 상가; 혼합 건물은 세대 기준 분리.
- 한 팀 카드+비공식; 비공식만 팀; 개인 식당만 있는 참가자.
- 팀 2 삭제/재생성, 구성원 이동, 참가 취소, 개인 식당 배정 유지.
- 범위 변경 후 대상 0개, 구역 밖 세대, 끊긴 링크, 빈 카드, 새 세대 실시간 추가.
- 저장 일부 실패/권한 오류/세션 만료/동시 공유/재시도/오프라인 초안.
- 이전 로컬 초안의 범위 기본값 all, 이전 서버 자료 복원, 구버전 호출 필드 보존.
- 지도 범위·핀·목록·분모 일치, 카드 전체 완료 상태 불변.
- 2번째/3번째 카드 기록의 세션 연결, 식당 중복 집계 방지, 과거 이력 불변.
- 새 시험은 핵심 조건을 일부러 되돌리는 변형 시험으로 실패를 확인한다.

## 7. 1차 리뷰 수용 및 교정

### 수용

- persistence.ts는 기존 teamKey로 그룹을 나눈 뒤 ID를 team-server-index-cardIds로 다시
  만든다. UUID 키까지 바뀌는 실제 코드 결함이다. 기존 키는 형식과 관계없이 보존해야 한다.
- event_informal_assignments에는 팀 키가 없다. 팀 연결과 개인 레거시 배정을 구별해야 한다.
- 새 계약을 지원하지 않는 DB에서는 저장을 거부하고 설치/업데이트를 안내한다.
- 이름 기반 참조를 추가하면 rename_user_name_references와 purge_user_name_references를
  함께 검토한다. 새 표는 백업/복원 순서, 설치 검증, FK, RLS, RPC 권한, Realtime 구독을 포함한다.
- 첫 UI 미리보기는 DB 변경 없이 진행한다. 저장/공유가 실제 적용된 것처럼 표시하지 않는다.

### 그대로 적용하지 않을 제안

- 운영의 키 형식별 181/253/73행 수치는 Claude 보고값이며 이번 작업에서 독립 재조회하지 않았다.
  문자열 형태만으로 서로 다른 키가 같은 팀이라고 판단하거나 현재 자료가 손상됐다고 단정하지 않는다.
- 기존 team-server-*를 전부 UUID로 즉시 치환하지 않는다. 기존 값을 불투명한 안정 키로
  보존하면 새 재계산을 중단할 수 있다. 치환이 필요하면 (event_id, old_key)별 참조·로컬 초안·
  구버전 재공유를 조사하고 일대일 매핑과 복원 계획을 마련한다.
- 키 없는 자료는 읽을 때마다 UUID를 새로 만들면 안 된다. 최초 확정/명시 이관 시 발급·영속하고
  새로고침, 저장 실패, 동시 편집에도 팀 정체성이 유지되는 경로를 별도로 설계한다.
- team_key와 nullable 컬럼 추가만으로 팀 scope, 이름/순서 보존까지 해결되지는 않는다.
  팀 번호 재사용 요구도 있으므로 메타데이터 영속 여부는 나중으로 무조건 미루지 않는다.
- 세션을 현재 assignment_id로만 따라가면 배정 변경/삭제 후 과거 카드 집합이 바뀐다.
  기존 참조는 재사용 가능하지만 당시 배정 버전 또는 카드 집합 스냅샷은 별도로 필요하다.
- 식당의 unit_id 배정은 현재 이미 구현돼 있다. 이번 변경은 개인 선택 UI와 공유 계약 변경이다.
  병합 보류/이동 회귀 시험은 추가하되 단순 UI 변경을 이유로 병합 알고리즘까지 바꾸지 않는다.
- SELECT using(true)를 새 표에 자동 복제하지 않는다. 현행 Realtime·공개 범위를 확인하고,
  최소 데이터 노출과 실제 구독 시험으로 정한다. 기존 정책 축소도 별도 승인 없이 하지 않는다.

### 기존 즉시 저장 배정 이관 규칙

- 첫 편집 시 서버의 카드/비공식/식당 배정을 전부 초안의 기준 스냅샷으로 읽는다.
- team_key 없는 비공식은 기존 개인 배정으로 보존한다. 같은 자료를 받은 사람들을 임의로
  한 팀으로 묶거나 개인 배정을 팀 배정으로 자동 승격하지 않는다.
- 팀으로 전환할 배정은 담당자가 명시적으로 확인한다. 전환되지 않은 개인 행은 계속 표시한다.
- 식당 개인 배정은 그대로 흡수하고, 해당 참가자가 현재 명단에 없어도 조용히 지우지 않고 표시한다.
- 초안에서 누락됐다는 이유만으로 기존 행을 삭제하지 않는다. 명시 해제 목록과 서버 버전을 검증한다.
- 기존 로컬 초안에 비공식/식당 필드가 없으면 빈 배정이라는 뜻이 아니다. 서버 자료를 합쳐 초기화한다.
